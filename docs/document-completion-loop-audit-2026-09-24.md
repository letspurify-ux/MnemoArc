# 문서 작성 반복과 조기 종료 점검

2026-09-24 기준으로 실행 루프, 도구 실패 복구, 문서 검토, 완료 조건 검증, 기능 목록 검사, 재개 경로를 점검했다. 반복 감지 자체는 필요하지만, 문서 작업을 횟수만으로 중단하는 정책과 실제 완료를 막는 재진입 조건이 함께 있었다.

## 확인한 문제와 수정

| 문제 | 수정 후 동작 | 회귀 검증 |
| --- | --- | --- |
| 최종 응답·동일 조회·수정·보완 횟수가 각각 고정 한도에 도달하면 실행 예산이 남아도 partial 또는 blocked로 종료 | 문서 작업의 횟수는 집중 복구 기준으로 사용한다. 원인을 유지하고 실제 수정·검증으로 돌아간다. 거절된 최종 응답 다음 일반 요청은 도구 동작을 요구한다. | 기존 한도를 넘긴 40회 반복 이후 저장·완료 조건 승인까지 진행. 끝까지 잘못 응답하는 경우 실행 토큰 예산으로 중단하고 재개 후 완료. |

| 유한한 페이지를 정상적으로 전진해도 32페이지에서 긴 문서 검토 종료 | 페이지 수 제한을 제거하고 요청별 입력 예산·전체 실행 토큰·시간을 적용한다. 모든 범위가 끝나기 전에는 승인하지 않는다. | 3,302줄 문서를 34페이지로 처리하고 빠진 범위 없이 최종 승인. |
| 구조 사전 검사 `final_check`가 총 검토 호출 수에 묶임 | 읽기 전용 사전 검사를 누적 호출 수로 차단하지 않는다. 내용 승인과 별개인 구조 검사라는 의미를 유지한다. | `review_limit=1`에서도 사전 검사 12회 성공, 내용 승인은 여전히 없음. |
| 검증 단계에서 필요한 검색 도구가 숨겨지고 누락 조사 항목의 신규 등록을 거부 | 특정 경로 검색과 구체적 문서 섹션을 지정한 누락 항목 등록을 허용한다. 넓은 재탐색과 섹션 없는 임의 확장은 계속 제한한다. | 검증 복구 중 helper 경로 검색과 누락 조사 항목 등록 성공. 기존 항목과 새 항목은 자동 검증 처리하지 않음. |
| 승인 결과가 문서·소스 해시만 확인해 바뀐 요구사항에도 재사용될 수 있음 | 원래 요청·완료 조건·제약·결과물 요구를 검토 버전에 포함한다. 검토 중 변경도 거부하고 페이지를 다시 구성한다. | 완료 조건·제약·결과물 변경과 소스 변경 시 이전 승인·거절 재사용 차단. |
| 검토 JSON 재시도에 오류 안내가 추가되면 문서 페이지 경계가 달라지고 근거 커서는 이전 범위를 가리킴 | 오류 안내 공간을 별도로 예약하고 근거 페이지가 끝날 때까지 문서 범위를 고정한다. | 수정 전에는 동일 문서의 종료 줄이 34에서 33으로 바뀌었다. 수정 후 재시도 문서·근거와 다음 근거 커서가 일치한다. |
| 검토 준비 중 잘못된 인용 경로 등 교정 가능한 오류로 실행 전체 종료 | 읽기 전용 검토에서 나와 실제 편집 단계로 원인을 전달하고, 부분 판정은 폐기한 뒤 다시 검토한다. | 없는 파일 인용을 교정하고 조사 항목 재검증·문서 검토·완료 조건 승인을 모두 통과. |
| 최종 채팅 답변이 검토 입력 상한을 넘으면 답변을 줄일 기회 없이 partial 종료 | 요구 문서는 유지하고 최종 채팅 보고를 줄여 완료 조건 검토를 재시도한다. | 긴 최종 답변을 거절한 뒤 간결한 답변으로 승인. 거절된 완료 주장은 게시하지 않음. |
| 문서 체크포인트가 입력 오류 8회에서 종료 | 실제 문맥·실행 예산 내에서는 원인 교정과 정리 완료를 계속한다. | 잘못된 체크포인트 ID 12회 후 13번째 완료로 문서 작업 재개·승인. 끝까지 실패하면 실행 예산에서 중단하며 원문 유지. |
| 비활성 도구 오류가 3회 누적되면 도구 선택으로 해결할 수 있어도 종료 | 도구 선택·지원 언어의 텍스트 조회 전환·체크포인트 완료로 교정할 수 있는 오류는 복구 대상으로 분류한다. | 비활성 도구 40회 이후 실제 문서 편집과 최종 승인까지 진행. 불확실한 쓰기는 기존 보호 유지. |
| 도구 호출 수 초과가 전체 작업 종료로 이어짐 | 배치 전체를 실행하지 않았음을 알리고 허용 개수 안에서 다시 호출하도록 한다. 도구가 없는 검토 요청에는 도구 재호출 대신 JSON 형식 교정만 안내한다. | 결과 예산의 2개 한도에 3개 요청, 32개 한도에 33개 응답, 공급자 파싱 거절 모두 복구·최종 승인. 문서·완료 검토 중 금지된 도구 호출도 미실행. |
| 문서 편집 인자가 출력 한도로 반복 잘리면 8회에서 종료 | 작은 완전한 호출로 다시 생성하도록 안내하고 남은 문맥·실행 예산으로 계속한다. | 잘린 도구 배치 40회 후 유효한 편집·최종 승인. 잘린 호출은 실행하지 않음. |

## 추가 정밀 검토

기존 수정이 있는 작업 폴더에서 다음 여섯 경로를 별도 테스트로 재현했다. 각 재현 테스트는 수정 전에 실패하는 것을 확인했다.

| 남아 있던 문제 | 수정 및 검증 |
| --- | --- |
| 공급자가 잘못된 도구 JSON·호출 ID를 파싱 단계에서 거절하면 도구 실행부의 복구 정책을 거치지 않고 blocked 종료 | 배치 전체가 미실행임을 알리고 원인 교정으로 돌아간다. 파싱 오류·잘못된 호출 식별자를 각각 12회 반환한 뒤 문서 저장과 완료 조건 승인까지 진행했다. 거절된 배치의 동반 쓰기도 실행되지 않았다. |
| 존재하지 않는 도구 이름을 세 번 호출하면 실제 도구를 선택할 기회 없이 종료 | `unsupported_tool`을 도구 목록 조회와 이름 교정으로 복구한다. 잘못된 이름 12회 이후 정상 도구로 저장하고 최종 승인했다. |
| 완료 검사에서 정상 전달된 읽기 결과를 다시 3,000자로 잘라, 요청한 뒷부분을 반복해서 잃음 | 관측을 설정된 도구 결과 토큰 예산으로 보존한다. 파일의 6,000자 미리보기 밖이면서 읽기 결과의 3,000자 뒤에 있는 근거가 최종 검토에 도달하는 것을 검사했다. |
| 같은 파일 근거를 다른 순서로 읽으면 근거 ID·배열 순서가 바뀌어 완료 검토를 다시 시작 | 파일 근거의 순서와 임시 참조 번호를 판정 버전에서 정규화한다. 교대 조회 12회에도 거절 검토는 한 번만 수행했다. 본문 없는 중복 읽기 안내는 새 근거로 저장하지 않는다. 실제 내용·파일·요구사항 변경과 쓰기·DB 관측 순서는 계속 구분한다. |
| 넓게 인용한 범위에서 `//` 주석을 제거해, 실제 계약 설명을 검토자가 볼 수 없음 | 근거 범위의 주석을 유지한다. 주석으로 된 24줄의 계약을 넓은 범위로 인용해 모두 전달한 뒤 승인했다. |
| 소스 근거를 고정 48줄씩 묶어 한 묶음이 요청 예산보다 커지면, 여러 페이지로 나눌 수 있어도 검토 실패 | 줄 수와 토큰 크기를 함께 제한해 근거를 나눈다. 길이가 큰 소스 60줄 전체를 중복·누락 없이 여러 페이지로 검토했다. 중간에 입력 예산을 바꿀 때에는 페이지와 부분 판정을 다시 구성하는 것도 확인했다. |

수정 위치는 [실행부](../src/agent.rs), [공급자 응답 처리](../src/llm.rs), [도구 오류 분류](../src/tools/recovery.rs), [완료 검토](../src/tools/completion_review.rs), [소스 문서 검토](../src/tools/document_review.rs)다.

복구된 공급자 파싱 오류도 실행 예산을 소모한다. 오류 응답의 사용량을 받지 못하면 요청별 입력 추정량과 예약 출력량을 반영하며, 30,000토큰 예산 테스트에서 저장된 초안을 보존하고 예산 사유로 중단하는 것을 확인했다.

## 최종 응답 경로 추가 점검

실행 루프의 최종 답변 처리, 공급자 응답 크기 검사, 설정 변경 경계를 다시 살펴보고 다음 조기 종료·조기 게시 경로를 재현했다.

| 재현한 경로 | 수정 후 동작 |
| --- | --- |
| 문서 작업 중 최종 JSON 답변의 인용이 잘못되면 수정 기회를 주지 않고 `partial`로 종료하며, 잘못된 답변을 스트림에 게시 | 인용 오류를 다음 요청에 전달하고 문서 작업을 이어간다. 12회의 잘못된 답변 뒤 인용을 바로잡아 최종 완료 조건 승인을 통과한다. 거절한 답변은 게시하지 않는다. |
| 설정 정리가 보류된 상태에서 모델이 최종 답변을 하면, 이미 유효한 설정 변경 명령이 대기 중이어도 실행을 `blocked`로 종료 | 현재 설정 아래에서 정리와 설정 적용을 계속 시도한다. 다음 요청 경계에서 유효한 설정 변경을 적용하고 최종 승인을 완료한다. |
| 공급자 SSE 디코더 또는 응답 검증에서 `response_size_limit`이 발생하면, 도구 배치가 한 번도 실행되지 않았는데도 문서 실행 전체를 종료 | 응답을 더 짧게 만들고 큰 문서 수정을 작은 완전한 호출로 나누도록 안내한다. 공급자 오류 12회와 파싱 완료 후 크기 검증 오류를 각각 복구해 실제 저장 및 승인을 마친다. 거절된 응답에 포함된 쓰기는 실행되지 않으며, 크기 초과가 최종 답변뿐이면 불필요한 도구 호출 없이 간결하게 재답변한다. |
| 도구 호출에 동반된 텍스트가 검증 전에 문서 완료를 주장해도 스트림과 대화 이력에 나타남 | 문서 작업의 도구 호출 문구는 최종 사용자 출력에서 보류한다. 도구 결과와 완료 조건을 확인한 최종 답변만 게시한다. |

이 변경도 실행 토큰과 전체 시간 예산을 우회하지 않는다. 설정 적용이 실제로 불가능하거나 공급자가 계속 잘못된 응답을 반환하면 해당 예산에서 중단하며 저장된 문서와 실패 원인을 유지한다.

## 완료와 중단의 의미

문서 작성은 결과 파일의 실제 저장 버전, 필요한 조사 항목과 인용 범위, 기능 목록의 누락, 활성화된 문서 내용 검토, 최종 완료 조건 검증을 모두 통과해야 complete가 된다. 횟수 제한을 넘겼다고 승인하거나 사용자 요구를 낮추지 않는다. 검증 전 완료 주장은 스트림과 최종 답변 이력에 게시하지 않는다.

전체 실행 토큰·시간 예산과 사용자 취소는 계속 적용한다. 문맥·보관 용량, 체크포인트 원문 보존·커밋 실패, 모델 통신 및 실행 오류, 결과를 확인할 수 없는 쓰기 같은 실제 진행 불가 상황의 보호도 유지한다. 체크포인트 인자 오류나 잘린 문서 편집 호출은 횟수만으로 중단하지 않는다. 문서 검토·완료 조건 검토의 잘못된 JSON도 오류를 다음 요청에 전달해 남은 예산으로 복구하며, 각각 12회 실패 후 13번째 유효한 응답으로 완료하는 경로를 검사한다. 문서 외 작업의 기존 반복 중단 정책은 변경하지 않았다.

이 검증은 실제 파일 도구와 실행 상태 전이를 사용하되 모델 응답은 재현 가능한 테스트 대역으로 공급한다. 실제 공급자 모델이 모든 문서를 예산 안에서 완성한다는 보장은 아니며, 실행 중 서버나 기존 세션을 변경한 검증도 아니다.

## 실행한 검증

- 최종 전체 `npm test`: Rust 353개, JavaScript 9개 통과. Rust의 기존 명시적 실행 대상 5개는 ignored로 유지했다.
- 기존 정밀 검토에서 회귀 테스트 8개, 최종 응답 경로 추가 점검에서 6개를 추가했다. 여섯 기존 문제의 수정 전 실패와 수정 후 통과 외에 DB 관측 순서 보존, 공급자 파싱 오류의 실행 예산 차감, 최종 답변의 보류·복구, 설정 적용, 큰 응답의 무실행 복구를 검사했다.
- `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check`, `git diff --check` 통과.
- 유료 공급자 모델을 사용하는 라이브 테스트와 운영 서버 재시작은 수행하지 않았다.

## 후속 변경: 마감 단계와 실제 모델 검증 (2026-09-24~25)

위 점검 뒤 등록 프로젝트 `llm_agent` 문서 작업을 실제 모델(OpenRouter `z-ai/glm-5.3-flash`)로 반복 실행했다(`tests/live_documentation.rs`, 실행 한도 토큰 10M·1시간, DB 도구와 답변 검토는 끄고 문서 검토·완료 조건 검증은 켬). 그 결과 위 문서의 일부 정책은 다음처럼 바뀌었다.

| 위 문서의 정책 | 현재 정책 |
| --- | --- |
| 문서 작업은 반복 횟수로 종료하지 않고 실행 예산까지 계속한다(40회 반복 이후에도 진행). | 하나의 진척 점수로 판단한다. 점수가 오르지 않은 요청이 정체 기준의 1배면 집중 안내, 2배면 탐색 도구 축소(문서가 생긴 뒤에만), 3배이거나 남은 예산이 마감 예산 비율(기본 10%) 이하면 마감 단계. 마감 단계는 최대 12회 요청 안에 저장된 문서를 `complete_with_gaps`로 마감하고 확인하지 못한 항목을 모두 보고한다. |

### 현재 권장 설정 (이 모델 기준)

`context_tokens` 160000, `output_tokens` 16000, `low_water` 0.4, `stall_round_limit` 8, `request_timeout_secs` 180. 이 모델은 라운드마다 도구를 한 번 정도만 호출하므로, 비용은 주로 매 요청 다시 보내는 문맥 크기에 비례한다. 입력 예산을 너무 크게 잡으면 체크포인트는 줄지만 요청당 비용이 늘어난다(3차 실행).

### 남은 한계

- 성공 사례는 현재 코드 기준 12차 1회다. 실행마다 모델의 경로 선택이 크게 달라 안정성은 반복 실행으로 계속 확인해야 한다.
- 마감 단계의 `mark_gap`, 검토 미반영 마감(`review_unrepaired`), 예산 소진 마감은 테스트 대역으로 검증했고, 실제 모델로는 8·11차에서만 일부 경로가 동작했다.
- 같은 요청에서도 검토 모델의 분량 판정이 다르다(7차 88줄 통과, 8차 91줄 거절). 분량이 중요하면 요청에 하한을 명시한다.
