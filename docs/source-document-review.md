# 소스 문서 작업과 완료 검토

## 문제와 변경

등록된 `llm_agent`의 실제 모델 실행에서 문서 작업이 단순 질문 종료 안내를 받았고, task_state에 존재하지 않는 필드를 보내며 비용을 썼다. 75줄 문서에 누적 입력 1,031,828토큰이 들었으며, 인용 구조 검사를 통과한 뒤에도 루프 종류 오류와 history 정규화 설명 누락이 남았다.

작업 방식(workflow)은 사용자가 세션 창의 "작업 방식"에서 고른다: 질문 답변(`answer`, 기본값), 소스 기반 문서 작성(`source_document`). 간단한 결과 문서 편집은 `answer`에서 기본 활성화된 document_edit/document_edit_batch로 하며, 문서 작업 검증(진행 정체 처리·마감 단계·완료 조건 검토)을 받지 않는다. `answer`는 완료 조건 검토를 포함한 어떤 검토도 실행하지 않으며 document_audit을 선택할 수 없다. 선택은 다음 요청부터 적용되며 새 요청마다 task에 반영된다. `source_document`는 document_edit/document_edit_batch/document_audit를 즉시 활성화하고 매 저장에서 인용 검사를 실행한다. 모델은 workflow를 바꿀 수 없고(`workflow_selected_by_user`), 첫 task_state에서 구체적인 `completion`과 deliverables만 채운다. 첫 사용자 메시지 전에 설정한 완료 조건은 보존하며, 조건이 없으면 사용자 요청을 바탕으로 초기값을 만든다. `completion: []`로 기존 조건을 지우는 갱신은 거부한다. 이후 새 요청은 검토 상태를 초기화하고 새 완료 조건을 만들며, continue/resume는 상태를 유지한다. 저장된 프로젝트 목적·출력 경로만으로 문서 작업을 추정하지 않는다.

```json
{"action":"update","patch":{"deliverables":["요청한 백엔드 문서"],"completion":["요청 검증과 history 정규화 설명","모든 분기와 종료 조건 설명"]}}
```

- task_state patch는 실제 필드와 타입을 명시한다. 빈 patch는 revision을 올리지 않는다.
- 문서 작업에는 6라운드 단순 답변 안내를 적용하지 않는다. 라운드 수로 작성을 재촉하지도 않는다. 얼마나 읽고 언제 쓸지는 모델이 요청과 근거로 판단한다(6라운드 뒤 작성 우선 안내와 "짧은 첫 섹션부터 저장" 지침을 따라, 파일 한두 개만 읽고 짧은 문서로 끝낸 실행이 있었다). 분석·조사 범위·할 일 관리를 줄이라는 지시도 없앴다("요청한 흐름만 조사", "모든 보조 함수를 훑지 말 것", "부족한 근거만 읽을 것", 30줄 단위 읽기, "계획 편집·분할은 진척이 아님", 검증 단계의 "범위를 넓히지 말 것"). 채팅 답변용 간단 응답 지침은 답변(answer) 작업에만 남긴다. 예산이 절반 아래로 줄면 남은 예산 안에서 문서를 완성하도록 계획하라는 안내가 나가고, 진행 정체 처리는 같은 동작의 반복만 막는다. 다만 인용은 필수이고 줄 번호는 읽은 원문이 활성 문맥에 있을 때만 보이므로, 섹션의 근거가 갖춰지면 그 섹션을 인용과 함께 바로 따로 저장하고 다음 섹션을 읽으라고 안내한다(라운드 수가 아니라 근거 기준이다). 인용 형식은 `frontend/src/App.jsx:120-140`처럼 프로젝트 상대 경로와 `-` 범위로 쓰고, 파일 이름만 쓰거나 `~` 범위·괄호 범위를 쓰지 말라고 예를 든다(`App.jsx(1~140)`처럼 써서 인용 0개로 293줄을 저장한 실행이 있었다). 체크포인트는 기억과 진행 요약만 남기고 앞서 읽은 원문을 활성 문맥에서 빼므로, 인용할 줄 범위는 `memory_write`의 출처(`source_ids`)로도 남기라고 안내한다. `memory_read`는 출처마다 경로와 줄 범위를 돌려준다. 체크포인트 요청과 인용 없는 문서 저장 결과에도 같은 내용을 붙였다(파일 43개를 읽고 체크포인트 두 번 뒤 313줄을 한 번에 쓴 실행이 줄 번호를 몰라 인용 없이 저장했고, 인용을 채우려 다시 읽는 데 입력 약 180만 토큰을 썼다).
- 실제 전달 범위·cursor를 따르고 섹션을 한 번에 전체 쓰기 대신 따로 저장하도록 안내한다. 첫 섹션은 `create`로 저장하고, 이후 현재 목차를 확인해 끝에 둘 섹션은 `append`, 중간에 둘 섹션은 `insert_before`·`insert_after`, 기존 섹션 수정은 `section`으로 처리한다. 읽지 않은 내용을 채우도록 강요하지 않는다.
- 문단이나 문장 수준의 수정은 `replace_text`·`delete_text`·`insert_before_text`·`insert_after_text`로 고유한 원문을 지정한다. 전체 파일을 다시 쓰지 않고 저장된 해시와 수정 결과를 확인한다.
- 문서 수정 결과의 `citation_check.unread_citations`는 인용했지만 이번 세션에서 현재 파일 버전의 완전한 줄로 전달되지 않은 범위다(파일별로 인접 범위를 합친다). 해당 범위를 `file_read`로 읽거나 인용을 읽은 줄로 좁힌다. 등록·검증 호출은 없으며 런타임이 저장·감사·완료 판정마다 전달된 근거 레지스트리에서 다시 계산한다. 소스 파일이 바뀌면 이전 읽기는 무효가 된다.
- 매 문서 쓰기에서 인용 경로·줄 범위 문제(`citation_check`)와 Markdown·Mermaid 형식 검사 결과(`format_check`)를 함께 즉시 반환한다. 부분 초안을 거부하지 않으며, 읽지 않은 인용은 최종 감사에서 다시 검사한다.
- 쉼표로 묶은 `file.js:3, 8-10`은 각 범위를 검사하고 검토 근거에 함께 포함한다.
- 일반 코드 예시의 인용은 감사에서 제외하지만 Mermaid 안의 소스 인용은 검사한다.

## 최종 완료 조건

기존 쓰기 해시·읽지 않은 인용·구조 검사가 통과하면 `source_document_review=true`일 때 별도의 읽기 전용 모델 요청으로 문서를 검토한다. 인용이 하나도 없는 문서는 대조할 소스가 없으므로 최종 답변을 거절하고 `경로:줄` 인용을 요구한다. 마감 단계에서는 문서 검토 없이 수락하되 소스 인용이 없다는 미확인 항목으로 보고한다. 같은 모델을 사용하며, 별도 에이전트나 도구 실행 권한을 주지 않는다.

모델에 완료 준비 안내를 제공할 때도 실제 최종 처리와 같은 구조 감사를 수행한다. 읽지 않은 인용 범위, 잘못된 인용, 형식 문제가 남으면 완료 안내나 할 일 일괄 종료 안내를 제공하지 않는다. 대신 `document_readiness`에 문제·절 경로·감사 페이지의 revision을 전달해 필요한 읽기·수정으로 돌아가게 한다.

기존 결과 문서를 부분 수정할 때는 작업의 첫 성공적인 문서 편집 직전 원문을 런타임 기준본으로 보관한다. 미완료 작업에서 요구사항을 추가하거나 바꾸더라도 기존 보존 조건을 검증할 수 있도록 최초 기준본을 유지한다. 재시도·체크포인트·단순 진행 재개·검토 증거의 보관 한도 초과로도 기준본을 바꾸지 않는다. 새 사용자 작업 또는 `complete`로 끝난 결과에 대한 명시적 수정 요청에서 새 비교를 시작한다. 해당 작업에서 새로 생성한 문서는 이전 원문이 없으므로, 명시적 후속 수정 요청 시 저장된 초안을 새 기준본으로 삼을 수 있다. 기준본 갱신은 다음 성공적인 편집의 직전 원문으로 이루어진다. 완료 검토에는 `runtime_document_changes`로 기준본·현재 파일 해시, 변경 전후 텍스트와 줄 범위, 나머지 범위의 동일 여부를 전달한다. 수정 전 읽기 결과는 여전히 오래된 현재 상태 증거로 제외하지만, 런타임 기준본은 원문 보존 비교에 사용할 역사적 증거로 구별한다. 인용 읽기 상태만으로 원문 보존을 인정하지 않는다.

기준본은 최대 256KiB, 변경 텍스트는 총 12,000자와 변경 범위 64개까지 보관·전달하며 세션 메모리 한도에도 포함한다. 줄 비교의 작업량을 넘으면 공통 앞뒤를 제외한 하나의 넓은 변경 범위로 표시한다. 기준본이나 변경 내용이 생략되면 `truncated`를 명시하며 생략된 부분의 보존을 확인했다고 판단하지 않는다. 큰 기준본을 보관하지 못해도 기준본·현재 파일의 전체 해시가 동일하면 무변경임을 확인할 수 있다.

최종 채팅에서 요구한 생성 경로·검증 범위 보고는 문서 본문 요구와 구분한다. 검토 입력은 원래 사용자 요청, 요청 시작 전에 지정된 completion/constraints/deliverables, 프로젝트 설정의 독자(`audience`)·목적(`purpose`), 실제 문서의 번호가 붙은 범위와 줄 수, 그 범위에서 인용한 소스의 현재 본문이다. 검토자는 독자 수준에 맞춰 세부 수준을 판단한다. 일반 사용자 같은 비개발자 독자의 문서에는 화면·버튼·메시지·보이는 결과 수준의 정확성만 요구하고, 내부 식별자·상태 변수·요청 값·경로·코드 수준 조건을 요구하지 않으며 문서에 들어간 내부 세부는 독자 용어로 고치도록 지적한다. 작업 중 모델이 `task_state`에 추가한 조사 등록·검증 같은 실행 조건은 문서의 필수 내용으로 넘기지 않는다. 문서는 요청당 최대 100줄과 토큰 예산에 맞춰 나누고, 가능하면 Markdown 제목 경계에서 끊는다. 인용 구간 앞뒤 8줄도 포함해 루프 선언이나 조건을 본문과 함께 확인한다. 겹친 구간을 합치되 넓은 인용 범위의 `//` 주석도 원래 줄 번호와 함께 보존한다. 파일별 근거 묶음은 최대 48줄과 토큰 크기를 함께 고려해 나누고 번갈아 전달한다. 긴 소스 줄이 많아도 인용 범위를 축소하지 않고 여러 페이지로 검토한다. 문서와 근거의 모든 페이지가 끝나야 검토 시도 1회가 완료되고, 중간에 문서·소스·요구사항이 바뀌면 처음부터 다시 검토한다. 재개 중 모델이나 입력 예산이 바뀌어 묶음 경계가 달라질 때도 부분 판정을 초기화해 새 페이지를 건너뛰지 않는다. 접근에는 기존 프로젝트 경계·include/exclude 규칙을 적용한다.

- 요청 전체 입력 상한: 로컬 추정 24,000토큰 또는 설정의 입력 예산 중 작은 값. 이는 모델 문맥 길이가 아닌 검토 요청당 비용·크기 상한이므로, 여러 페이지의 누적 입력은 이 값보다 클 수 있다. 한 줄이나 요구사항 자체가 들어가지 않으면 명시적인 오류와 함께 편집 단계로 돌아간다. 원래 요구를 낮추지 않고 문서 줄·인용 범위·중복 작업 메타데이터 등을 교정한 뒤 다시 검토한다. 페이지 수로 중단하지 않으며, 유한한 문서·근거 범위를 전진하면서 전체 실행 토큰·시간 예산을 적용한다.
- 잘못된 응답의 오류 안내는 128토큰으로 제한하고 이를 위한 공간을 페이지 구성 전에 따로 예약한다. 같은 문서 범위의 근거를 여러 페이지로 읽는 동안에는 문서 경계를 고정하므로 재시도 안내가 길어져도 근거 커서와 인용 범위가 어긋나지 않는다.
- 요청 출력 상한: 첫 요청은 4,096토큰 또는 설정 출력 상한 중 작은 값이다. 출력 제한으로 JSON을 완성하지 못한 복구 요청은 설정된 출력 상한을 사용해 추론 토큰이 검토 JSON을 가로막지 않게 한다.
- `review_limit`은 문제가 줄거나 새 문서 내용·검증이 생기지 않은 검토가 누적될 때 집중 복구로 전환하는 기준이다. 검토 지적의 문구만 달라지는 것은 진전으로 세지 않는다. 본문 줄 수 증가는 직전 판정에 문서 길이 부족 지적이 있을 때만 진전으로 센다. 지적을 고치면 문서가 대개 길어지므로, 그렇지 않으면 새 지적이 계속 나올 때 정체가 감지되지 않는다. 이 횟수에 도달해도 남은 실행 예산으로 수정을 계속한다.
- `document_repair_limit`(기본 8, 양의 정수)은 지적 후 자동 재검토 간격이다. `document_edit` 또는 `document_edit_batch`가 포함된 모델 요청을 한 번으로 세며 실패한 시도도 포함한다. 읽기·조회·검증·최종 답변·체크포인트 정리는 제외한다. 간격에 도달한 요청의 편집과 동반 도구 호출을 모두 실행한 뒤 변경된 문서를 재검토한다. 실패·무변경 편집으로 문서와 근거가 그대로면 기존 지적을 재사용하고 다음 수정 구간을 시작한다. 이미 제안된 편집 요청을 버리지 않는다.
- 체크포인트 정리는 문서 작업에서 요청 16회 또는 실패 16회 뒤 종료한다(일반 작업은 각각 8회). 잘못된 확인 ID나 확인 누락을 같은 세션 예산 전체 동안 반복하지 않고, 원래 이력과 완료된 변경을 보존한 채 `checkpoint_retry_limit`으로 막는다. ID 불일치는 오류에 현재 기대 ID를 돌려준다.
- 결과는 페이지마다 최대 12개의 구체적인 문제를 담은 JSON이며, 전체 검토에서 최대 12개를 유지한다. 문제가 있으면 실제 수정·검증 도구 호출로 돌아간다. 같은 문서·근거·요구사항에 대한 반복 최종 답변은 새 검토 호출을 만들지 않는다. 승인과 거절 모두 문서·소스 해시 및 원래 요청·완료 조건·제약·결과물 요구가 같은 경우에만 재사용한다.
- 파싱 실패, 입력·출력 한도, 검토 중 근거 변경은 성공으로 처리하지 않는다. 완전한 JSON은 잘못 붙은 `length` 플래그만으로 거부하지 않지만 도구 호출이 섞인 응답은 거부한다. 잘못된 검토 JSON에는 오류 원인을 다음 요청에 전달하고, 문서와 `pending` 상태를 유지한 채 남은 실행 예산으로 형식을 교정한다. 문서 작업은 연속 8회 같은 별도 응답 횟수로 중단하지 않는다. 전체 실행 예산·취소·실제 실행 오류의 제한은 유지한다.
- 검토 요청 준비 중 인용 경로 누락이나 입력 크기 문제처럼 모델이 교정할 수 있는 오류는 읽기 전용 검토를 해제하고 원인을 실제 편집·근거 조회 단계로 전달한다. 부분 검토 결과는 폐기하고 이후 현재 문서로 다시 시작한다. 최종 채팅 답변만 길어 완료 조건 검토에 들어가지 못했다면 답변을 줄여 재검증하며, 이미 유효하게 승인된 문서 검토는 유지한다.
- 문서 검토는 모델의 최종 답변이 계기가 된다. 런타임은 그 답변과 당시 문서 해시를 보관하고, 같은 문서에 대한 검토가 모든 문서·근거 페이지와 지적 검증을 마치고 승인되면 모델에게 다시 묻지 않고 보관한 답변으로 최종 처리(할 일·구조 감사·완료 조건 검토)를 이어간다. 건너뛴 페이지 때문에 승인 없이 미검토로 끝난 검토도 같은 답변을 미검토로 수락한다. 보관한 답변은 검토가 진행 중인 동안 페이지·검증 요청 사이에서 유지한다(첫 페이지 응답에서 버려져, 근거 페이지 2개와 지적 검증으로 승인된 라이브 실행이 같은 답변을 다시 받는 데 입력의 3.9%를 썼다). 승인된 답변의 재시도는 마감 단계의 최종 답변 횟수에 더하지 않는다. 거절되거나, 검토 사이에 다른 요청·체크포인트가 끼었거나, 문서가 바뀌었으면 보관한 답변을 버리고 기존처럼 모델로 돌아간다. 라이브 실행에서 승인 뒤 같은 답변을 다시 받는 요청이 실행 입력의 4~8%(약 39K~47K 토큰)를 썼다.
- 검토 중의 JSON과 검증 전 ‘완료’ 주장은 스트림·최종 답변 이력에 노출하지 않는다. 오류/partial 상태와 작성된 문서는 보존한다.
- 리뷰 지적은 문서에 붙이는 메모가 아니라 관련 원문 섹션의 수정 지시로 다룬다. 수정 단계에서는 최종 목차의 검토 메모 섹션을 확인하고, 최종 모델 검토에서도 사용자가 요청하지 않은 수정 목록 섹션을 문제로 보고한다. 사용자가 후속 과제 섹션을 명시적으로 요청했거나 주제를 이해하는 데 필요한 실제 한계는 유지한다.
- session API와 모델 상태에 검토 횟수·문제·토큰·승인 해시를 제공한다. 설정 화면의 **소스 문서 검토**로 끌 수 있다.

이 검토 역시 모델 판단이다. `document_audit.semantic_verified`는 계속 false이며, 읽지 않은 인용 검사는 인용한 줄이 전달됐음을 확인할 뿐 문서 의미를 증명하지 않는다. 다음 페이지가 있으면 검토 입력과 상태에 표시하고, 모든 페이지가 처리되기 전에는 승인하지 않는다. 모델이 지적하지 않은 오류까지 없음을 보장하지 않는다.

### 사용자용 설명과 검증용 출처

독자 수준에 관한 지침은 본문의 설명 내용에 적용한다. 일반 사용자 매뉴얼에서도 주장에 연결된 파일 경로·줄 번호 인용은 필수 검증 정보로 인정한다. 리뷰어는 독자 수준이나 가독성을 이유로 정확한 출처를 삭제·생략하거나 매뉴얼 내부 링크로 바꾸거나 부록·별도 문서로 옮기도록 요구하지 않는다. 부정확한 동작 설명, 근거가 없는 주장, 불필요한 내부 구현 설명은 계속 지적하고, 잘못된 인용은 올바른 근거 범위나 근거에 맞는 설명으로 수정하도록 요구한다.

독자가 개발자가 아니면 런타임이 문서 본문에서 찾은 구현 세부(식별자로 읽히는 인라인 코드, 본문의 `::` 경로, Mermaid가 아닌 코드 블록, 다이어그램 노드·연결선 라벨의 식별자)를 검토 요청의 `audience_flags`(줄·종류·텍스트)로 넘긴다. 리뷰어는 이번 페이지 범위 안의 항목 중 독자가 화면에서 보지 않는 것을 `requirement_id`가 `audience`인 scope 지적으로 보고하고, 독자의 말로 바꾸도록 요구한다. 화면에 보이는 이름은 지적하지 않는다. 일반 사용자용 라이브 문서가 함수 이름과 오류 코드를 그대로 썼는데, 리뷰어가 독자 수준 지침이 있는데도 지적하지 않았다.

런타임은 테스트 코드를 가리키는 인용도 검토 요청의 `test_code_citations`(문서 줄·인용)로 넘긴다. 리뷰어는 이번 페이지의 그런 인용이 테스트 방법이 아니라 제품 동작에 대한 주장을 뒷받침하면, 그 동작을 구현한 제품 코드를 인용하라는 citation 지적을 낸다. 라이브 문서가 테스트의 반복문을 "리뷰가 반복되는 방식"의 근거로 인용했는데 리뷰가 승인했다.

리뷰 지침의 해시를 판정 재사용 조건에 포함한다. 지침이 바뀌면 실행 재개와 리뷰 요청 전에 기존 지적·승인·실패 판정·부분 검토·수정 횟수를 초기화하고 현재 문서 전체를 다시 검토한다. 누적 검토 횟수와 토큰 사용량은 보존한다. 이전 지침으로 요청한 리뷰 응답도 수락하지 않는다.

## 재현과 테스트

일반 회귀 테스트는 API 비용 없이 워크플로 잠금·스키마·선언 줄과 주석 포함·해시 무효화·부정확한 문서 거부·변경 없는 검토의 재사용·실행 예산 종료·긴 근거의 페이지 진행·잘못된 Mermaid 인용·검증 전 완료 주장 노출 방지를 검사한다.

유료 문서 평가는 기본 cargo test에서는 실행하지 않는다. 명시적으로 다음을 실행한다.

```sh
MNEMOARC_LIVE_TEST=1 MNEMOARC_DOC_REPORT=/tmp/mnemoarc-document-report.json \
  cargo test --test live_documentation registered_source_documentation -- --ignored --nocapture
```

일반 사용자 매뉴얼의 출처 유지 문제는 등록된 MnemoArc의 새 세션 버튼 소스로 세 가지를 비교한다: 정확한 설명·인용은 승인하고, 틀린 동작 설명과 무관한 인용은 거절하는지 확인한다. 각 문서는 임시 경로에 저장하며 요청·응답·사용량을 보고서에 기록한다.

```sh
MNEMOARC_LIVE_TEST=1 MNEMOARC_LIVE_MODEL=stealth/space-bunny-alpha \
  MNEMOARC_REVIEW_REPORT=/tmp/mnemoarc-citation-review.json \
  cargo test --test live_documentation registered_user_manual_review_preserves_citations -- --ignored --nocapture
```

2026-09-29에 `stealth/space-bunny-alpha`로 위 세 사례를 실행했다. 정확한 설명·인용은 지적 없이 승인됐고, 틀린 설명과 무관한 인용은 각각 구체적인 수정 요구와 함께 거절됐다. 출처 삭제 요구는 없었다. 세 리뷰의 공급자 집계는 입력 5,137토큰·출력 359토큰이며, 모델 요청 소요 시간의 합은 약 8.1초다. 이 평가는 새 세션 버튼에 관한 짧은 리뷰 입력 세 건을 대상으로 한다.

`MNEMOARC_LIVE_CONFIG`로 설정 파일을 지정할 수 있다. 전체 문서 생성 평가인 `registered_source_documentation`은 기본 등록 프로젝트 llm_agent와 설정된 모델·토큰 예산을 사용하고, 별도 지정이 없으면 실행 시간 상한을 900초로 제한한다. 임시 출력으로 생성해 원래 문서를 보호한다. 보고서에 생성 문서, 호출 기록, 첫 작성 시점, 사용량, 검토 상태, 원본 불변 여부를 저장한다. 문서 검토와 완료 조건 검토의 요청·응답은 `review_calls`에 남긴다(완료 조건 검토가 빠져 있어, 라이브 실행에서 거절 뒤 이어진 보완의 이유를 모델의 기록으로 추정해야 했다). 각 호출에는 응답을 처리한 업스트림 프로바이더(`provider`, OpenRouter처럼 스트림이 알려 줄 때)와 요청을 보낸 뒤 첫 스트림 이벤트까지 걸린 시간(`first_event_seconds`)도 남긴다. 같은 리뷰 페이지가 한 실행에서는 116초, 다른 실행에서는 11초 걸렸는데, 프로바이더에서 기다린 시간과 생성 시간을 구분할 수 없었다. `MNEMOARC_DOC_MAX_INPUT`을 지정하면 누적 입력 상한도 검사한다. 토큰은 누적 사용량이지 고유 소스 크기나 청구 금액이 아니다. 비용과 정확성을 평가할 때 동일 조건 반복 실행 및 별도 소스 대조가 필요하다.
