# 소스 문서 작업과 완료 검토

## 문제와 변경

등록된 `llm_agent`의 실제 모델 실행에서 문서 작업이 단순 질문 종료 안내를 받았고, task_state에 존재하지 않는 필드를 보내며 비용을 썼다. 75줄 문서에 누적 입력 1,031,828토큰이 들었으며, 인용 구조 검사를 통과한 뒤에도 루프 종류 오류와 history 정규화 설명 누락이 남았다.

문서 작업은 첫 task_state에서 `workflow: "source_document"`와 구체적인 `completion`을 선언한다. 이 선언은 근거 검증 요구를 잠그고 investigation/document_edit/document_audit를 즉시 활성화한다. 첫 사용자 메시지 전에 설정한 완료 조건은 보존하며, 조건이 없으면 사용자 요청을 바탕으로 초기값을 만든다. 빈 완료 조건으로 문서 작업을 시작하거나 `completion: []`로 기존 조건을 지우는 갱신은 거부한다. 이후 새 요청은 선언과 검토 상태를 초기화하고 새 완료 조건을 만들며, continue/resume는 상태를 유지한다. 일반 질문은 이 선언 없이 답하고, 기존 문서의 단순 편집은 `document_edit` 모드를 사용한다. 저장된 프로젝트 목적·출력 경로만으로 문서 작업을 추정하지 않는다.

```json
{"action":"update","patch":{"workflow":"source_document","deliverables":["요청한 백엔드 문서"],"completion":["요청 검증과 history 정규화 설명","모든 분기와 종료 조건 설명"]}}
```

- task_state patch는 실제 필드와 타입을 명시한다. 조사 항목은 task_state가 아닌 investigation upsert로 만든다. 빈 patch는 revision을 올리지 않는다.
- 아직 조사 항목이 없어도 문서 작업에는 6라운드 단순 답변 안내를 적용하지 않는다. 6라운드 이후 초안이 없으면 작성 우선 안내를 주되, 낮은 예산에서 이미 검증 단계인 경우를 되돌리지 않는다. 이 안내는 모델을 돕는 지침이며 읽기를 강제로 차단하지 않는다.
- 실제 전달 범위·cursor를 따르고 조사한 섹션을 하나씩 저장하도록 안내한다. 짧은 첫 섹션을 `create`로 저장하고, 이후 현재 목차를 확인해 끝에 둘 섹션은 `append`, 중간에 둘 섹션은 `insert_before`·`insert_after`, 기존 섹션 수정은 `section`으로 처리한다. 읽지 않은 내용을 채우도록 강요하지 않는다.
- 문단이나 문장 수준의 수정은 `replace_text`·`delete_text`·`insert_before_text`·`insert_after_text`로 고유한 원문을 지정한다. 전체 파일을 다시 쓰지 않고 저장된 해시와 수정 결과를 확인한다.
- 문서 수정 결과의 `verification_required_ids`만 재검증한다. `preserved_verified_ids`는 섹션·소스·참조 기억이 유효하여 검증을 유지한 항목이다. `verify_batch`에 다시 포함해도 유효성을 확인한 뒤 기존 검증과 근거를 재사용하며 `reused_ids`로 알린다. 근거를 의도적으로 교체하려면 단일 `verify`를 사용한다.
- 매 문서 쓰기에서 인용 경로·줄 범위 문제를 즉시 반환한다. 부분 초안을 거부하지 않으며, 전체 조사 상태는 최종 감사에서 검사한다.
- 쉼표로 묶은 `file.js:3, 8-10`은 각 범위를 검사하고 검토 근거에 함께 포함한다.
- 일반 코드 예시의 인용은 감사에서 제외하지만 Mermaid 안의 소스 인용은 검사한다.

## 최종 완료 조건

기존 쓰기 해시·조사 항목·소스 변경·구조 검사가 통과하면 `source_document_review=true`일 때 별도의 읽기 전용 모델 요청으로 문서를 검토한다. 같은 모델을 사용하며, 별도 에이전트나 도구 실행 권한을 주지 않는다.

최종 채팅에서 요구한 생성 경로·검증 범위 보고는 문서 본문 요구와 구분한다. 검토 입력은 원래 사용자 요청, completion/constraints, 실제 문서의 번호가 붙은 범위와 줄 수, 그 범위에서 인용한 소스의 현재 본문이다. 문서는 요청당 최대 100줄과 토큰 예산에 맞춰 나누고, 가능하면 Markdown 제목 경계에서 끊는다. 인용 구간 앞뒤 8줄도 포함해 루프 선언이나 조건을 본문과 함께 확인한다. 겹친 구간을 합치고, 넓은 범위의 주석만 있는 `//` 줄은 생략하되 16줄 이하의 명시적 인용 구간에 있는 주석은 보존한다. 원래 줄 번호는 유지한다. 파일별 48줄 묶음을 번갈아 넣어 한 파일이 예산을 독점하지 않게 한다. 문서와 근거의 모든 페이지가 끝나야 검토 시도 1회가 완료되고, 중간에 문서·소스가 바뀌면 처음부터 다시 검토한다. 접근에는 기존 프로젝트 경계·include/exclude 규칙을 적용한다.

- 요청 전체 입력 상한: 로컬 추정 24,000토큰 또는 설정의 입력 예산 중 작은 값. 이는 모델 문맥 길이가 아닌 검토 요청당 비용·크기 상한이므로, 여러 페이지의 누적 입력은 이 값보다 클 수 있다. 한 줄이나 요구사항 자체가 들어가지 않거나 총 32페이지를 넘으면 명시적으로 실패한다.
- 요청 출력 상한: 첫 요청은 4,096토큰 또는 설정 출력 상한 중 작은 값이다. 출력 제한으로 JSON을 완성하지 못한 복구 요청은 설정된 출력 상한을 사용해 추론 토큰이 검토 JSON을 가로막지 않게 한다.
- `review_limit`은 문제 해결·감소, 새 문서 제목·본문 줄 또는 새 조사 항목 검증 없이 이어진 전체 검토 횟수의 한도다. 이런 진전이 있으면 정체 횟수를 다시 센다. 한도에 도달해도 문서 또는 검토 근거가 바뀐 뒤에는 재검토할 수 있다. `document_repair_limit`(기본 8, 양의 정수)은 지적 후 다음 재검토까지 허용하는 편집 요청 수다. 이 수에 도달한 뒤 모델이 다시 편집을 요청하면 현재 문서를 먼저 재검토하고, 남은 문제가 있으면 다음 수정 구간을 시작한다. `document_edit`를 포함한 모델 요청만 1회로 세며, 한 요청에 여러 편집이 있어도 1회다. 실패한 편집 시도도 포함하지만 읽기·조회·검증·최종 답변·체크포인트 정리·문서 리뷰 요청은 제외한다. 전체 실행 토큰·시간·취소 제한은 그대로 적용된다.
- 결과는 페이지마다 최대 12개의 구체적인 문제를 담은 JSON이며, 전체 검토에서 최대 12개를 유지한다. 문제가 있으면 수정 단계로 돌아가고 진전 없는 검토가 `review_limit`에 도달하면 partial로 보존한다. 파싱 실패, 제한 초과, 근거 변경도 성공으로 처리하지 않는다. 완전한 JSON 본문이 있으면 호환 provider가 잘못 붙인 tool-call 메타데이터나 `length` 종료 플래그만으로 실패시키지 않는다. 유효한 본문을 얻지 못한 복구가 8회에 도달하면 문서와 `pending` 검토 상태를 보존한 partial로 반환하며, 계속 실행해 재시도할 수 있다.
- 문서 해시와 검토에 사용한 소스 해시가 그대로인 경우에만 승인 결과를 재사용한다.
- 검토 중의 JSON과 검증 전 ‘완료’ 주장은 스트림·최종 답변 이력에 노출하지 않는다. 오류/partial 상태와 작성된 문서는 보존한다.
- 리뷰 지적은 문서에 붙이는 메모가 아니라 관련 원문 섹션의 수정 지시로 다룬다. 수정 단계에서는 최종 목차의 검토 메모 섹션을 확인하고, 최종 모델 검토에서도 사용자가 요청하지 않은 수정 목록 섹션을 문제로 보고한다. 사용자가 후속 과제 섹션을 명시적으로 요청했거나 주제를 이해하는 데 필요한 실제 한계는 유지한다.
- session API와 모델 상태에 검토 횟수·문제·토큰·승인 해시를 제공한다. 설정 화면의 **소스 문서 검토**로 끌 수 있다.

이 검토 역시 모델 판단이다. `document_audit.semantic_verified`는 계속 false이며, `investigation.verify_batch`는 에이전트의 대조 확인 기록이다. `final_check`는 구조 사전 검사이며 문서 의미를 증명하지 않는다. 다음 페이지가 있으면 검토 입력과 상태에 표시하고, 모든 페이지가 처리되기 전에는 승인하지 않는다. 모델이 지적하지 않은 오류까지 없음을 보장하지 않는다.

## 재현과 테스트

일반 회귀 테스트는 API 비용 없이 워크플로 잠금·스키마·선언 줄 포함·해시 무효화·부정확한 문서 거부·2회 상한·잘못된 Mermaid 인용·검증 전 완료 주장 노출 방지를 검사한다.

유료 문서 평가는 기본 cargo test에서는 실행하지 않는다. 명시적으로 다음을 실행한다.

```sh
MNEMOARC_LIVE_TEST=1 MNEMOARC_DOC_REPORT=/tmp/mnemoarc-document-report.json \
  cargo test --test live_documentation registered_source_documentation -- --ignored --nocapture
```

`MNEMOARC_LIVE_CONFIG`로 설정 파일을 지정할 수 있다. 등록된 llm_agent와 모델·토큰 예산을 사용하고 시간 상한은 최대 900초다. 임시 출력으로 생성해 원래 문서를 보호한다. 보고서에 생성 문서, 호출 기록, 첫 작성 시점, 사용량, 검토 상태, 원본 불변 여부를 저장한다. `MNEMOARC_DOC_MAX_INPUT`을 지정하면 누적 입력 상한도 검사한다. 토큰은 누적 사용량이지 고유 소스 크기나 청구 금액이 아니다. 비용과 정확성을 평가할 때 동일 조건 반복 실행 및 별도 소스 대조가 필요하다.
