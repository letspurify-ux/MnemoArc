# 프론트엔드 화면 전환·실행 요청 리뷰 — 2026-09-27

## 범위와 재현

`a8eae86`의 프론트엔드를 기준으로 화면 이동 중의 미전송 입력, 실행 요청 잠금, 상태 조회 교체, 설정 저장 실패 후 복원을 검토했다. 앞선 수정의 경계 조건을 지연 응답과 서버 상태 변경으로 재현했다.

수정 전에 브라우저 테스트 7개가 실패했다. 설정 화면 왕복·세션 전환에서 입력이 사라지고, 실행 응답 대기 중 화면을 다시 열거나 상태 조회를 교체하면 잠금이 풀렸다. 작업 방식과 도구 선택의 실패 처리도 최신 서버 값 대신 오래된 값을 복원했다.

## 발견한 문제와 수정

| 우선순위 | 문제 | 수정 |
| --- | --- | --- |
| 보통 | 채팅 초안과 요청 종류를 채팅 컴포넌트 안에 보관했다. 설정·프로젝트 화면을 열거나 다른 세션으로 이동하면 컴포넌트가 해제되면서 입력을 잃었다. | 세션 ID별 초안을 앱 메모리에 보관한다. 화면을 다시 열면 해당 세션의 입력과 선택한 요청 종류를 읽는다. 입력 변경은 채팅만 구독하므로 타이핑마다 전체 작업 공간을 다시 렌더링하지 않는다. |
| 높음 | 전송 잠금이 채팅 화면에만 있어 화면을 다시 열면 사라졌다. 상단 재개·기억 정리에도 공통 잠금이 없어 응답을 받기 전에 실행 요청을 겹쳐 보낼 수 있었다. | 앱에서 전송·재개·기억 정리를 같은 잠금으로 관리한다. 서버가 한 번에 하나의 작업을 실행하므로 다른 세션으로 이동한 경우에도 추가 실행을 막는다. 실패 후에는 잠금을 해제한다. |
| 보통 | 실행 이후 상태 조회 A를 기다리는 동안 기억 상세 조회 등이 조회 B를 시작하면 A를 취소했다. A의 취소를 기다림의 종료로 처리해, B가 아직 대기 중인데도 실행 버튼을 다시 활성화했다. | 각 조회가 취소 제어기와 완료 Promise를 함께 소유한다. 교체된 조회를 기다리던 작업은 새 조회의 완료까지 기다린다. 종료된 앱에서 늦은 콜백이 조회를 다시 시작하는 것도 막는다. |
| 보통 | 작업 방식·도구 저장이 실패하면 요청 전에 캡처한 선택을 복원했다. 그 사이 서버에서 변경한 값은 이미 받아도 화면에 다시 반영되지 않았다. | 저장 중에는 사용자가 고른 값을 표시하고, 저장 대기가 끝나면 최신 서버 선택으로 동기화한다. 오래된 클로저의 값으로 되돌리는 처리를 제거했다. |

## 초안의 수명과 비동기 응답

- 초안은 현재 브라우저 탭의 메모리에서 세션별로 유지한다. 브라우저 저장소나 서버에 미전송 메시지를 추가 저장하지 않는다.
- 전송 시 초안 객체를 기억한다. 성공 응답을 받았을 때 현재 초안이 같은 객체인 경우에만 지운다. 다른 화면을 다녀와 새로 입력했거나, 내용을 바꿨다가 같은 문자열로 되돌린 경우에도 후속 편집을 보존한다.
- 화면을 다시 연 뒤 도착한 성공 응답도 제출했던 초안을 정리한다. 실패한 요청의 입력은 남는다. 다른 세션의 초안에는 영향을 주지 않는다.
- 세션이 목록에서 제거되거나 앱이 종료되면 해당 초안을 정리한다. 삭제된 세션의 늦은 응답이 초안을 되살리지 않는다.
- 미전송 내용이 있으면 브라우저 이탈 확인에 포함한다. 사용자가 새로고침·탭 종료를 진행하면 메모리의 초안은 사라진다. 앱 내부의 화면 이동에서는 초안을 유지한다.

신규 브라우저 검사는 수정 전 실패한 7개 사례와, 화면을 다시 연 뒤의 성공·실패 응답 및 미전송 초안의 이탈 보호 4개를 다룬다. 처리되지 않은 JavaScript 오류도 검사한다. 기존 설정·프로젝트 저장, 대화 병합, 각주, Markdown·수식·Mermaid 스트리밍, 실행 취소·완료 검증, 문서 다운로드, 모바일 화면 검사를 함께 통과했다.
