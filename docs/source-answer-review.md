# 소스 답변 검토와 검색 계약

## 목적과 경계

탐색 도구의 정확성과 LLM 답변의 의미 정확성을 구분한다. 파일을 읽었다고 올바르게 설명했다는 뜻은 아니다. 이번 변경은 정규식 오용을 줄이는 명시적 검색 계약, 이미 전달된 근거를 이용한 1회 답변 검토, 코드로 가능한 인용 검사를 결합한다. 특정 평가 질문의 정답이나 함수 이름을 런타임에 넣지 않는다.

## 실행 흐름

1. `source_search`의 `queries` 배열로 최대 16개 문자열을 문자 그대로 OR 검색한다. `query`와 `queries`는 함께 쓸 수 없고 `queries`에는 `regex:true`를 적용할 수 없다. 기존 단일 query는 문자 검색이 기본이며 유효한 명시적 정규식 검색도 유지한다. 잘못된 정규식을 자동으로 문자 검색으로 바꾸지 않고 복구 방법과 함께 거부한다.
2. 새 사용자 요청 이후 지원되는 소스 파일 본문을 읽은 채팅 답변은 초안을 보류한다. 기존 문서 요약, 문서 쓰기·조사 검증 작업에는 이 경로를 적용하지 않는다. 사용자가 선택한 도구와 문서 작업 계약은 유지한다.
3. 동일 모델에 원래 질문, 사용자 제약, 초안, 현재 파일 해시와 일치하는 **이미 전달된** 코드만 담아 한 번 수정 요청한다. 검토 요청에는 도구가 없고, 모델이 도구 호출을 반환해도 실행하지 않는다. 외부 에이전트를 만드는 방식이 아니다.
4. 검토 요청 전체를 로컬 추정 8,000 입력 토큰 또는 설정상 입력 예산 중 작은 값으로 제한한다. 최근 근거를 우선하고 전체 발췌 단위로 담으며 빠진 근거는 표시한다. 초안·제약 자체가 이 한도를 넘으면 숨기거나 자르지 않고 중단한다. 기존 취소·시간·전체 토큰 예산·전송 재시도 규칙이 적용되며 공급자 사용량은 전체 사용량에 합산한다.
5. 명시적인 JSON `citations` 배열은 경로·줄 범위·현재 버전·완전히 전달된 줄인지 검사한다. 실제 본문 읽기와 완전한 검색 결과 한 줄을 인정한다. 검색 문맥, 잘린 검색 줄, 내용 없이 나온 구조 목차는 구현 근거로 인정하지 않는다. 검사 실패는 `partial`이며 자동 재검토를 반복하지 않는다.

검토 결과가 나오기 전 초안 텍스트는 스트리밍하지 않는다. 검토 중 UI에 진행 상태를 표시한다. 중단된 초안은 재개를 위해 세션에 유지하며, 새 사용자 작업은 검토 상태를 초기화하고 명시적 resume은 유지한다. 검토가 끝난 작업을 재개하더라도 명시적 JSON 인용 검사는 유지한다.

## 설정

`source_answer_review=true`가 기본값이다. 설정 화면의 **소스 답변 검토**에서 끌 수 있다. 한 번의 모델 요청 비용이 추가되므로 정확도가 중요하지 않은 경우 끌 수 있으며, 켠 상태가 무조건 더 빠르거나 더 싸다는 뜻은 아니다. 기존 서버 프로세스는 새 빌드로 재시작해야 변경이 적용된다.

## 한계

- 동일 모델의 수정은 의미 정확성의 증명이 아니다. 인용 위치가 존재하고 읽힌 범위여도 해당 주장과의 의미 관계는 모델이 판단한다.
- 정적 인용 검사는 명시적인 JSON citations에 한정한다. 자연어·Markdown 답변은 모델 검토 대상이지만 같은 수준의 정적 인용 검사를 주장하지 않는다.
- 어떤 인용이 반드시 필요한지, 임의의 자연어 필드가 서로 모순되는지는 코드가 일반적으로 판정하지 않는다. 사실별 누락 검사는 준비된 평가 사례의 오라클이 담당한다.
- 이 경로는 현재 Tree-sitter에서 지원하는 확장자의 본문 읽기에 반응한다. 구조 목차만 보는 위치 질문에는 추가 검토를 요구하지 않는다.
- 내용 변경이 발견되면 검토 근거에서 제외한다. 검토 모델에는 추가 탐색 권한이 없으므로 부족한 근거는 한계로 표현해야 한다.

## 평가

기존 취소 의미·검색 복구·Java 오버로드 사례에 별도의 Rust 조기 반환 순서 사례를 추가했다. 의미 사례의 “응답”은 스트림 헤더와 구분되는 최종 완료 응답 본문으로 명확히 했고, Java 호출 대상 필드는 호출 화살표 없이 대상 이름만 요구한다고 명확히 했다. 기대 정답과 근거 검사는 유지한다. 질문 계약이 명확해졌으므로 이전 결과와 차이를 모두 런타임 개선 효과로 돌리지 않는다.

보고서는 검토 전 초안의 정답 오류, 검토 후 정답·인용·실제 읽기 오류, 도구 오류, 전체 토큰, 검토 토큰, 시간을 기록한다. 호출 수·전체 입력 토큰의 기존 상한은 유지하며 검토 비용도 포함한다. `MNEMOARC_NAV_REVIEW=off`로 같은 평가에서 검토만 끈 비교를 할 수 있다. 전체 평가가 통과하지 않으면 실패를 그대로 보고한다.

## 실제 모델 관측 (2026-09-20)

저장된 `z-ai/glm-5.3-flash`, 새 세션 기본 도구로 네 사례를 각각 두 번 실행했다. 다음 토큰 수는 검토 요청을 포함한 공급자 누적 입력 사용량이다.

| 사례 | 호출 수 | 전체 입력 토큰 | 그중 검토 입력 | 결과 |
|---|---:|---:|---:|---|
| 취소 의미 1 | 5 | 41,123 | 5,388 | 전체 통과 |
| 취소 의미 2 | 9 | 92,405 | 5,718 | 정답·인용 통과, 호출·토큰 상한 초과 |
| 검색 복구 1 | 2 | 28,498 | 1,481 | 전체 통과 |
| 검색 복구 2 | 2 | 28,962 | 1,697 | 전체 통과 |
| Java 1 | 6 | 31,328 | 893 | 전체 통과 |
| Java 2 | 6 | 34,831 | 990 | 전체 통과 |
| Rust 조기 반환 1 | 2 | 21,570 | 541 | 전체 통과 |
| Rust 조기 반환 2 | 2 | 20,816 | 651 | 전체 통과 |

- 준비된 정답·인용·실제 전달 근거는 8/8, 기존 효율 상한까지 포함하면 7/8 통과했다. 따라서 전체 live 테스트 명령의 종료 상태는 **실패**다. 호출 9회/입력 92,405 토큰인 실행을 통과로 처리하지 않았다.
- 취소 의미 두 번째 실행의 초안은 `always_new_abort_error`를 잘못 답했으나 검토 후 올바르게 수정됐다. 다른 일곱 초안은 검사 대상 정답 필드가 이미 맞았다. 이 비교는 동일 실행의 검토 전후이며, 자유 서술 전체의 정확도까지 증명하지 않는다.
- 검토 입력은 합계 17,359 토큰, 검토 출력은 합계 2,886 토큰이었다. 검토를 켠 것이 무조건 비용을 줄인다는 주장은 하지 않는다.
- 문자 OR 검색이 실제로 사용됐고 최종 8회에 도구 오류는 없었다. 초기 개발 단계의 검색 인용 인정 누락과 실패 실행은 `/tmp/mnemoarc-navigation-reviewed-20260920.json`에 남겼다.
- 이후 `file_read` 새 범위/커서와 `source_search` query/queries의 상호 배타 조건을 모델용 JSON Schema에도 명시했다. 마지막 스키마 상태에서 Rust 사례를 추가 1회 실행해 2회 도구 호출/22,047 입력 토큰으로 전체 통과했다. 이 추가 실행은 위 8회 통계에 섞지 않았다. 잘린 소스 초안을 숨기고 동일 검토 경로에서 완성하는 예외 처리는 별도 Rust 테스트로 확인했다.

최종 일반 검증은 Rust 142개, 프런트엔드 4개 통과다. 유료 테스트 3개는 일반 실행에서 제외된다. Clippy(경고 오류 처리), 포맷 검사, 프런트엔드 빌드, Rust 릴리스 빌드도 통과했다. 보호 범위는 검토 전 초안 미노출, 1회 검토, 잘린 초안 처리, 도구 실행 금지, 예산 초과 시 초안 유지, 새 요청·재개 구분, 파일 변경, 검색 줄의 완전성, 인용 범위다.

최종 원시 보고서는 `/tmp/mnemoarc-navigation-designed-final-20260920.json`, 마지막 스키마 확인은 `/tmp/mnemoarc-navigation-schema-final-20260920.json`이다. 표본이 작고 질문 계약을 명확히 한 부분도 있어 일반적인 정확도나 속도 개선율로 확대 해석하지 않는다. 남은 개선 대상은 복잡한 다중 파일 탐색의 호출·토큰 편차다.
