# 문서 작성 세션의 partial 종료 원인과 수정

2026-09-20, 세션 `77ecaa0c-9536-430d-9afa-47cf4779b200`의 읽기 전용 기록을 확인했다. 결과 파일은 생성됐지만 `complete`가 아닌 `partial`로 종료됐다. 조사 항목 4개는 verified였으나 최종 문서 검토는 두 번 모두 지적 사항을 반환했고 approved_hash가 없었다.

## 실제 오류와 수정

| 증상 | 원인 | 수정 |
| --- | --- | --- |
| `No such file or directory` | 출력 파일명을 상대경로로 전달해 프로젝트 안의 다른 경로를 조회. canonicalize의 OS 오류에 경로 문맥이 없었음 | `file_not_found` 등으로 분류하고 실제 조회 경로·루트·설정된 출력 경로·path 생략 방법 제공. 읽기 시 파일 소실도 경로 포함 |
| `cursor_arguments_conflict` | cursor와 새 path/start_line/max_lines를 동시에 전달 | 입력 계약 오류로 정확하게 분류해 인자 수정 안내. 기존 충돌 거부는 유지 |
| `item_must_be_written_before_verification` | 문서는 생성됐지만 등록된 조사 항목이 uninvestigated 상태 | 성공한 문서 저장 뒤, 등록된 유일한 섹션에 실제 본문이 있으면 written으로 동기화. 자동 verified 전환은 하지 않음. 남은 상태 위반에는 항목 ID·현재 상태·선행 동작을 안내 |
| 검증 메모와 실제 출처 파일 불일치 | 예: 웹 설명에 main.rs 출처 ID를 제출해도 기존 검증은 출처 존재·신선도만 검사 | 섹션의 각 인용 파일·행 범위를 제출된 출처 범위의 합집합이 덮는지 확인. 잘못된 출처는 `source_coverage_missing`으로 거부 |
| 최종 검토의 반복적인 근거 부족 | 검토 요청 24,000 토큰 상한에서 뒤쪽 소스 청크를 버렸음. 모델이 파일을 다시 읽어도 검토 입력은 같은 알고리즘으로 다시 누락됨 | 순차 페이지로 근거 전체 전달. 모든 페이지가 끝나기 전에는 승인하거나 내용 검토 시도 횟수를 소모하지 않음. 페이지별 지적을 모아 최종 판단. 문서·소스 버전 변경 시 이전 페이지 판단을 버리고 다시 시작 |
| 백오프 상한 누락 | 생성 문서가 `attempt.min(5)`를 생략 | 문서 설명을 `500ms × 2^min(attempt, 5)`, 최대 16초로 교정. 검토 지시에도 수치 상한 비교 명시 |

검토는 요청당 기존 입력 상한, 최대 32페이지, 기존 전체 실행 시간·토큰 상한을 따른다. 문서 자체나 단일 근거 청크가 요청 예산에 들어가지 않으면 명시적으로 중단하며 누락한 채 승인하지 않는다. 인용되지 않은 helper까지 모두 검토하는 증명은 아니며, 의미적 정확성 판단은 여전히 모델 검토의 한계를 가진다.

## 검증

- 이후 소스 버전 변경 회귀 테스트를 추가한 문서 검토 테스트 모음 12개 통과.
- Clippy 경고 검사, 포맷 검사, diff 공백 검사 통과.
- 실제 실패 세션의 문서와 설정으로 오프라인 검토 입력을 생성: 3페이지, 페이지별 22,369 / 23,337 / 14,437 추정 토큰, 중복 제외 1,846행의 대상 근거 전달. 이전에 빠졌던 agent.rs:493, web.rs:503, tools.rs:1982가 포함되는 것을 확인.
- 오프라인 검증은 페이지 전달을 시험하기 위한 모의 판정을 사용했다. 실제 LLM의 문서 내용 승인이나 기존 세션 상태 변경을 의미하지 않는다.

## 재시작 후 검증 (2026-09-20)

상태와 산출물을 `.mnemoarc/backups/20260920-204200`에 백업한 뒤 서버를 다시 빌드하고 재시작했다. 설정의 `review_limit=10`을 확인했다. 기존 세션 상태를 complete로 강제 변경하지 않았다.

새 세션 `2b268a08-f12f-46a0-b370-059708b8791b`의 자동 작성 실행은 반복 조사·기억 정리로 최종 검토에 도달하지 못해 취소했다. 이는 검토 페이지 누락과 별개의 모델 작업 진행 문제다. 따라서 자동 작성부터 최종 종료까지의 전체 흐름이 통과했다고 주장하지 않는다.

대신 `examples/verify_existing_document.rs`로 실제 설정의 모델을 호출하여 운영 코드의 `document_review::request/finish/approved` 경로를 검증했다. 이는 모의 판정이 아니며, 앱 세션의 조사 상태나 완료 상태를 변경하지 않는 별도 문서 검토다. 첫 실제 검토는 3페이지 전체를 처리하고 지적을 반환했으며, 문서의 길이 복구 한도·검토 재시도·API 표 범위·Mermaid 흐름 등을 현재 코드와 대조해 수정했다.

- 최신 전체 테스트: Rust 176개, JavaScript 7개 통과; 기존 환경 의존 테스트 5개 제외.
- Mermaid 4개를 Chromium에서 실제 Mermaid 파서로 검사: 모두 통과.
- 문서의 명시적 파일·행 범위 99개: 존재 및 범위 확인.
- 실제 검토에서 마지막 페이지가 앞선 페이지 근거를 누락으로 오인하는 경우도 재현됐다. 각 요청에 전체 근거 목록(파일·행 범위·이전 페이지 검토 여부)과 독립 요청이라는 범위를 명시하도록 보완했으며, 페이지별 목록 상태와 24,000토큰 상한을 함께 검사하는 회귀 테스트를 추가했다.
- 최종 실제 모델 승인 결과는 `.mnemoarc/live-final-review.json`에 보관한다. 승인 해시는 현재 문서 해시와 일치해야 하며, 이것만으로 자동 작성 세션 완료를 뜻하지 않는다.


최종 실제 모델 검토는 4페이지 모두 `issues=[]`로 완료됐으며 `approved=true`다. 입력 토큰은 페이지별 17,560 / 16,449 / 17,833 / 15,416, 합계 67,258이고 출력은 합계 6,425다. 승인 해시와 현재 문서, 검토한 모든 소스 파일의 해시 일치를 재확인했다. 문서 해시: `e5c792ddbccd03781292c91df79472fd91910b39643007e934493a993b7d60f4`. 검토 근거 전체를 처리한 뒤 `pending=false`, `evidence_omitted=false`인 것도 확인했다.

이는 최종 문서 내용 검토의 통과다. 취소한 자동 작성 세션이 정상 complete로 종료됐다는 뜻은 아니다. 서버에는 근거 목록 보완을 포함한 최신 코드를 재빌드·재시작했고, 공개 설정 API에서 `review_limit=10`을 확인했다. 전체 테스트 이후 근거 목록 보완에 대해서 문서 검토 테스트 12개, Clippy와 포맷 검사를 다시 통과했다.
