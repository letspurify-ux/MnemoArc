# 문서 조사·작성 도구 개선

## 제공 기능

`source-docs` 선택 시 기존 도구와 함께 다음 기능을 사용할 수 있다.

| 도구 | 사용법과 보장 |
|---|---|
| `file_read` | 전체 줄 수·파일 해시와 `content.line_start`, `content.line_offsets`를 제공한다. `line_offsets`는 반환 텍스트 내 Unicode 문자 위치이며 각 줄의 시작을 가리킨다. 본문을 잘라도 이어 읽기 위치와 줄 지도를 함께 갱신한다. `first_line_complete`·`last_line_complete`가 거짓인 경계 줄은 인용 검증 범위에 포함되지 않으므로 커서로 범위를 끝까지 읽어야 한다. 파일 끝을 지난 읽기는 근거 ID 없이 빈 결과를 반환하고, 빈 근거는 검증에 사용할 수 없다. |
| `document_inspect` | 인자 없이 출력 파일의 해시·실제 줄 수·목차를 조회한다. 목차에는 제목 수준 `level`과 상위 제목을 줄바꿈으로 연결한 `section_path`가 포함된다. 같은 제목이 다른 부모 아래에 있을 때 이 경로를 `section`에 복사해 정확한 섹션을 읽는다. `offset` 또는 `coverage_offset`으로 이어 읽을 때는 첫 페이지의 `hash`를 `expected_hash`로 전달해야 하며, 중간에 파일이 바뀌면 거부한다. 첫 저장 전에는 `exists:false`와 함께 `document_edit action=create`(또는 `document_edit_batch`)로 먼저 만들라는 `guidance`를 돌려준다. `path`로 설정된 출력(그 경로, 프로젝트 루트 기준 상대 경로, 프로젝트에 같은 이름이 없는 파일 이름)을 지정해도 인자 없이 부른 것과 같다(라이브 실행에서 출력 경로를 직접 지정한 첫 호출이 `file_not_found`로 실패했다). 출력 문서가 아닌 파일을 `path`로 조회하면 결과에 `configured_output: false`와 "편집·점검 도구는 설정된 출력 문서만 다룬다"는 안내를 붙인다(프로젝트의 기존 사용 매뉴얼을 자기 출력으로 착각해, 출력에 이미 없는 링크 문장을 고치려다 마감 요청을 모두 쓴 실행이 있었다). |
| `document_edit`의 `section` | `section`, `text`, `expected_hash`, `expected_section_hash`를 받아 해당 제목부터 다음 동급/상위 제목 전까지 교체한다. 자손 섹션도 교체 범위에 포함되므로 작은 수정에는 부분 텍스트 편집을 사용한다. 원래 제목을 유지해야 한다. 새 본문 뒤에 같은 수준의 제목이 이어지고 문서에 아직 없는 제목이면 그 섹션 뒤에 새 섹션으로 넣고 결과의 `inserted_sections`에 적는다(섹션 N을 고치면서 N+1을 같은 본문에 이어 쓴 호출이 세 번 거절돼 수천 토큰 본문을 다시 보낸 실행이 있었다). 상위 수준 제목, 이 섹션의 하위 번호(1.3 뒤의 1.3.1)를 단 같은 수준 제목, 문서에 이미 있는 제목은 지금처럼 거절한다. 새 본문의 끝 공백·빈 줄·줄바꿈 형식은 보존하며, 다음 제목이 있는데 새 본문에 끝 개행이 없을 때만 원래 섹션의 줄바꿈을 붙인다. 코드 펜스 안의 제목은 무시하며 모호한 경로와 외부 편집 충돌을 거부한다. |
| `document_edit`의 섹션 삽입 | `insert_before`·`insert_after`는 `section`으로 지정한 동급 섹션 앞뒤에 새 섹션을 넣는다. `insert_first_child`·`insert_last_child`는 부모 `section` 안에 한 단계 깊은 새 섹션을 넣으며, 자식이 없는 부모에도 쓸 수 있다. 목차의 `section_path`를 복사하면 다른 부모 아래 같은 제목을 구분한다. `expected_hash`로 문서 변경을 검사하고 새 섹션 하나만 허용한다. 문서의 제목이 빈 줄로 구분돼 있으면 새 섹션 앞뒤에도 빈 줄을 하나씩 두고, 빈 줄 없이 붙여 쓴 문서는 그대로 붙여 넣는다. 아직 첫 제목(대개 문서 제목)밖에 없으면 그 제목 다음 줄이 빈 줄인지로 판단한다. `append`로 붙이는 제목도 같은 규칙을 따른다(`# 제목` 뒤에 빈 줄을 둔 매뉴얼에 첫 `## …`를 붙였더니 앞 문단에 붙어 버린 라이브 실행). 섹션 끝의 빈 줄은 레이아웃으로 보아 앞 섹션의 검증 상태와 검토 변경 섹션 판단에 영향을 주지 않는다. 네 동작 모두 `document_edit_batch`에서도 사용할 수 있다. |
| `document_edit`의 부분 텍스트 편집 | `replace_text`는 고유한 `old_text`를 `text`로 교체하고, `delete_text`는 `old_text`만 받아 삭제한다. `insert_before_text`·`insert_after_text`는 고유한 `old_text` 앞뒤에 `text`를 원문 그대로 넣는다. 선택적 `section`에 `section_path`를 주면 그 섹션과 자손 안에서만 `old_text`를 찾으므로 다른 부모에 같은 문장이 있어도 수정할 수 있다. 이때 선택적 `expected_section_hash`를 함께 주면 그 섹션이 읽은 버전 그대로일 때만 적용한다(다르면 `section_revision_conflict`). `section` 없이 해시만 오면 확인할 섹션이 없다고 거절한다. 라이브 모델이 `replace_text`에 읽어 둔 `section_hash`를 붙였다가, 이 해시는 `action=section`만 받는다며 거절됐다. 모두 `expected_hash`를 확인하며, 대상이 없거나 범위 안에서 여러 번 나타나면 변경하지 않는다. `old_text`가 앞뒤 공백·줄바꿈만 다르면 잘라낸 구절로 찾고, 교체·삭제에서는 `text`에 같이 붙은 앞뒤 공백도 떼어 낸다. 같은 동작을 `document_edit_batch`에서도 순서대로 사용할 수 있다. `document_edit`·`document_edit_batch`의 `text`·`old_text`에서 줄바꿈(LF) 없이 홀로 있는 캐리지 리턴(`\r`)은 줄바꿈으로 바꾼다(CRLF 쌍은 그대로). 라이브 모델이 편집마다 19~40개의 `\r`을 줄바꿈 대신 보냈고, 저장된 문서의 깨진 글자를 문서 리뷰가 세 번 지적했다. 삽입하는 `text`가 `old_text`(20자 이상)를 정확히 한 번 담고 있으면 덧붙이지 않고 교체로 처리한다. `old_text`가 제목 한 줄이면 길이와 관계없이, `text`의 한 줄이 그 제목과 같을 때 같은 규칙을 적용한다. 라이브 모델이 15자짜리 `## 2. 새 세션 시작하기` 앞에 섹션을 넣으려고 그 제목 뒤에 "새 섹션 + 같은 제목"을 `insert_after_text`로 넣었는데, 20자 기준에 걸리지 않아 제목이 두 번 남았다. 제목 줄 바로 뒤에 다른 제목으로 시작하는 `text`를 넣는 `insert_after_text`는, 그 섹션의 본문을 새 제목 아래로 빼앗아 원래 제목을 빈 섹션으로 만들므로 거절하고 `insert_before`·`insert_after`·`insert_first_child`를 안내한다. |
| `document_audit` | `path.ext:10-20` 및 Markdown 링크의 `path.ext#L10-L20` 출처를 검사한다. 일반 코드 펜스 안의 예시는 인용 검사에서 제외하되 Mermaid의 소스 인용은 검사한다. 파일 존재·허용 경로·줄 범위, 이번 세션에서 현재 파일 버전의 완전한 줄로 전달되지 않은 인용 범위(`unread_citation`), Markdown 표·코드 펜스·Mermaid 문법을 한 번에 점검한다. 인용이 전혀 없는 문서의 `no_machine_readable_citations`는 구조 검사를 막지 않지만, 최종 답변은 인용이 생길 때까지 거절된다고 안내한다(저장 결과의 `citation_check.citations_required`에도 같은 안내). 링크의 `#L` 대상은 Markdown 링크처럼 출력 문서가 있는 폴더를 기준으로 해석한다. 해석되지 않으면 그 폴더, 대상이 실제로 가리킨 경로, 대신 쓸 프로젝트 기준 `경로:줄` 인용(대상에서 앞의 `../`를 빼거나 경로에 적힌 프로젝트 루트 뒤를 읽어 프로젝트 파일을 찾으면 그 파일)을 오류에 적는다. 이전에는 "상대 경로는 project.root 기준"이라는 일반 경로 오류를 그대로 보여 줘, 프로젝트 밖 출력에 docs/ 문서의 `../frontend/…#L` 링크를 따라 쓴 라이브 실행이 링크 대상을 여섯 가지로 바꾸며 19회를 요청하고 검사기가 틀렸다고 기록했다. 오류 목록은 페이지 조회 가능하며 `format_check`에 형식 검사 범위와 경고를 반환한다. 감사 대상은 항상 설정된 출력 문서이므로, `path`에 그 문서(경로, 심볼릭 링크를 따른 실제 경로, 프로젝트에 같은 이름이 없는 파일 이름) 또는 빈 값이 오면 빼고 감사한다. 다른 경로는 계속 알 수 없는 인자로 거절한다(출력 경로를 붙여 보낸 라이브 실행이 한 번 거절됐다). |
| 읽지 않은 인용 | 런타임이 전달된 근거 레지스트리에서 자동으로 계산한다. 매 저장의 `citation_check.unread_citations`와 `document_audit`의 `unread_citation` 항목이 파일별로 합친 범위와 `file_read` 호출 방법을 알려 주며, 하나라도 남으면 최종 완료를 거부한다. 소스가 바뀌면 이전 읽기는 무효다. 120줄 이상 범위에는 선언 줄만 인용하라는 안내를 덧붙인다. 조사 항목을 등록·검증하는 호출은 없다. |
| 테스트 코드 인용 안내 | 소스 기반 문서 작업에서 인용이 테스트 코드를 가리키면 저장 결과와 `document_audit`에 `test_code_check`(건수, 처음 12개의 문서 줄·인용, 안내)를 붙이고, 문서 검토 요청에는 `test_code_citations`로 넘긴다. 테스트 코드는 테스트 폴더(`tests`, `test`, `__tests__`), 테스트 파일 이름(`.test.`, `.spec.`, `_test`, `_tests`, `_spec`, `test_`, `tests`, `…Test`), Rust의 `#[cfg(test)]` 모듈(rustfmt 형식에서 그 `mod` 줄의 들여쓰기로 닫히는 범위)이다. 테스트는 동작을 확인하는 방법이지 제품이 동작하는 방식이 아니므로, 제품 코드를 인용하거나 본문에 테스트 설명임을 밝히라고 안내한다. 안내이므로 최종 답변을 막지 않는다. 라이브 문서가 테스트의 반복문을 "리뷰가 반복되는 방식"의 근거로 인용했는데 문서 검토가 승인했다. |
| 독자 수준 점검 | 소스 기반 문서 작업에서 프로젝트 독자가 개발자가 아니면 저장 결과와 `document_audit`에 `audience_check`(건수, 처음 12개 항목의 줄·종류·텍스트, 안내)를 붙인다. 독자 문구에 "개발", "developer", "engineer", "maintainer" 같은 말이 있으면 개발자로 보고 점검하지 않는다. 대상은 Mermaid가 아닌 코드 블록, 식별자나 코드로 읽히는 인라인 코드(`::`·`=>`·괄호·`=` 등이 든 코드, 밑줄 이름, camelCase, 대문자 상수), 본문의 `::` 경로, 그리고 Mermaid 다이어그램에서 독자가 보는 라벨(대괄호·괄호·중괄호 안 노드 라벨, 파이프 사이 연결선 라벨, 따옴표 안 글자, 시퀀스 메시지)에 든 같은 식별자(`diagram_label`)다. 노드 ID·다이어그램 종류·화살표·`<br/>`는 문법이라 보지 않는다. 최종 라이브 문서의 흐름도 노드에 도구 이름(`source_search`, `document_edit` 등)이 남았는데, 이전에는 Mermaid 블록을 통째로 건너뛰었다. 인용(`경로:줄`), 파일 이름·경로, 한글 등 화면 문구, 키 이름(`Shift+Enter`)은 제외한다. 안내이므로 `structural_ok`와 최종 답변을 막지 않는다. 같은 항목을 문서 검토 요청의 `audience_flags`로도 넘긴다. 일반 사용자용 라이브 문서가 `documentation::execute`, `resolve_heading`, 오류 코드를 그대로 썼는데 두 검토가 통과시켰다. |
| 반복 점검 생략 | `document_inspect`·`document_audit` 결과가 활성 문맥에 이미 그대로 있으면(문서·근거가 바뀌지 않음) 본문 대신 `unchanged: true`와 안내만 돌려준다. 새 정보가 없으므로 진척으로 세지 않는다. |
| 할 일 목록 | 소스 문서의 계획은 요청 전체를 덮도록 섹션·영역마다 짧은 항목(섹션 이름과 주요 출처 파일을 담은 한 문장)을 두고, 마지막 검증 항목을 둔다. | 탐색 도구 유지 | 진척 없는 라운드가 쌓여 집중 복구에 들어가도, 저장된 문서가 없으면 `file_list`·`source_search`·`symbol_search`·`symbol_relations`·`code_outline`을 숨기지 않는다. 작성 안내는 그대로 나간다. 문서를 쓰기 전에 탐색 도구를 숨기면 아직 소스를 찾지 못한 모델이 경로를 추측하게 된다. |
| `document_edit` `append` | 기존 문서가 줄바꿈 없이 끝나고 붙일 내용이 `#` 제목으로 시작하면 줄바꿈을 넣어 제목이 앞 문장에 붙지 않게 한다. 그 밖의 이어 쓰기는 그대로 붙인다. |
| 문서 해시 누락 | 빈 `expected_hash`(`""`, 모든 인자를 채워 보내는 모델의 자리표시 값)는 빠뜨린 것으로 본다. 구절 기준 편집은 그대로 적용되고 나머지는 아래 처리를 따른다. 일괄 수정의 편집 항목에 든 빈 값도 무시해, 최상위로 올려 "비어 있으면 안 된다"로 거절하거나 실제 최상위 해시와 충돌로 보지 않는다(`replace_text`에 빈 해시를 보낸 라이브 실행이 거절됐다). `append`·`section`·섹션 삽입과 `document_edit_batch`가 `expected_hash`를 빠뜨려도, 문서가 모델이 마지막으로 저장한 내용 그대로면 그 저장 결과의 해시를 채운다. 그 밖의 경우에는 편집을 메모리에서 현재 문서에 적용해 보고, 해시 누락과 함께 다른 문제(제목 수준, 없는 섹션, 일괄 수정의 실패 항목 전부)를 한 번에 알린 뒤 아무것도 쓰지 않는다. 다른 인자 오류에도 해시 누락을 덧붙인다. 섹션 삽입의 제목 수준이 틀리면 그 수준에 맞는 동작(형제면 `insert_after`/`insert_before`, 자식이면 `insert_last_child`/`insert_first_child`)을 안내한다. |
| `symbol_search` | Tree-sitter로 Rust·JS/TS·Python·Java·C# 선언을 검색한다. `path`/`path_glob`, 이름·종류·소속 필터와 페이지 조회를 지원하며, `symbol_read`와 공유하는 심볼 ID를 반환한다. 선언 발췌는 탐색용이다. |
| `symbol_relations` | 검색 결과의 `path`·`symbol_id`로 호출 대상·호출자·참조 위치를 조회한다. 지역 선언·import·소속을 고려하고 후보·모호함·미해결 사유를 반환한다. 원문 읽기와 의미 검증은 별도로 수행한다. |

일괄 검증은 관련 원문과 실제 문서를 비교한 뒤 호출해야 한다. 단순히 읽은 항목을 자동으로 검증 처리하지 않는다. 기존 ID를 지정한 `upsert`에서 생략한 제목·출처·기억 참조·섹션은 기존 값을 유지하며 같은 제목의 중복 항목 생성을 거부한다. 신규 항목은 제목이 필수이며, 존재하지 않는 ID에 제목 없이 수정 요청하면 오류를 반환한다. 기존 항목을 수정하면 이전 검증 상태는 무효화된다.

구현 범위와 사용법은 [Tree-sitter 심볼 검색과 호출·참조 추적](syntax-navigation.md)에 정리했다.

## Markdown·Mermaid 형식 검사

`source_document` 작업에서 `document_edit`와 `document_edit_batch`는 저장 직후 인용 경로·줄 범위를 검사한 `citation_check`와 형식 검사 결과인 `format_check`를 함께 반환한다. 오류가 있는 초안도 저장되므로 다음 편집에서 고칠 수 있다. `document_audit`는 인용과 형식 검사를 다시 실행해 형식 오류를 출처·조사 오류와 함께 `issues`에 넣는다. 실행부의 최종 완료 검사도 이 결과를 사용하므로 형식 오류가 남으면 구조 검사에 통과하지 못한다. 일반 `answer` 작업의 편집 결과는 기존처럼 저장 정보만 반환한다.

Markdown은 `comrak`의 GFM AST로 실제 표와 코드 펜스의 범위를 찾는다. 표는 원문 행의 열 수를 머리글과 비교한다. GFM이 부족한 셀을 빈칸으로 채우거나 넘치는 셀을 버려도 `markdown_table_columns`로 알린다. 머리글과 구분 행의 열 수 불일치, 잘못된 구분 행, 닫히지 않은 코드 펜스도 검사한다. 빈 셀과 이스케이프한 `\|`는 허용하며 목록·인용 안의 표와 펜스도 검사한다. 일반 코드 예시와 HTML 주석 안의 내용은 문서 문법으로 검사하지 않는다.

Mermaid는 AST의 `mermaid` 코드 펜스 본문을 `merman-core`의 `Engine::parse_diagram_sync(..., ParseOptions::strict())`에 전달한다. 흐름도·시퀀스·클래스·상태·ER 등 지원 문법의 파서 오류를 `mermaid_syntax_error`로 반환한다. `line`은 문서의 여는 펜스 줄이며 `diagram_start_line`과 `end_line`, 파서 메시지를 함께 제공한다. 메시지 안의 위치는 다이어그램 내부 위치이므로 문서의 정확한 오류 줄과 혼동하지 않는다. Rust 파서의 기준은 Mermaid 11.12.3이며 현재 UI의 Mermaid 11.17.2와 완전히 같지는 않다. Mermaid.js가 무시할 수 있는 잘못된 설정 지시문은 오류 대신 미검사 경고로 반환한다.

표의 수식·직렬화된 chart/Mermaid 셀, Mermaid의 직렬화 개행·수식 라벨처럼 UI가 추가 변환하는 문법은 경고와 함께 미검사로 표시한다. Mermaid 검사는 블록당 64 KiB, 문서당 128개 블록으로 제한하며 초과하거나 지원하지 않는 블록도 경고로 남긴다. `checks_complete`는 이 검사 범위에 미검사 경고가 없는지를 나타낸다. 경고는 구조 완료를 막지 않으며 승인이나 렌더링 성공을 뜻하지 않는다. 검사 개수·미검사 개수·전체 오류/경고 개수를 보고하고 저장 응답에서는 오류와 경고를 각각 최대 8개 미리 보여 준다. `document_audit`로 전체 오류를 페이지 조회할 수 있다.

이 검사는 외부 프로세스·Node.js·브라우저 없이 Rust에서 실행한다. 문서 내용의 정확성, CSS 배치, 글자 겹침·잘림, 실제 SVG 렌더링은 검증하지 않으므로 `semantic_verified`와 `ui_render_verified`는 항상 `false`다.

## 일반 프로젝트 파일 편집

`file_list`의 `path_glob`과 `source_search`의 `query`로 파일과 내용을 찾고, `file_read`로 본문과 해시를 확인한다. 신규 세션에서는 다음 편집 도구가 기본 활성화된다. 설정된 Markdown 출력 파일은 기존 `document_edit`와 `document_edit_batch`를 사용한다.

| 도구 | 기능 |
|---|---|
| `file_edit` | `path`, `expected_hash`, `old_text`, `new_text`로 정확한 문자열을 교체한다. 한 번만 일치해야 하며 여러 곳을 모두 바꾸려면 `replace_all: true`를 명시한다. |
| `file_write` | `path`, `content`로 새 UTF-8 파일을 만든다. 기존 파일을 전체 교체할 때는 `expected_hash`가 필수다. |
| `file_patch` | `operations` 배열에 최대 32개의 `add`, `update`, `replace`, `move`, `delete` 작업을 순서대로 넣는다. 기존 파일을 처음 수정할 때 `expected_hash`가 필요하며 같은 패치의 후속 작업에서는 생략할 수 있다. 모든 작업을 먼저 검증한 뒤 저장한다. |

모든 경로는 프로젝트 루트 기준 상대 경로다. 제외 경로, 심볼릭 링크, 프로젝트 외부 경로, 바이너리 파일, 16MiB 초과 파일은 수정할 수 없다. 다중 파일 패치의 원본·결과 텍스트 합계는 128MiB로 제한한다. 파일 시스템 오류나 취소가 발생하면 완료된 변경을 되돌리려고 시도하고 복구 오류를 반환한다. 파일 시스템 수준의 다중 파일 트랜잭션을 보장하지는 않는다.

## 순서 있는 할 일 목록

여러 단계가 필요한 작업은 `task_plan`으로 관리한다. 진행 화면에도 같은 목록을 표시하며, 별도의 현재/다음 작업 문구를 작성하지 않는다. 첫 미완료 항목이 현재 작업이고, 완료 후에는 다음 미완료 항목으로 자동 이동한다. 항목은 작은 결과 단위로 나눌 수 있다. 문서 조사와 섹션 저장을 나눴다면 필요한 근거를 확인한 뒤 저장으로 이어가며, 근거 수집만 반복하지 않는다.

- 미완료 최대 **100개**, 완료 기록 최근 **5개**: 목록은 최대 105개를 유지한다. 누적 완료 수는 별도로 보존한다. 항목 설명과 완료 결과·변경 사유는 500자까지다. 상태에는 첫 미완료 항목 최대 6개만 예산에 맞춰 싣고, 전체 목록은 세션과 화면에 유지한다.
- `list`로 현재 목록·버전을 조회한다. 기본 10개, 최대 20개씩 보여주며 `next_offset`을 다음 호출의 `offset`으로 전달해 이어 본다. `apply`에는 `expected_revision`과 최대 16개 연산을 전달한다. ID는 생성 후 순서가 바뀌어도 유지한다.
- `operations`의 표준 형식은 작업 객체의 JSON 배열이다. 모델이 이를 JSON 문자열로 감싸거나 단일 작업 객체·JSON 문자열 항목 배열로 보내도 의미가 명확하면 정규화한다. 잘린 JSON, ID별 작업 맵처럼 순서가 모호한 형식은 추측해 실행하지 않고 `applied: false`, 잘못된 위치·입력 타입·올바른 예시를 반환한다. 정규화된 호출도 버전·순서·문자 수·개수 제한을 그대로 검사한다.
- `insert`는 `texts`를 추가한다. `before`에 미완료 ID를 주면 해당 항목 앞에 선행 작업을 끼워 넣고, 생략하면 끝에 추가한다. 기존 항목의 순서 변경은 `move`, 설명 수정은 `update`다.
- `split`은 진행 중 또는 뒤에 있는 미완료 항목 하나를 실행 순서대로 2개 이상의 작은 항목으로 나눈다. 첫 항목은 원래 ID를 유지하고 나머지에 새 ID를 붙인다. 완료 항목과 원래 설명을 그대로 반복한 항목은 분할할 수 없으며, 분할한 항목들이 원래 목표를 함께 충족해야 한다. 100개 한도 초과·중복·잘못된 설명이면 전체 묶음을 적용하지 않는다.
- `complete`는 현재 항목에만 적용하며 실제 결과인 `result`를 기록한다. 불필요 항목 삭제(`remove`)와 완료 항목 재개(`reopen`)에는 `reason`이 필요하다. 재개한 항목은 현재 작업 앞으로 이동한다.
- 한도 초과·오래된 버전·잘못된 ID·순서 위반은 기존 목록을 보존하고 `applied: false`와 수정 방법을 반환한다. 실행 실패로 세지 않으며, 현재 작업을 완료하거나 항목을 합치고 불필요한 항목을 제거해 계속 진행한다. 완료와 후속 항목 삽입을 한 번에 처리할 수 있다. 묶음 중 하나라도 실패하면 전체 목록을 변경하지 않는다.
- 목록 수정·기억 저장·체크포인트는 실제 진행으로 세지 않는다. 문서/파일 변경이나 새 검증이 없으면 회복 안내가 유지된다. 미완료 목록을 남긴 최종 답변은 현재 항목 실행으로 돌리며 문서 검증 재시도 한도를 소모하지 않는다.
- 첫 목록을 만들기 전의 잘못된 `operations` 반복도 정체 감지 대상이다. 적용되지 않은 호출은 성공 캐시에 넣지 않아 수정한 인자로 복구할 수 있다. 결과가 길어 축약돼도 미적용 여부와 형식 수정 안내를 유지하고, 적용된 변경은 적용 여부·새 버전·현재 항목 ID를 유지한다.
- 사용자 요구와 완료 조건은 `task_state.completion`에 보존한다. 목록에서 항목을 삭제해도 문서 근거·검증 조건은 해제되지 않는다. 체크포인트와 이어 실행은 목록을 유지하며, 새로운 사용자 작업은 새 목록으로 시작한다.

```json
{"action":"apply","expected_revision":0,"operations":[{"op":"insert","texts":["요청 처리 흐름 조사 및 섹션 저장","최종 문서 검증"]}]}
```

반환된 ID와 버전을 사용해 선행 작업을 삽입한다.

```json
{"action":"apply","expected_revision":1,"operations":[{"op":"insert","texts":["누락된 입력 정규화 함수 확인"],"before":"T1"}]}
```

나중에 `T1`이 너무 크다는 사실을 알았다면 현재 버전을 사용해 나눈다. `T1`은 첫 세부 작업의 ID로 유지된다.

```json
{"action":"apply","expected_revision":2,"operations":[{"op":"split","id":"T1","texts":["요청 처리 흐름의 근거 확인","흐름 섹션 저장 및 검증"]}]}
```

목록 한도와 일반적인 진행 정체는 먼저 집중 복구 단계로 전환한다. 미완료 할 일 앞에서 최종 답변만 반복하거나 `task_plan`이 `applied=false`를 되풀이하는 경우, 이전 내용으로 돌아가는 파일 수정과 함께 결과 없는 회차로 센다. 서로 다른 파일 수정도 할 일 진행·섹션 작성·인용 해소 없이 계속되면 집중 복구한다. 문서 작업은 아래 [마감 단계](#마감-단계)의 진척 사다리로 반복을 제한한다. 거절된 최종 답변(인용 오류 포함) 다음에는 도구 동작을 요구한다. 사용자 취소, 전체 시간·토큰 예산, 복구할 수 없는 실제 오류의 제한도 적용한다.

### 마감 단계

문서 작업의 반복은 하나의 진척 점수로 판단한다. 점수는 문서 섹션 수(2)와 비어 있지 않은 줄 수의 최고치, 줄어든 문서 검토 지적, 충족된 완료 조건(2), 새로 전달된 근거 수(단계와 관계없이 언제나. 이전에는 조사 단계·첫 저장 전·읽지 않은 인용이나 검토 보완이 있을 때만 세어, 저장 뒤 예산 후반의 추가 조사가 정체로 보였다)를 더한 값이다. 근거 수는 출력 문서를 뺀 프로젝트 파일에서 전달된 서로 다른 줄 수(파일 버전별)다. 이미 전달된 줄을 다시 읽거나 출력 문서를 읽으면 늘지 않는다. 같은 기준으로 진척 사다리, 같은 결과 반복, 실질 진척 없는 요청 수, 이정표 없는 편집 수를 판단한다. 전에는 새 조회 하나하나를 새 근거로 세어, 출력 문서 재독 22회와 이미 읽은 범위 재독 12회가 매번 정체 감지를 초기화했다. 문서 검토 지적 몫은 승인 뒤의 수정으로 새 검토 주기가 시작돼도 앞 주기까지 쌓인 값을 유지한다(이 몫이 0으로 돌아가 승인 뒤 보완 수정이 다음 승인 전까지 진척으로 잡히지 않던 문제). 새 주기는 첫 검토를 기준으로 삼아 그 뒤에 줄인 지적만 더하므로, 다시 고친 문서를 곧바로 다시 승인받는 것만으로는 진척이 되지 않는다. 읽지 않은 인용 범위를 읽어 해소하는 작업도 진척으로 잡힌다. 문서를 쓰기 전의 탐색은 진척이므로, 작업 성격 때문에 안내가 작성 단계로 바뀌어도 탐색 중에 마감되지 않는다. 문서 없이 6라운드가 지나면 그 요청만 작성 단계로 안내하고 이 안내는 작업 단계에 저장하지 않는다. 그래서 첫 저장 뒤 예산상 조사 단계라면 다음 섹션을 위한 새 근거도 진척으로 센다(저장했던 안내가 남아 라이브 실행이 다음 섹션을 읽는 동안 15/24까지 올라간 문제). 공급자 장애로 대기한 뒤 다시 보낸 요청은 응답이 없던 요청을 대신하므로 작업 라운드·진척 사다리·마감 라운드에 세지 않는다. 모두 최고치 기준이라 이전 상태로 되돌리거나 할 일을 완료·재개해도 오르지 않는다. 문서 검토·완료 조건 검증 요청은 진척 사다리에 세지 않는다. 실패한 검토 응답은 페이지 건너뛰기와 미검토 처리로 이미 제한되기 때문이다(느리지만 진행 중인 라이브 실행의 검토가 사다리를 4에서 18까지 올린 문제). 마감 단계의 요청 수에는 재시도한 검토 응답을 계속 센다. 모델이 `task_state`로 draft 단계를 선언해도 예산상 조사 단계라면 다음 섹션을 위한 새 근거를 진척으로 센다.

| 점수가 오르지 않은 요청 | 동작 |
|---|---|
| 감지 횟수 × 1 (기본 8) | 집중 안내 |
| 감지 횟수 × 2 (기본 16) | `file_list`·`source_search`·`symbol_search`·`code_outline` 숨김. `file_read`·`symbol_read`는 유지 |
| 감지 횟수 × 3 (기본 24) 또는 남은 예산 ≤ 마감 예산 비율(기본 10%), 또는 남은 시간 < 이 실행의 평균 요청 시간 × 6(검증 예산 비율만큼의 시간이 상한) | 마감 단계 |

문서 작업에서 모델이 텍스트도 도구 호출도 없는 빈 응답을 내면, 다음 요청의 `run_guidance.recovery_reason`에 연속 빈 응답 횟수를 적고 도구 호출 강제(`tool_choice: required`)를 풀어 같은 요청이 반복되지 않게 한다(일부 공급자는 강제된 도구 선택에 추론만 내고 빈 응답을 돌려준다). 빈 응답이 3회 연속이면 진척 사다리를 기다리지 않고 마감 단계(`empty_response`)로 들어간다. 라이브 실행에서 같은 요청이 24회 반복돼 입력 1.4M 토큰을 쓴 뒤에야 정체 마감된 문제를 막는다.

마감 단계에서는 탐색·기억 도구를 막고(저장된 문서가 아직 없으면 `file_read`·`symbol_read`·`source_lookup`까지 막고 수집한 근거로 문서를 바로 만들라고 지시한다), 모델에 수집한 근거로 문서를 마무리하라고 지시한다. 최대 12회 요청이 허용된다. 마감 단계에서는 요청이 고수위(`high_water`)를 넘는 것만으로 체크포인트를 시작하지 않고, 입력 예산을 넘을 때만 시작한다(입력 예산은 정리 요청 공간을 이미 예약한다). 체크포인트 요청은 12회에 세지 않으며, 마감 요청으로 센 회차가 체크포인트로 바뀌면 그 회차를 돌려준다. 라이브 실행에서 마지막 마감 요청이 체크포인트가 되고 이어진 정리 요청 4회(입력 약 36만 토큰)가 끝나자마자 `closing_round_limit`으로 마감된 문제를 막는다.

- 읽지 않은 인용 범위는 마감 단계에서도 `file_read`로 읽거나 인용을 읽은 줄로 좁혀 해소한다. 남은 범위는 마감 보고에 `근거 미확인`으로 표시하며 검증된 것으로 보고하지 않는다.
- 문서 검토와 완료 조건 검증은 마감 단계에서 각각 한 번만 실행한다. 첫 최종 답변의 거절은 한 번의 보완 기회로 쓰고, 두 번째 최종 답변은 남은 문제를 보고하며 수락한다.
- 12회 요청을 모두 쓰거나 실행 예산이 소진되면 모델 호출 없이 런타임이 마감 보고를 작성한다. 마감 시각이 모델 요청 도중에 와도 같다(느린 모델에서는 거의 항상 요청 도중에 온다). 남은 시간이 이 실행의 평균 요청 시간의 절반보다 짧으면 끝나지 못할 요청을 보내지 않고 바로 마감 보고를 작성한다. 실행 중 설정 변경으로 모델이 바뀌면 평균 요청 시간은 새 모델의 요청으로 다시 잰다(앞 모델의 느린 요청 시간으로 곧바로 마감되지 않게 한다). 라이브 실행이 요청 도중 마감 시각을 맞아 미완료 보고 없이 `blocked`로 끝난 문제를 막는다.
- 마감 결과는 `complete_with_gaps`(화면: 완료 · 미확인 있음)다. 읽지 않은 인용 범위, 소스 인용이 없는 문서, 미완료 할 일, 남은 문서 검토 지적, 미충족·확인 불가 완료 조건, 구조 점검 문제, 미확인 사항을 최종 답변 끝과 진행 패널에 모두 표시한다(최대 30건). 마지막 완료 검토 뒤 산출물은 그대로이고 근거·작업 기록만 바뀌었다면 "다시 검토하지 못했다"는 항목과 함께 마지막 검토의 미충족 조건을 `완료 조건 R0 (마지막 검토: 미충족)` 형태로 보고한다. 산출물이 바뀌었다면 이미 보완됐을 수 있으므로 미검토로만 보고한다.
- 이 작업에서 저장했고 제목 외 본문이 있으며 마지막 저장 이후 바뀌지 않은 문서만 마감할 수 있다. 문서가 없거나 외부에서 바뀌면 `closing_round_limit`으로 중단한다.
- 이어서 실행하면 새 예산으로 사다리가 다시 시작되고, 미확인 항목을 실제로 검증하면 완료로 바뀐다.

검토 응답이 3회 연속 형식에 맞지 않으면 그 검토 페이지만 건너뛰고 다른 페이지에서 모은 지적은 그대로 검증·보완으로 넘긴다. 잘못된 도구 호출이나 크기 초과로 내용을 읽기 전에 거부된 검토 응답도 같은 형식 오류로 센다(이전에는 안내 없이 재시도했고, 검토를 생략한 뒤 답변을 다시 요구했다). 건너뛴 문서 줄 범위는 승인을 막으며, 남은 지적이 없으면 "문서 검토 — N–M줄은 검토를 마치지 못했습니다."로 보고한다. 한 문서 범위의 근거가 여러 페이지로 나뉘면 문서 본문·독자 수준 후보(`audience_flags`)·요구사항·이전 지적은 첫 근거 페이지에서만 판단하고, 이어지는 근거 페이지에는 그 범위가 이어진다는 안내만 붙여 이 페이지의 근거가 뒷받침하거나 반박하는 사실·인용 지적만 내게 한다(근거 페이지마다 같은 독자 수준 지적 7개를 되풀이해 응답마다 출력 3천~1만 토큰을 쓴 실행이 있었다. 앞서 모은 지적은 런타임이 보존한다). 지적 검증 단계도 같다. 응답이 3회 연속 형식에 맞지 않으면 그 검증 묶음의 지적만 건너뛰고 나머지 지적을 계속 검증한다. 건너뛴 지적의 문서 구간(구간이 없는 지적은 문서 전체)은 확인하지 못한 범위로 보고하며, 이전에 확정된 지적을 다시 낸 것이면 그 지적을 보완된 것으로 세지 않는다(이전에는 검토 전체를 생략해 확정된 지적까지 버렸다). 완료 조건 검증도 조건 페이지 단위로 같다. 건너뛴 조건은 판정하지 않고 나머지 조건을 검증한다. 판정한 조건에 미충족이 있으면 보완 작업을 이어가고, 판정한 조건이 모두 충족이면 결과를 미검토로 수락한다. 일부 조건만 건너뛰었으면 "완료 조건 R0 (검토 미완료) — 조건 내용"처럼 그 조건을 보고한다. 마감 단계에서는 형식에 맞지 않는 응답 1회로 그 페이지(검증 묶음·조건 페이지)만 건너뛰고 나머지 검토를 이어간다. 남은 지적이 없고 판단할 것도 없으면 그 결과를 미검토로 보고한다(전에는 마감 단계의 깨진 응답 하나로 검토 전체를 생략해, 이미 검토한 페이지와 다른 페이지에서 모은 지적까지 버린 실행이 두 번 있었다). 이렇게 검토가 판정 없이 끝나면, 그 검토를 시작한 최종 답변을 모델에게 다시 요구하지 않고 그대로 최종 확인에 넣어 미검토로 수락한다(마감 단계에서 답변을 다시 요구받은 라이브 실행이 수정만 이어가다 마감 시각을 넘긴 문제). 문서가 바뀌면 다시 검토할 수 있다. 문서 검토와 완료 조건 검증 요청은 처음부터 설정된 출력 한도로 보낸다(추론 모델이 4096 토큰의 짧은 첫 한도를 추론에 다 써서 응답이 끊겼다). 검토 응답을 받지 못하면, 즉 JSON이 닫히기 전에 출력 한도에서 끊기거나 요청이 시간 초과(응답 데이터 없음, 504, 공급자의 유휴 시간 초과)로 끝나면, 그 페이지의 문서 줄 수를 절반으로 줄이고, 근거는 응답을 받지 못한 요청에 실린 근거 토큰의 절반을 상한으로 해 한 번 더 요청한다. 같은 요청을 다시 보내면 같은 방식으로 끝나기 때문이다. 이 상한은 같은 작업의 이후 페이지에도 그대로 적용된다(전에는 요청마다 남은 근거 묶음 수의 절반만 담아, 입력 한도에 한참 못 미치는 요청이 남은 것의 절반·4분의 1·묶음 1개로 줄었다. 137줄을 검토하는 데 요청 13번이 들어 리뷰가 제한 시간 안에 끝나지 못한 실행이 있었다). 지적 검증은 응답 없던 요청에 실린 지적 수의 절반을 상한으로 하고, 이후 검증 묶음도 그 크기로 보낸다. 문서 검토 페이지의 줄이기와는 따로 센다(전에는 검토 페이지를 줄인 횟수만큼 남은 지적 수를 매번 줄여, 지적 6건을 1건씩 검증한 실행이 있었다). 완료 조건 검증은 한 페이지의 조건 수를 절반으로 줄인다. 문서 검토의 줄이기는 작업당 최대 두 번이며, 이미 두 번 줄인 페이지나 지적·조건이 하나뿐인 요청은 같은 크기로 한 번 더 요청한다. 다시 받지 못하면 그 페이지(검증 묶음·조건 페이지)를 건너뛰고 나머지 검토를 이어간다(형식 오류 3회로 건너뛴 경우와 같이 보고한다). 응답을 받지 못한 페이지는 마감 단계에서도 같다: 절반으로 줄여 한 번 더 요청하고, 다시 받지 못하면 그 페이지만 건너뛰고 나머지 검토를 이어간다. 다시 보낸 검토 요청은 마감 단계의 요청 횟수(12회)에 포함된다. 전에는 마감 단계에서 응답 없음도 1회로 검토 전체를 생략해, 첫 검토 페이지가 공급자 유휴 시간 초과(504)로 끝난 실행이 마감 요청 9회를 남기고도 문서 검토 없이 끝났다. 문서 작업의 검토 요청은 시간 초과를 클라이언트에서 재시도하지 않고, 공급자 장애 대기(10·30·60·120초 뒤 재전송)로도 넘기지 않는다. 라이브 실행에서 추론 모델의 검토 페이지가 504 유휴 시간 초과로 끝난 뒤 같은 요청을 기다렸다 다시 보내며 실행이 11분 멈췄다. 429나 다른 5xx 같은 일시 오류의 빠른 재시도는 그대로 적용한다. 줄인 크기는 같은 작업의 이후 검토에도 이어지지만, 모델이 바뀌면(문서 검토는 입력 한도가 바뀌어도) 처음 크기로 돌아간다. 같은 방식은 질문 모드의 요청에도 적용한다. 요청 변경 확인(메시지 판별)은 응답을 받지 못하면 선택 문맥(과거 대화·계획)을 절반 크기로 줄여 한 번 더 요청하고, 다시 받지 못하면 `message_routing_unanswered`로 멈춘다. 기존 작업에 대한 질문 답변은 작업 상태 요약의 긴 문자열을 절반으로 줄여 한 번 더 요청하고, 다시 받지 못하면 `question_unanswered`로 멈춘다. 두 경우 모두 작업은 그대로 보존되고 같은 메시지를 다시 보내면 된다. 일반 작업 요청과 기억 정리 요청은 줄이거나 건너뛸 부분이 없어 이 방식 대신 기존의 재시도와 공급자 장애 대기를 따른다. 문서 검토·완료 조건 검증 요청은 엄격한 JSON Schema 출력을 요청하고, 서버가 거부하면 JSON 모드, 그다음 형식 지정 없음으로 전환한다. 거부한 서버·모델 조합은 프로세스 동안 기억해 다음 요청부터 바로 JSON 모드를 쓴다. JSON 모드까지 거부하고 형식 지정 없이 보낸 같은 요청이 성공한 서버·모델 조합도 기억해, 다음 요청부터는 형식 지정 없이 보낸다(형식을 빼도 실패한 400은 형식 문제로 보지 않는다). 라이브 실행에서 이 기억이 없어 모든 검토 호출이 거부되는 시도를 한 번씩 더 냈다. 검토 응답이 `{"issues":[...]}`·`{"decisions":[...]}`·`{"checks":[...]}` 대신 목록 배열만 보내면 그 배열을 목록으로 받아들인다. 객체도 배열도 아니면 기대하는 형태를 오류에 적는다. 엄격한 JSON이 거절한 응답은 문자열 안의 줄바꿈·탭 같은 제어 문자를 이스케이프하고 ANSI 색상 코드(`ESC[32m` 등)를 걷어낸 뒤 한 번 더 읽는다. 그래도 읽히지 않으면 원래 오류로 거절한다. 그러면 인용 하나가 잘못돼도 응답 전체가 아니라 그 지적만 대조에서 걸러진다(라이브 실행에서 검토 모델이 인용 속 라벨을 터미널 색상 코드로 감싸, 마지막 시도 응답이 통째로 거절되고 1–98줄이 미검토로 남았다). 재검토 요청은 이전 지적(`F1`…)과 마지막 검토 이후 바뀐 섹션 목록을 함께 전달하며, 바뀌지 않은 섹션에 새로운 사소한 지적을 내지 않도록 지시한다. 검토는 문서를 페이지로 나눠 보므로, 이전 지적은 그 부분이 해당 페이지 범위 안에 있을 때만 판단하고 범위 밖이면 건너뛰게 한다. 지적 목록에는 그 페이지에 실제로 남아 있는 문제만 적고, 해결 확인이나 "이 페이지에서 볼 수 없음"은 적지 않게 한다(다른 페이지가 볼 수 없다는 이유로 해결된 지적을 되살려 검토가 끝나지 않던 문제).


### 문서 리뷰 지적의 근거 확인

- 리뷰는 자유 문장 대신 유형·현재 문서 구절과 줄 범위·소스 인용·수정 방향을 반환한다. 사실/인용 오류에는 해당 페이지에서 전달된 소스 근거가 필요하다. 문서만 보고 알 수 있는 결함(깨지거나 다른 언어가 섞인 문장, 깨진 Markdown, 문서 두 구절 사이의 모순)은 `document` 유형으로 보고한다. 이 유형은 소스 파일 대신 현재 문서 구절을 근거로 쓰며, 모순의 다른 쪽 구절은 `path: "document"` 출처로 붙인다(문서 전체에서 대조). 소스 근거가 없거나 출처가 모두 문서인 사실/인용 지적은 `document` 유형으로 읽는다. 근거 확인 단계는 이 지적을 문서 원문만으로 판단하며, 소스 근거가 필요해 판단할 수 없으면 `unverified`로 보완 없이 버린다. 필수 내용 누락은 원래 요청과 호출자 조건의 ID로 연결하며 문서 전체 목차를 함께 판단한다.
- 프로그램이 발급한 `F1` 등의 ID는 재검토에서도 유지한다. 같은 ID와 같은 대상의 반복 지적은 페이지별로 병합하며, 같은 문장에 있는 서로 다른 오류는 별도로 남긴다. 새로운 지적의 의미상 중복은 근거 확인 단계에서 확정된 지적에만 합칠 수 있다.
- 문서/소스 인용은 긴 코드 블록을 재작성하지 않고 위치를 특정할 짧은 원문을 사용하도록 요청하며, 프로그램이 실제 주변 문맥을 붙여 의미를 검증한다. 인용을 실제 전달한 페이지 안에서 대조하고, 오류 안내에도 제공하지 않은 파일이나 줄의 내용을 넣지 않는다. 들여쓰기와 끝줄 번호 차이는 인용 내용이 유일하게 일치할 때 실제 위치와 원문으로 보정한다. 문서 인용은 렌더링된 글처럼 `**`·`__`·백틱을 빼거나 여러 줄을 공백으로 이어 붙인 경우도, 그렇게 비교한 내용이 유일하게 일치하면 해당 줄의 원문으로 보정한다(라이브 실행에서 이런 인용 4건이 버려지고 그 범위가 미검토로 남았다). 소스 인용은 `**`·백틱이 코드일 수 있어 그대로 정확히 대조한다. 그 밖에 단어가 다르거나 위치가 모호하면 거부한다. 제안한 UI 문자열이 인용한 소스에 존재하는지 먼저 검사한다. 원문에 없는 인용, 다른 페이지의 지적, 근거 없는 UI 문자열은 잘못된 검토 응답으로 재요청한다. 제거해서 빈 승인 목록으로 처리하지 않는다.
- 전체 문서 페이지 검토 후 새롭거나 바뀐 지적만 묶어 같은 모델에 원문·주변 문맥·소스 대조를 요청한다. 이미 확인한 동일 지적과 근거는 재사용한다. 입력 한도 내에서 묶고 넘으면 나눠 처리하며, 모든 호출은 기존 시간·토큰 예산과 응답 재시도 한도에 포함된다. 확인 불가나 결정 누락은 승인이 아니다.
- 엄격한 스키마 요청에서 공급자 SSE 오류가 반복되면, 설정된 일시 오류 재시도 후 JSON 모드로 한 번만 비교 재시도한다. 시간 초과를 재시도하지 않는 문서 작업의 검토 요청은 시간 초과에 이 비교 재시도도 하지 않는다(형식 문제가 아니다). 서로 다른 요청 두 번이 연속으로 JSON 모드로 복구된 경우에만 해당 서버·모델·스키마 조합을 기억한다(비교 재시도 직전에 풀린 일시 장애와 구분하기 위해서이며, 그 사이 엄격한 스키마 응답이 성공하면 첫 복구 기록을 지운다). 다른 스키마에는 적용하지 않으며, 두 형식이 모두 실패하면 공급자 오류로 남긴다. 프롬프트에도 응답 구조를 명시하고 프로그램의 근거·형식 검증은 그대로 적용한다.
- 확인된 지적만 보완 안내에 공개한다. 검증은 사실 모순·근거 없는 주장·미충족 요구 외에, 개발자가 아닌 독자용 문서가 노출한 내부 식별자(CSS 클래스, API 경로·HTTP 메서드, 저장 키, 컴포넌트·상태·설정 키 이름)를 빼거나 독자가 보는 말로 바꾸라는 지적도 확인한다. 구현 세부를 더 요구하는 지적과 출처 인용 제거 요구는 여전히 기각한다. 중복 병합 뒤의 지적 수와 실제 해결된 지적으로 진행을 판단하며, 단순 표현 변경은 진전으로 세지 않는다. `validation_rounds`, `merged_findings`, `dismissed_findings`와 제한된 검증 로그를 라이브 보고서에 남긴다. 이 대조도 모델 판단이므로 의미적 정확성을 보장하지 않는다.

## 할 일 완료 후 결과 검증

할 일 완료 표시와 사용자 요청의 충족 여부는 별개다. 계획을 사용한 작업, 문서/파일/DB 변경, 명시적 결과물·완료 조건을 선언한 작업은 기본적으로 최종 답변을 보류한 뒤 별도의 읽기 전용 `completion_review`를 거친다. `completion_review_enabled`는 기본 `false`이며(라이브 실행 17회 중 15회가 1차 승인으로 끝나 효과가 작았다) 켰을 때만 이 승인 게이트가 실행된다. 단순 대화에는 기본 검증을 강제하지 않는다. 문서별 쓰기·출처·인용 검사와 정적 문서 감사는 별도로 동작한다.

- 소스 기반 문서 작업에는 범위 조건 `S1`을 더한다. 검토 근거에 프로젝트 지도(`runtime_project_map`)를 넣는데, 프로젝트의 모든 파일을 폴더별로 나열하고(바이너리 파일과 결과 문서 제외) 이번 세션에서 읽은 줄과 문서 인용 여부를 표시한다. 읽은 파일에는 전체 줄 수와 읽은 범위를 함께 적고(`App.jsx[read 120 of 1921 lines (1004-1123), mostly unread, cited]`, 범위가 3개를 넘으면 개수만, 다 읽었으면 `read all N lines`), 파일의 절반 넘게, 그리고 100줄 이상을 읽지 않았으면 `mostly unread`를 붙인다. 코드 파일은 구문 개요(tree-sitter)로 읽지 않은 최상위 선언을 큰 순서로 최대 6개까지 줄 범위와 함께 적는다. 100줄 이상 읽지 않은 읽은 파일은 표시 뒤에 `; unread: App 64-1003, Inspector 1272-1921, +4 more`처럼, 읽은 파일과 같은 폴더의 열지 않은 파일은 `api.js(81 lines: api 1-31, …)`처럼 적는다. 3줄 미만 선언과 Rust `#[cfg(test)]` 모듈 안 선언은 나열하지 않고(앞의 것은 개수에만 넣는다), 테스트 파일은 개요를 만들지 않는다. 한 지도에 최대 12개 파일(덜 읽은 파일 먼저, 그다음 큰 열지 않은 파일)·1초까지만 만든다. 리뷰어는 먼저 요청의 주제와 이름이 겹치는 열지 않은 파일·폴더(요청이 다른 언어면 주제의 영어 이름도), 지도에 적힌 읽지 않은 선언 중 그 주제에 속하는 것(UI 매뉴얼이면 사용자가 보는 화면·페이지·패널·대화상자), 그 주제로 인용했지만 `mostly unread`인 파일을 찾는다. 그런 파일의 읽지 않은 줄도 열지 않은 영역으로 보고, 각각이 요청 범위인지 판단한다. 분명히 요청 범위인 영역이 있으면 `S1`은 미충족이고, `next_action`에 읽을 파일·선언·폴더(최대 3개, 지도에 줄 범위가 있으면 함께)와 보완할 문서 섹션을 적게 한다. 충족이면 이유에 가장 가까운 열지 않은 영역과 제외한 까닭을 적는다. 요청과 관계없는 영역·테스트·요청 이상의 완전성은 요구하지 않는다. 열지 않은 파일과 나열된 선언은 경로와 이름으로만 판단하고 코드가 하는 일을 추측하지 않는다. 지도는 저장된 문서 바로 뒤, 도구 관측 앞에 두며 검토 판정의 지문에는 넣지 않는다.
- 지도의 크기는 프로젝트 크기와 무관하다. 탐색은 완료 검토를 시작하거나 페이지를 요청할 때만 하고 결과를 5분간 재사용한다(판정 확인에서는 탐색하지 않는다). 한 번에 최대 20만 개 파일·1.5초까지 훑고, 멈추면 `truncated`로 표시하며 최상위 폴더 목록을 따로 읽어 훑지 못한 폴더도 `(not scanned)`로 보여 준다. 표시는 항목 400개 예산 안에서 루트와 읽은 파일까지의 경로를 먼저 펼치고, 나머지는 한 깊이의 폴더가 모두 들어갈 때만 그 깊이를 함께 펼친다. 펼치지 않은 폴더는 `이름/(N files, M opened)`로, 펼친 폴더는 파일 이름 최대 40개(읽은 파일 우선)와 `+K more`로 보인다. 탐색이 실패하거나 입력 한도 때문에 지도가 빠지면 `S1`도 빠진다. 라이브 실행에서 "문서화 로직 상세 정리" 문서가 200여 개 파일 중 한 모듈만 읽고도 두 검토를 통과했다. 리뷰어가 작성 모델이 읽은 근거밖에 보지 못해 빠진 영역을 알 수 없었기 때문이다. 또 "ui 사용 심플 매뉴얼" 실행은 `App.jsx` 1921줄 중 120줄만 읽었는데, 지도에 `read 120 lines`만 보여 이 파일이 다뤄진 것으로 판단됐고, 사이드바·상단 버튼·상세 패널이 빠진 매뉴얼이 승인됐다. 다음 실행은 `App.jsx`를 아예 열지 않았고, 리뷰어는 경로만으로는 그 파일에 프로젝트 화면과 상세 패널이 있다는 것을 알 수 없었다.
- 원래 사용자 요청은 `R0`, 작업 시작 전에 호출자가 지정한 완료 조건은 `C1`부터 각각 검사한다. 조건·제약·결과물은 `request_review_criteria`에 보존하며, 모델이 `task_state`에 추가한 작업용 체크리스트를 새 사용자 요구사항으로 취급하지 않는다. 원래 요청과 호출자 조건은 작업 목록의 수정으로 약화되지 않으며 재개·체크포인트 이후에도 유지한다.
- 조사 상태는 현재 런타임 기록을 사용한다. `verified`는 저장된 내용을 검증한 상태로 `written` 단계를 포함한다. 작업용 조건의 문구를 맞추기 위해 `verified`를 `written`으로 되돌리라고 요구하지 않으며, 과거 도구 응답보다 현재 조사 상태를 우선한다. 이 기록만으로 문서의 의미적 정확성을 보장하지는 않는다.
- 각 조건의 판정은 `met`(충족), `unmet`(미충족), `unverified`(확인 불가)다. 모든 조건이 충족되고 `task.unresolved`도 비어야 완료할 수 있다. 존재하는 근거 ID와 구체적인 판정 이유를 요구하며, 파일/외부 작업을 최종 답변의 주장만으로 승인하는 응답은 거부한다.
- 현재 파일 내용·전체 줄 수·해시와 최근 전달된 도구 결과를 대조한다. 해시가 바뀐 과거 읽기 기록은 제외한다. 최대 100개 파일과 최근 16개 도구 관측을 유지하고, 입력은 최대 24,000토큰(설정된 입력 한도가 더 작으면 그 한도), 조건은 요청당 8개씩 검증한다. 도구 관측은 `result_tokens` 안에서 보존하며, 정상적으로 전달한 범위를 다시 3,000자로 자르지 않는다. 본문 없는 반복 읽기 안내와 문서 개요 조회는 새 근거 관측으로 추가하지 않으며, 실제 본문을 전달하는 섹션 읽기는 포함한다. 미리보기·관측 내용이 잘리거나 입력에서 빠지면 명시한다. 부족한 근거는 필요한 범위를 읽는 보완 작업으로 돌아간다.
- 미충족·확인 불가 조건의 구체적인 `next_action`을 같은 할 일 목록에 등록한다. 검토 기준 ID와 할 일 ID를 연결해 같은 조건의 조치 문구가 바뀌어도 기존 항목을 갱신하거나 재개한다. 여러 조건에 같은 조치가 필요하면 하나의 항목을 공유한다. 100개 한도와 상태 예산을 지키며, 등록이 어려워도 조건별 지적 사항과 복구 안내를 남긴다.
- 길이 제한으로 나뉜 답변은 앞부분을 포함한 전체 내용으로 검증하고, 최종 조각의 이어붙이기 표시를 보존한다. 검증 중 재개에도 보류한 답변을 유지한다.
- 동일 결과·근거·조건·답변의 재검증은 이전 판정을 재사용한다. 같은 파일 근거의 읽기 순서와 프로그램이 붙인 참조 번호만 바뀌어도 같은 검토로 취급한다. 실제 근거 내용·포함 범위·파일 해시·호출자 조건·조사 상태·답변 변경은 새 검토를 요구하며, 쓰기와 DB 관측의 순서는 계속 구분한다. 판정의 유효성은 페이지 분할·입력 축소 전의 동일한 검토 자료 지문으로 검사한다. 완료 준비 안내·캐시·응답 수용·진행 UI·최종 미충족 보고가 이 검사를 함께 사용한다. 현재 자료와 다른 과거 지적은 새 보완 작업으로 재등록하거나 현재 미충족으로 보고하지 않고, 재검토가 필요하다고 표시한다. 변경만으로 자동 승인하지 않는다. 할 일 완료/삭제와 작업용 조건 수정만으로 검증을 통과하거나 검증 호출을 반복하지 않는다. 검증 응답 누락·잘못된 ID·허위 근거 ID·잘린 응답은 승인이 아니다.
- 검토 판정의 이유가 300자, `next_action`이 160자, 증거 ID가 8개를 넘으면 잘라서 받는다. 길이만으로 판정 전체를 버리지 않는다(마감 단계의 유일한 완료 조건 검증이 441자 이유 하나로 미검토가 된 라이브 실행).
- 보완 가능한 누락은 즉시 작업을 이어간다. 충족 조건 수가 늘지 않은 검토 3회, 또는 미충족 판정 후 보완 도구 호출 16라운드에서는 첫 미충족 조건의 `next_action`에 집중한다. 문서 작업은 그 이후에도 원인을 명시해 보완을 계속하되, 진척 점수가 계속 오르지 않으면 마감 단계에서 미충족 조건을 보고하며 마감한다. 문서 외 작업은 기존의 6회·32라운드 미완료 보존 기준을 유지한다. 파일 해시가 매번 바뀌더라도 이 보완 횟수는 초기화되지 않는다. 보완 작업(근거 읽기, `task_state` 변경, 문서 수정)으로 결과가 바뀌어도 반려된 조건은 다음 완료 검토 전까지 `completion_review.last_review`에 보완 대상으로 남는다. `completion_review.checks`는 현재 결과에 대한 판정만 담는다. 검증 단계와 보완 중 새 근거의 진척 인정도 그때까지 유지한다. 모델에게 주는 `completion_review_unmet` 안내(`run_guidance.completion_error`)도 그때까지 주되, 보완 할 일을 모두 마쳐 최종 답변 준비가 되거나 마감 단계에 들어가면 뺀다(현재 결과 자체가 반려된 상태라면 유지한다). 그 답변이 다음 검토를 시작하거나 마감이 답변을 요구하므로, "다시 답하지 말라"는 안내가 "지금 답하라"는 안내와 충돌하지 않게 하기 위해서다. 결과가 바뀐 뒤의 이 안내는 체크포인트 정리 요청에는 넣지 않고, 사용자 화면의 세션 오류로는 현재 결과가 반려된 동안만 보인다. 라이브 실행에서 첫 보완 읽기 뒤 이 정보가 모두 사라져 30라운드를 기록 정리에 쓰고 진행 정체로 마감했다. 문서의 잘못된 검증 응답은 오류를 전달해 교정하고, 3회 연속 실패하면 해당 결과의 검증을 생략해 미검증으로 보고한다. 문서 외 작업의 형식 복구는 기존 연속 8회 기준을 유지한다. 조건·보완 목록·반복 횟수는 재개 후에도 남으며, 결과가 실제로 개선되면 이어서 완료 검토를 진행한다. 이 상태를 `complete`로 표시하지 않는다.

동일 모델을 이용한 별도 대조이므로 의미적 정확성을 수학적으로 보장하지는 않는다. 추가 모델 호출은 전체 실행 예산에 포함되며, 유료 공급자에서는 비용이 발생한다. 진행 패널의 완료 조건 검증에는 최근 판정·이유·보완 작업을 표시한다.

## 실행 제어와 UI 설정

`모든 설정 → 실행과 예산`에서 다음 값을 편집할 수 있다. 기본 설정·저장 설정·세션 설정에 동일하게 적용된다.

- 작성·검증 예산 비율: 기본 50%. 실행 토큰 또는 시간 예산이 이 비율 이하로 남으면 조사 결과를 문서로 작성하는 단계로 전환한다.
- 검증 예산 비율: 기본 25%. 읽지 않은 인용과 남은 지적의 처리를 우선하며 전체 파일 목록·빈 쿼리 심볼 탐색을 제한한다. 특정 경로 검색·소스 읽기·문서 수정은 허용한다.
- 동일 범위 반복 조회 제한: 기본 2회. 활성 대화에 동일 파일 해시·줄 범위·문자 오프셋의 결과가 이미 이 횟수 이상 있으면 본문을 재전송하지 않는다. `force_read=true`로 의도적인 재검증을 할 수 있다. 파일 변경이나 컨텍스트 제외 후에는 다시 읽을 수 있다.
- 진행 정체 감지 횟수: 기본 8회. 결과물 변경이나 검증 없이 호출이 누적되면 작성·검증 중심의 복구로 전환한다. 초기 작성 복구에서는 광범위한 재탐색을 줄이고, 검증 중에는 특정 경로·심볼 검색을 다시 제공해 필요한 근거를 찾을 수 있게 한다. 미완료 할 일 앞의 최종 답변, 미적용 계획, 이전 파일 버전으로 되돌리는 수정, 내용 없는 줄 추가는 진전으로 보지 않는다. 탐색만 누적되면 `max(24, 감지 횟수 × 8)`, 검증 없는 수정이 누적되면 `max(32, 감지 횟수 × 8)`에서 원인을 명시해 접근을 바꾼다. 문서 작업에서는 이 기준으로 중단하지 않고, 감지 횟수의 3배 동안 진척 점수가 오르지 않으면 마감 단계로 전환한다. 문서 외 작업은 기존 미완료 보존 기준을 유지한다. 진행 상태는 이어 실행에서도 유지하며, 마감 사다리는 실행마다 새 예산으로 다시 시작한다.
- 마감 예산 비율: 기본 10%. 남은 실행 예산이 이 비율 이하가 되면 문서 작업을 마감 단계로 전환한다. 검증 예산 비율보다 작아야 한다.

작성 비율은 검증 비율보다 커야 하며 두 비율은 0과 1 사이여야 한다. UI에서는 퍼센트로 입력한다. 남은 예산과 단계·읽지 않은 인용 수(`run_guidance.unread_citation_count`)는 진행 패널 및 매 LLM 요청의 현재 상태에 포함된다. 비율은 단계 전환 기준이며 토큰을 별도 계정에 적립하는 방식은 아니다. 모델이 모든 검증을 예산 안에 끝낸다고 보장하지 않는다.

읽기 전용 구조 사전 검사(`document_audit`)는 누적 호출 수로 차단하지 않는다. 인용한 범위를 모두 읽었더라도 구조적 출처 검사가 실패하면 완료로 처리하지 않는다. 모델이 도구 없이 종료하려 해도 실행부에서 같은 검사를 수행하며, 문서 작업은 실패 원인을 도구로 보완한 뒤 다시 검증한다. 별도 내용 검토와 완료 조건 검증까지 통과해야 최종 답변을 공개한다.

## 권장 작업 순서

1. 심볼·경로 검색으로 범위를 좁히고 필요한 소스 줄만 읽는다.
2. 확인한 내용부터 섹션으로 작성하고, 저장 결과의 `citation_check.unread_citations`를 바로 처리한다.
3. 출력 파일 해시나 줄 수는 `document_inspect`로 얻는다. 전체 파일을 다시 읽지 않는다.
4. 오류는 해당 섹션 원문을 수정한다. 문서 끝에 정정 설명을 덧붙이지 않는다.
5. `document_audit`의 읽지 않은 인용과 오류를 처리한다.
6. 최종 답변에 결과 경로·검증 범위·남은 한계를 명시한다. 문서 검토는 그 뒤 런타임이 실행한다.

## 확인한 범위와 한계

모의 LLM과 작은 로컬 fixture로 단계 전환, 반복 회복, 출처 검사, 부분 실패, 한글 문서 이어 읽기, 충돌·범위 제한을 회귀 검증한다. 브라우저 테스트는 외부 API 대신 로컬 SSE 서버를 사용한다. 실제 사용자 서버와 RAM 세션은 재시작하지 않는다.

심볼 검색은 정규식 기반 선언 탐색이며 LSP·AST·호출 그래프가 아니다. 메서드나 여러 줄 선언을 놓칠 수 있고 상수 선언도 포함한다. 문서 제목은 ATX 형식(`# 제목`)을 지원한다. 출처 검사는 지원 표기법의 경로·줄 범위·최신성을 확인할 뿐 모든 설명과 API 예제의 의미를 증명하지 않는다. 이번 변경은 이전 실제 모델 테스트의 실패를 회귀 검증한 것이며, 동일 실제 모델을 통한 500줄 요약 품질·비용 개선 측정은 별도 평가가 필요하다.

## 입력 문서 조회와 읽기 범위

`document_inspect`는 선택 인자 `path`로 입력 문서를 지정한다. 상대 경로는 프로젝트 루트 기준이며, 생략하면 기존처럼 `project.output`을 조회한다. `file_read`와 같은 프로젝트 경계·포함/제외·심볼릭 링크 규칙을 적용한다. 프로젝트 밖에서는 설정된 결과 파일만 허용한다.

```json
{"path":"docs/design.md"}
{"path":"docs/design.md","section":"실행 흐름"}
```

섹션 결과가 잘리면 `next_cursor`의 `tool`을 호출할 도구 이름으로 사용하고 나머지 인자를 그대로 전달한다. 이어 읽기 정보에는 입력 문서의 절대 경로, 섹션, 문자 오프셋, 파일 해시가 포함된다. 파일이 바뀌면 이어 읽기를 거부한다.

섹션을 지정하지 않은 조회는 `coverage`와 목차 항목별 `fully_read`를 반환한다.

- `fully_read_lines`: 해당 파일 버전에서 본문 전체가 전달된 줄 수. 부분적으로 전달된 줄은 제외한다.
- `missing_ranges`: 아직 완전히 전달되지 않은 줄 범위(`start_line`, `end_line`, 양 끝 포함).
- `complete`: 모든 줄의 본문이 전달되었는지 여부. 빈 파일은 참이다.
- `previous_revision_ignored`: 이전 해시의 읽기 기록이 있어 현재 계산에서 제외했는지 여부.
- `missing_range_count`, `next_offset`: 누락 범위 목록의 개수와 다음 페이지 위치. `coverage_offset`과 `limit`으로 페이지를 조회한다. 목차의 `offset`과는 별개다.

읽기 기록은 에이전트가 개별·묶음 토큰 제한을 모두 적용한 **최종 본문**을 전달할 때 저장한다. `file_read`와 섹션 조회의 겹치는 범위를 합치며 한글·부분 줄·CRLF를 처리한다. 목차, 검색 발췌, 원문 보관소에만 남긴 결과, 반복 조회로 생략한 본문은 새 읽기로 계산하지 않는다. 원문 보관소를 통해 텍스트를 회수한 경우도 이 집계에는 포함하지 않으므로 필요하면 해당 파일/섹션 도구로 읽는다.

`file_read`·`symbol_read`는 범위 내부의 LF·CRLF를 원문 그대로 보존하며, 범위 마지막 줄의 종결 개행만 생략한다. 커서와 `line_offsets`는 이 원문 기준 Unicode 문자 위치다. 읽은 본문을 `document_edit`의 `old_text`로 복사할 때는 줄 번호 접두사를 제거하고 공백과 줄바꿈을 유지한다. 단일·배치 patch 모두 공백·개행만 있는 비어 있지 않은 대상을 허용하되, 겹치는 출현까지 포함해 문서 전체에서 정확히 한 번 일치해야 한다.

이는 세션 내 전달 이력이며 이해·의미 검증 또는 현재 활성 컨텍스트 보존을 증명하지 않는다. 체크포인트 이후에도 유지되고 세션 종료 시 사라진다. 파일이 바뀌면 이전 해시 기록을 적용하지 않으며 새 본문 전달 시 해당 파일의 기록을 교체한다. 기록은 세션 메타데이터 용량 제한에 포함한다. 전체 읽기를 강제하는 완료 조건은 추가하지 않는다.

`document_edit`와 `document_edit_batch`는 저장 결과가 이후에도 읽히도록 16MiB 초과 본문과 NUL 문자를 거부한다. 배치 결과가 이 제한을 넘으면 기존 파일은 변경하지 않는다.


## 코드 탐색 옵션

파일명만 필요한 경우 `file_list`의 `mode=paths`를 사용한다. 파일 본문을 열지 않고 일반 파일의 경로를 반환하므로 바이너리·비 UTF-8·대용량 파일도 목록에 포함될 수 있다. 기본 `mode=text`는 기존처럼 읽을 수 있는 UTF-8 텍스트 파일만 반환한다. 두 모드 모두 프로젝트의 포함/제외 규칙과 심볼릭 링크 제외 규칙을 유지하며 `total_files`를 제공한다.

```json
{"mode":"paths","path_glob":"src/**/*.rs","limit":100}
```

`source_search`는 다음 옵션을 지원한다.

| 옵션 | 동작 |
|---|---|
| `path` | 단일 파일의 정확한 경로. glob 문자를 해석하지 않으며 `path_glob`·`pattern`과 함께 사용할 수 없다. 프로젝트 경계와 제외 규칙을 유지한다. |
| `path_glob` | 여러 파일을 좁히는 glob. `pattern`은 기존 별칭이다. |
| `case_sensitive` | 기본 `true`. `false`이면 대소문자를 구분하지 않는다. |
| `whole_word` | 기본 `false`. `true`이면 정규식의 Unicode 단어 경계로 감싼다. 밑줄은 단어 문자이므로 `load`는 `load_all`에 일치하지 않는다. 구두점으로 시작하거나 끝나는 검색에는 적합하지 않을 수 있다. |
| `mode=matches` | 기본값. 일치한 줄과 출처 ID를 반환한다. |
| `mode=files` | 일치하는 파일 경로만 `files` 배열로 반환한다. 출처 ID는 만들지 않는다. |
| `mode=count` | 파일별 `matching_lines`를 `counts` 배열로 반환한다. 한 줄에 여러 번 일치해도 1줄로 센다. 출처 ID는 만들지 않는다. |
| `before`, `after` | `matches` 모드에서 앞뒤 문맥을 각각 0~20줄 제공한다. 기본 0. |

```json
{"query":"handle_request","mode":"files","path_glob":"src/**"}
{"query":"session","case_sensitive":false,"whole_word":true,"before":2,"after":2}
{"query":"TODO|FIXME","regex":true,"mode":"count"}
{"query":"agent|run|db","regex":true,"mode":"files","path_glob":"backend/**/*.js"}
```

`regex`를 생략하면 `|`, `.*` 같은 기호도 문자 그대로 검색한다. 여러 단어 중 하나를 찾으려면 위 예시처럼 `regex=true`를 명시한다.

결과가 없으면 `empty_reason`과 재탐색 안내 `guidance`를 반환한다. `no_searchable_files`는 경로 조건에 맞는 검색 가능한 텍스트 파일이 없는 경우이며, 제외·바이너리·크기 제한도 원인일 수 있다. `no_matching_lines`는 파일을 검색했지만 검색어가 일치하지 않은 경우다. 파일명만 알면 `file_list`의 `mode=paths`, `path_glob=**/파일명`으로 찾고, 검색어는 알려진 식별자나 경로부터 사용한다. 호출 객체·따옴표 형태를 추측한 검색이 비었으면 파일 범위를 유지하면서 검색어를 줄인다.

모든 검색 모드에서 `matched_files`는 검색한 텍스트 파일 수, `matching_files`는 실제 일치가 있는 파일 수, `total_matching_lines`는 일치한 전체 줄 수다. `limit`은 `matches`에서 줄 수, `files`와 `count`에서 파일 수이며 최대 100이다. 다음 페이지는 기존 검색 인자에 `cursor`를 추가한다. `limit`은 바꿀 수 있지만 검색·문맥·모드·경로 필터가 바뀌면 커서가 만료된다.

일치 줄과 문맥 줄은 각각 최대 500 Unicode 문자로 표시하고 생략이 있으면 `truncated=true`를 붙인다. 잘린 일치 줄의 출처 ID는 탐색용이며 인용 검증을 충족하지 않으므로 `file_read`로 전체 줄을 읽어야 한다. `context`에는 일치 줄을 제외한 앞뒤 줄과 줄 번호가 들어간다. 출처 ID는 일치 줄만 가리킨다. 문맥을 검증 근거로 사용할 때에도 `file_read`로 해당 범위를 읽는다.

내용 검색과 심볼 검색은 파일 후보 목록을 만든 뒤 각 파일을 한 번 읽어 텍스트 검사와 탐색을 수행한다. 내용 검색은 반환할 페이지의 결과만 보관하므로 100,000줄이 넘는 일치도 전체 결과를 메모리에 쌓지 않고 페이지 조회할 수 있다. 파일 내용과 검색 조건의 해시를 재검사하므로 다음 페이지에서도 전체 대상 파일을 다시 읽는다. 지속 캐시나 의미 기반 심볼 인덱스는 사용하지 않는다.


## 구조 탐색

구현과 테스트는 Rust이며 JS/Python 보조 구현은 추가하지 않는다. 탐색 대상 언어용 소스 fixture는 Rust 테스트 문자열로 생성한다. 구조 탐색은 [Tree-sitter Rust 바인딩](https://docs.rs/tree-sitter/latest/tree_sitter/)과 언어별 네이티브 문법을 사용한다.

두 도구는 `source-docs` 그룹 또는 개별 이름으로 선택할 수 있다.

| 도구 | 인자와 결과 |
|---|---|
| `code_outline` | `path` 필수. 선택 `query`, `match`, `case_sensitive`, `kind`, `container`, `max_depth`, `view`, `cursor`, `limit`(기본 50, 최대 100). 선언의 종류·소속·위치·`symbol_id`를 반환한다. |
| `symbol_read` | `path`, `symbol_id` 필수. 선택 `start_line`(파일의 절대 줄 번호), `max_lines`(1~2,000), `force_read`. 심볼 범위 안에서 본문과 출처를 반환한다. 범위를 생략하면 기존처럼 전체 심볼 읽기를 요청한다. |

```json
{"path":"backend/src/agent.js","view":"compact","max_depth":0}
{"path":"backend/src/agent.js","query":"handleQuestion","match":"exact","kind":"function"}
{"path":"Store.java","container":"Store","kind":"method","max_depth":1,"view":"compact"}
```

위 인자를 `code_outline`에 전달한 후, 반환된 `symbol_id`를 그대로 `symbol_read`에 전달한다. `name_line`, `name_column`은 이름의 위치이며 줄·열 모두 1부터 시작하고 열은 Unicode 문자 수다.

처음에는 `view=compact`, `max_depth=0`으로 파일의 최상위 구조를 확인한다. 함수 목록에는 `kind=function`, 클래스 메서드 목록에는 `kind=method`를 추가한다. 인자·기본값·선언된 반환 타입은 정확한 이름으로 상세 조회한 시그니처부터 확인한다. 잘리지 않은 시그니처로 답할 수 있으면 본문을 읽을 필요가 없다. 실행 동작을 확인할 때는 `symbol_read`에 `max_lines=30`처럼 필요한 양을 지정하고, 필요하면 심볼 안의 절대 `start_line`으로 이동한다.

- `query`: 이름 검색. 기본 `match=contains`는 부분 일치, `match=exact`는 전체 이름 일치다. `case_sensitive` 기본값은 false다.
- `kind`: 언어 간 공통 분류인 `symbol_kind`로 필터링한다. `function`, `method`, `constructor`, `class`, `struct`, `interface`, `trait`, `impl`, `enum`, `enum_member`, `record`, `annotation`, `field`, `variable`, `constant`, `type`, `module`, `macro`, `property`, `accessor`, `event`, `delegate`, `operator`, `destructor`를 지원한다. 기본값은 모든 종류다.
- `container`: 출력에서 복사한 정확한 소속 경로로 필터링한다. `Store`, `Outer::Inner`처럼 쓰며 대소문자를 구분한다. 빈 문자열은 최상위만 선택한다.
- `max_depth`: 심볼 중첩 깊이의 상한이다. 최상위는 0, 클래스의 직접 멤버는 1이다. AST 노드 깊이가 아니며 기본값은 제한 없음이다. 필터에서 부모가 제외돼도 자식의 소속·깊이는 유지된다.
- `view=compact`: 이름·공통 종류·소속·깊이·위치·심볼 ID만 반환한다. 선언 발췌와 출처 ID를 발급하지 않으므로 본문 근거가 필요하면 `symbol_read`를 사용한다.
- 기본 `view=detailed`: 기존 상세 필드를 유지하며 `symbol_kind`, `depth`를 추가한다. `kind`는 기존 Tree-sitter 노드 이름이고, 필터 인자 `kind`는 공통 분류를 사용한다.

각 심볼의 `location`은 `프로젝트상대경로:시작줄-끝줄` 형식이다. 위치 목록에서는 이 값을 그대로 사용하며, 다른 심볼의 끝 줄과 섞어 범위를 만들지 않는다. 메서드는 클래스 내부에 있으므로 `kind=method`, 정확한 `container`를 사용하고 `max_depth=0`은 지정하지 않는다.

자식 멤버 조회에는 부모의 `qualified_name`을 `container`에 그대로 복사한다. Java 중첩 클래스도 `Service::Inner` 형식을 사용하며 `Service.Inner`로 바꾸지 않는다. 오버로드는 같은 `qualified_name`을 가질 수 있으므로 본문 읽기에는 각각의 `symbol_id`를 사용한다. 빈 구조 조회에는 `empty_reason`, 필터 수정 안내, 최대 12개의 `available_containers`를 반환하며 후보가 더 있으면 `container_suggestions_truncated=true`로 알린다.

JS/TS의 변수에 직접 할당한 화살표 함수·함수 표현식은 `function`으로 분류한다. Java 필드 시그니처에는 타입과 접근 제한자를 포함한다. 여러 변수가 같은 선언문에 있으면 심볼 ID는 각각 구분되지만 시그니처와 본문 읽기에는 공유 선언문이 포함될 수 있다. 분류는 구문 기반이며 모든 언어의 모든 선언 형식을 인식하는 것은 아니다.

### 구조 탐색 범위

Rust(`rs`), JavaScript(`js`, `jsx`, `mjs`, `cjs`), TypeScript(`ts`, `tsx`, `mts`, `cts`), Python(`py`, `pyi`), Java(`java`), C#(`cs`)을 지원한다. 함수·클래스·메서드·인터페이스·Rust impl/trait·Java 생성자/record/enum/annotation 등의 이름 있는 선언을 탐색한다. 모든 언어의 모든 구문이나 타입 관계를 모델링하는 기능은 아니다. `container`는 구문상 소속이며 실제 호출 관계가 아니다. 지원하지 않는 확장자는 `source_search`와 `file_read`로 안내한다.

C#은 블록·파일 범위 namespace(`module`), class/struct/interface/record/enum, 생성자·메서드·지역 함수, 필드·상수, 프로퍼티·인덱서(`property`), get/set/init/add/remove(`accessor`), 이벤트·delegate·연산자·소멸자를 탐색한다. namespace도 심볼 깊이에 포함된다. `namespace Demo.Core;` 아래 `Store` 클래스의 멤버 조회에는 `container:"Demo.Core::Store"`를 사용하며, 반환된 `qualified_name`을 그대로 복사한다. 파일 범위 namespace 심볼 자체의 읽기는 namespace 선언만 포함한다. partial 타입 병합, record의 컴파일러 생성 멤버, 활성 전처리 분기 선택, 의미 기반 참조 해석은 하지 않는다. `.csproj`, `.razor`, `.cshtml`은 구조 탐색 대상이 아니다.

구문 오류가 있으면 `has_parse_errors=true`로 표시하며 부분 구조를 반환할 수 있다. 상세 조회의 `source`는 이름 선언 줄을, `signature_source`는 표시된 시그니처의 줄 범위를 가리킨다. 구조 목록과 시그니처 발췌는 탐색용 출처이므로 인용 검증에는 사용할 수 없다. 시그니처와 선언 발췌는 최대 500문자다. `signature_truncated=true`이면 시그니처가 불완전하므로 필요한 원문을 읽는다. 여러 줄에 걸친 복수 선언에서 뒤쪽 선언의 공통 수식어·타입 접두부가 생략되면 이 플래그와 `signature_context_start_line`을 함께 반환한다. 필요한 공통 접두부는 해당 줄부터 `file_read`로 확인한다. 시그니처는 실행 동작의 근거를 대신하지 않는다. 본문은 `symbol_read`로 확인하며, 한 줄에 여러 선언이 있으면 같은 줄의 주변 코드도 포함된다. 다른 선언만 있는 줄은 해당 심볼의 읽기 범위에 포함하지 않는다.

`symbol_read`의 시작 줄은 심볼 범위 밖이면 거부하고, 요청한 줄 수는 심볼 끝에서 제한한다. 일부 줄만 읽은 결과를 전체 구현을 확인한 것으로 취급하지 않는다. 출력 예산 때문에 잘린 경우 먼저 `file_read` 커서로 요청 범위를 마저 읽는다.

LLM 요청에서는 `file_read`·`symbol_read`의 본문을 `content.numbered_text`의 `절대줄번호|원문`으로 전달한다. 원문을 중복 전송하지 않으며 `line_offsets`는 모델용 표현에서 제외한다. 원시 도구 결과·저장 이력·출처·읽기 기록은 기존 `content.text`와 Unicode 오프셋을 유지한다. 토큰 예산은 원시 표현과 모델용 표현 중 큰 값을 기준으로 제한한다. 줄 중간부터 이어 읽은 경우에도 같은 절대 줄 번호와 `first_line_complete`·`last_line_complete`를 유지하며, 번호 접두사는 원문이나 커서 오프셋에 포함되지 않는다. 빈 본문에는 가상의 줄을 추가하지 않는다.

심볼 ID는 파일 해시와 구문 범위에 연결된다. 파일이 변경되면 `symbol_read`와 목차 커서는 만료된다. 본문 읽기는 기존 파일 읽기의 결과 예산·최종 전달 범위 기록을 사용하며, 잘린 결과는 반환된 **file_read 커서**로 이어 읽는다. 2,000줄을 넘는 심볼은 `next_line`에서 새 읽기를 시작하되 `symbol.end_line`까지만 읽는다. 구조 목록이 출력 예산을 넘으면 온전한 심볼 단위로 페이지를 줄이고 `code_outline`의 `next_cursor`로 이어 조회한다. 도구 응답의 `next_cursor`에는 경로와 필터를 포함한 후속 호출 인자를 제공한다. 모든 필터와 `view`를 유지해야 하며 `limit`만 변경할 수 있다. 변경된 조건이나 소스로 커서를 재사용하면 거부한다. 예산이 심볼 하나도 담을 수 없을 만큼 작은 경우에만 원문 보관소로 이어 조회한다.

### 테스트

`cargo test`는 지원 문법의 구조 추출, 오래된 심볼·커서 거부, 본문 결과 예산·이어 읽기를 검증한다. 구조 목록을 반복 축소하거나 여러 페이지로 읽어도 심볼이 누락·중복되지 않는지, 심볼 하나도 담지 못하는 예산에서는 원문을 보존하는지도 검사한다. 구조 탐색 테스트만 실행하려면 `cargo test --test suite structure::`를 사용한다.

문서 작업 초기화와 최종 모델 검토는 [소스 문서 작업·검토 설계](source-document-review.md)를 참고하세요. `document_edit`는 쓰기 직후 제한된 인용 오류 목록도 반환합니다.

## 조사 도구 제거와 체크포인트 저장 완화 (2026-10-06)

라이브 실행 29회(완료 17회)의 `report.json`을 라운드별로 분류한 결과, `investigation`(upsert·verify·verify_batch·final_check·mark_gap) 전용 라운드가 중앙값 10%(최대 18%), 입력 토큰의 중앙값 12%(최대 26%)를 차지했다. 그 검증이 실제로 잡은 것은 인용 범위를 읽지 않은 `source_coverage_missing` 7건뿐이었고, 같은 결함은 문서 검토가 인용 줄을 디스크에서 직접 읽어 대조하므로 중복이었다. 반면 모델이 항목을 끝내 등록하지 않아 리뷰 자체가 실행되지 않은 채 `complete_with_gaps`로 끝난 실행이 3회 있었고, 조사 절차를 유도하는 안내·재연결·보충 장치가 계속 늘었다.

- `investigation` 도구와 조사 항목 상태(`investigations`, `require_investigation`, `verification_events`, `retire_investigation_ids`), `final_check`·`mark_gap`, 미등록 항목 안내(`unregistered_document`)를 제거했다. 진행 패널의 조사 목록과 세션 API의 `investigations` 필드도 사라졌다.
- 조사 절차가 보장하던 "인용한 줄을 실제로 읽었는가"는 런타임 자동 검사로 남겼다. `src/tools/documentation.rs`의 `unread_citations`가 전달된 근거 레지스트리(`sources`)에서 현재 파일 버전의 완전한 줄 범위를 모아 문서의 모든 인용과 대조하고, 읽지 않은 범위를 파일별로 합쳐 `citation_check.unread_citations`(매 저장), `document_audit`의 `unread_citation`, `run_guidance.document_readiness`, 완료 검토 증거 `runtime_citation_coverage`, 마감 보고의 `근거 미확인`으로 전달한다. 하나라도 남으면 최종 완료를 거부한다. 모델은 ID를 모을 필요 없이 그 범위를 읽거나 인용을 좁히면 된다.
- 완료 판정은 저장된 문서 + 구조 감사(읽지 않은 인용 포함) + 문서 검토(+ 켜져 있으면 완료 조건 검토)다. 소스 문서 작업에서 문서를 저장하지 않은 최종 답변은 거절한다. `경로:줄` 인용이 하나도 없는 문서도 대조할 소스가 없으므로 최종 답변을 거절하고(`document_citations_missing`) 읽은 범위로 주장 옆에 인용을 달게 한다. 마감 단계의 두 번째 최종 답변은 수락하되, 문서 검토 없이 "소스 인용 — …" 미확인 항목으로 보고한다(인용이 없어 문서 검토를 건너뛴 라이브 실행이 미확인 항목 없이 `complete`로 끝났다).
- 진척 점수에서 항목 점수를 빼고, 읽지 않은 인용이 남아 있는 동안의 새 근거 읽기와 읽지 않은 범위의 감소를 진척으로 센다.
- `completion_review_enabled` 기본값을 `false`로 바꿨다. 완료된 라이브 실행 17회 중 15회가 1차 승인이었고, 거절은 조사 장부 상태를 근거로 한 오탐이었다. 테스트 설정(`compact_test`, `support::compact_config`)은 계속 켠다.
- 체크포인트의 `memory_write` 의무를 없앴다. `checkpoint_complete`는 `progress`만으로 완료되며(`checkpoint_memory_missing` 제거, `no_save_reason`은 선택), 안내는 아직 저장하지 않은 재사용 가능한 발견이 있을 때만 기억을 쓰라고 말한다.

회귀 테스트는 저장 시 미읽은 인용 보고와 파일별 범위 병합, 읽기·파일 변경에 따른 해소·무효화, 긴 범위의 선언 줄 안내, 읽지 않은 인용이 최종 준비·마감 안내를 막는 경로, 인용 읽기만으로 완료 조건 재검토가 시작되는 경로, 기억 저장 없는 체크포인트 완료를 검사한다. 같은 요청의 라이브 비교 실행은 아직 하지 않았다.
