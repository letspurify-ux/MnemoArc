# 문서 조사·작성 도구 개선

## 제공 기능

`source-docs` 선택 시 기존 도구와 함께 다음 기능을 사용할 수 있다.

| 도구 | 사용법과 보장 |
|---|---|
| `file_read` | 전체 줄 수·파일 해시와 `content.line_start`, `content.line_offsets`를 제공한다. `line_offsets`는 반환 텍스트 내 Unicode 문자 위치이며 각 줄의 시작을 가리킨다. 본문을 잘라도 이어 읽기 위치와 줄 지도를 함께 갱신한다. `first_line_complete`·`last_line_complete`가 거짓인 경계 줄은 인용 검증 범위에 포함되지 않으므로 커서로 범위를 끝까지 읽어야 한다. 파일 끝을 지난 읽기는 근거 ID 없이 빈 결과를 반환하고, 빈 근거는 검증에 사용할 수 없다. |
| `document_inspect` | 인자 없이 출력 파일의 해시·실제 줄 수·목차를 조회한다. 목차에는 제목 수준 `level`과 상위 제목을 줄바꿈으로 연결한 `section_path`가 포함된다. 같은 제목이 다른 부모 아래에 있을 때 이 경로를 `section`에 복사해 정확한 섹션을 읽는다. `offset` 또는 `coverage_offset`으로 이어 읽을 때는 첫 페이지의 `hash`를 `expected_hash`로 전달해야 하며, 중간에 파일이 바뀌면 거부한다. |
| `document_edit`의 `section` | `section`, `text`, `expected_hash`, `expected_section_hash`를 받아 해당 제목부터 다음 동급/상위 제목 전까지 교체한다. 자손 섹션도 교체 범위에 포함되므로 작은 수정에는 부분 텍스트 편집을 사용한다. 원래 제목을 유지해야 한다. 새 본문의 끝 공백·빈 줄·줄바꿈 형식은 보존하며, 다음 제목이 있는데 새 본문에 끝 개행이 없을 때만 원래 섹션의 줄바꿈을 붙인다. 코드 펜스 안의 제목은 무시하며 모호한 경로와 외부 편집 충돌을 거부한다. |
| `document_edit`의 섹션 삽입 | `insert_before`·`insert_after`는 `section`으로 지정한 동급 섹션 앞뒤에 새 섹션을 넣는다. `insert_first_child`·`insert_last_child`는 부모 `section` 안에 한 단계 깊은 새 섹션을 넣으며, 자식이 없는 부모에도 쓸 수 있다. 목차의 `section_path`를 복사하면 다른 부모 아래 같은 제목을 구분한다. `expected_hash`로 문서 변경을 검사하고 새 섹션 하나만 허용한다. 네 동작 모두 `document_edit_batch`에서도 사용할 수 있다. |
| `document_edit`의 부분 텍스트 편집 | `replace_text`는 고유한 `old_text`를 `text`로 교체하고, `delete_text`는 `old_text`만 받아 삭제한다. `insert_before_text`·`insert_after_text`는 고유한 `old_text` 앞뒤에 `text`를 원문 그대로 넣는다. 선택적 `section`에 `section_path`를 주면 그 섹션과 자손 안에서만 `old_text`를 찾으므로 다른 부모에 같은 문장이 있어도 수정할 수 있다. 모두 `expected_hash`를 확인하며, 대상이 없거나 범위 안에서 여러 번 나타나면 변경하지 않는다. 같은 동작을 `document_edit_batch`에서도 순서대로 사용할 수 있다. |
| `document_audit` | `path.ext:10-20` 및 Markdown 링크의 `path.ext#L10-L20` 출처를 검사한다. 일반 코드 펜스 안의 예시는 인용 검사에서 제외하되 Mermaid의 소스 인용은 검사한다. 파일 존재·허용 경로·줄 범위·연결된 소스 변경·문서 섹션·미검증 조사 항목을 한 번에 점검한다. 오류 목록은 페이지 조회 가능하다. |
| `investigation`의 `verify_batch` | `items`에 조사 항목 ID를 키로 하고 `{source_ids: [...], verification_note: "비교 내용"}`을 값으로 전달한다. 최대 20개를 순차 검증하며 항목별 성공/실패를 반환한다. 성공한 항목은 유지하고 실패한 항목은 재시도한다. |
| `symbol_search` | `query`, 파일 glob `pattern`, `cursor`, `limit`으로 JS/TS·Rust·Python 선언을 검색한다. 이름·위치·선언 줄·프로그램 발급 출처를 반환한다. 파일 변경 시 커서는 만료된다. |

일괄 검증은 관련 원문과 실제 문서를 비교한 뒤 호출해야 한다. 단순히 읽은 항목을 자동으로 검증 처리하지 않는다. 기존 ID를 지정한 `upsert`에서 생략한 제목·출처·기억 참조·섹션은 기존 값을 유지하며 같은 제목의 중복 항목 생성을 거부한다. 신규 항목은 제목이 필수이며, 존재하지 않는 ID에 제목 없이 수정 요청하면 오류를 반환한다. 기존 항목을 수정하면 이전 검증 상태는 무효화된다.

## 일반 프로젝트 파일 편집

`file_list`의 `path_glob`과 `source_search`의 `query`로 파일과 내용을 찾고, `file_read`로 본문과 해시를 확인한다. 신규 세션에서는 다음 편집 도구가 기본 활성화된다. 설정된 Markdown 출력 파일은 기존 `document_edit`와 `document_edit_batch`를 사용한다.

| 도구 | 기능 |
|---|---|
| `file_edit` | `path`, `expected_hash`, `old_text`, `new_text`로 정확한 문자열을 교체한다. 한 번만 일치해야 하며 여러 곳을 모두 바꾸려면 `replace_all: true`를 명시한다. |
| `file_write` | `path`, `content`로 새 UTF-8 파일을 만든다. 기존 파일을 전체 교체할 때는 `expected_hash`가 필수다. |
| `file_patch` | `operations` 배열에 최대 32개의 `add`, `update`, `replace`, `move`, `delete` 작업을 순서대로 넣는다. 기존 파일을 처음 수정할 때 `expected_hash`가 필요하며 같은 패치의 후속 작업에서는 생략할 수 있다. 모든 작업을 먼저 검증한 뒤 저장한다. |

모든 경로는 프로젝트 루트 기준 상대 경로다. 제외 경로, 심볼릭 링크, 프로젝트 외부 경로, 바이너리 파일, 16MiB 초과 파일은 수정할 수 없다. 다중 파일 패치의 원본·결과 텍스트 합계는 128MiB로 제한한다. 파일 시스템 오류나 취소가 발생하면 완료된 변경을 되돌리려고 시도하고 복구 오류를 반환한다. 파일 시스템 수준의 다중 파일 트랜잭션을 보장하지는 않는다.

## 순서 있는 할 일 목록

여러 단계가 필요한 작업은 `task_plan`으로 관리한다. 진행 화면에도 같은 목록을 표시하며, 별도의 현재/다음 작업 문구를 작성하지 않는다. 첫 미완료 항목이 현재 작업이고, 완료 후에는 다음 미완료 항목으로 자동 이동한다. 항목은 작은 결과 단위로 나눌 수 있다. 문서 조사와 섹션 저장을 나눴다면 필요한 근거를 확인한 뒤 저장으로 이어가며, 근거 수집만 반복하지 않는다.

- 미완료 최대 **100개**, 완료 기록 최근 **5개**: 목록은 최대 105개를 유지한다. 누적 완료 수는 별도로 보존한다. 항목 설명은 160자, 완료 결과·변경 사유는 240자까지다. 상태에는 첫 미완료 항목 최대 6개만 예산에 맞춰 싣고, 전체 목록은 세션과 화면에 유지한다.
- `list`로 현재 목록·버전을 조회한다. 기본 10개, 최대 20개씩 보여주며 `next_offset`을 다음 호출의 `offset`으로 전달해 이어 본다. `apply`에는 `expected_revision`과 최대 16개 연산을 전달한다. ID는 생성 후 순서가 바뀌어도 유지한다.
- `operations`의 표준 형식은 작업 객체의 JSON 배열이다. 모델이 이를 JSON 문자열로 감싸거나 단일 작업 객체·JSON 문자열 항목 배열로 보내도 의미가 명확하면 정규화한다. 잘린 JSON, ID별 작업 맵처럼 순서가 모호한 형식은 추측해 실행하지 않고 `applied: false`, 잘못된 위치·입력 타입·올바른 예시를 반환한다. 정규화된 호출도 버전·순서·문자 수·개수 제한을 그대로 검사한다.
- `insert`는 `texts`를 추가한다. `before`에 미완료 ID를 주면 해당 항목 앞에 선행 작업을 끼워 넣고, 생략하면 끝에 추가한다. 기존 항목의 순서 변경은 `move`, 설명 수정은 `update`다.
- `split`은 진행 중 또는 뒤에 있는 미완료 항목 하나를 실행 순서대로 2개 이상의 작은 항목으로 나눈다. 첫 항목은 원래 ID를 유지하고 나머지에 새 ID를 붙인다. 완료 항목과 원래 설명을 그대로 반복한 항목은 분할할 수 없으며, 분할한 항목들이 원래 목표를 함께 충족해야 한다. 100개 한도 초과·중복·잘못된 설명이면 전체 묶음을 적용하지 않는다.
- `complete`는 현재 항목에만 적용하며 실제 결과인 `result`를 기록한다. 불필요 항목 삭제(`remove`)와 완료 항목 재개(`reopen`)에는 `reason`이 필요하다. 재개한 항목은 현재 작업 앞으로 이동한다.
- 한도 초과·오래된 버전·잘못된 ID·순서 위반은 기존 목록을 보존하고 `applied: false`와 수정 방법을 반환한다. 실행 실패로 세지 않으며, 현재 작업을 완료하거나 항목을 합치고 불필요한 항목을 제거해 계속 진행한다. 완료와 후속 항목 삽입을 한 번에 처리할 수 있다. 묶음 중 하나라도 실패하면 전체 목록을 변경하지 않는다.
- 목록 수정·기억 저장·체크포인트는 실제 진행으로 세지 않는다. 문서/파일 변경이나 새 검증이 없으면 회복 안내가 유지된다. 미완료 목록을 남긴 최종 답변은 현재 항목 실행으로 돌리며 문서 검증 재시도 한도를 소모하지 않는다.
- 첫 목록을 만들기 전의 잘못된 `operations` 반복도 정체 감지 대상이다. 적용되지 않은 호출은 성공 캐시에 넣지 않아 수정한 인자로 복구할 수 있다. 결과가 길어 축약돼도 미적용 여부와 형식 수정 안내를 유지하고, 적용된 변경은 적용 여부·새 버전·현재 항목 ID를 유지한다.
- 사용자 요구와 완료 조건은 `task_state.completion`에 보존한다. 목록에서 항목을 삭제해도 문서 근거·검증 조건은 해제되지 않는다. 체크포인트와 이어 실행은 목록을 유지하며, 새로운 사용자 작업은 새 목록으로 시작한다.

```json
{"action":"apply","expected_revision":0,"operations":[{"op":"insert","texts":["요청 처리 흐름 조사 및 섹션 저장","최종 문서 검증"]}]}
```

반환된 ID와 버전을 사용해 선행 작업을 삽입한다.

```json
{"action":"apply","expected_revision":1,"operations":[{"op":"insert","texts":["누락된 입력 정규화 함수 확인"],"before":"T1"}]}
```

나중에 `T1`이 너무 크다는 사실을 알았다면 현재 버전을 사용해 나눈다. `T1`은 첫 세부 작업의 ID로 유지된다.

```json
{"action":"apply","expected_revision":2,"operations":[{"op":"split","id":"T1","texts":["요청 처리 흐름의 근거 확인","흐름 섹션 저장 및 검증"]}]}
```

목록 한도와 일반적인 진행 정체는 먼저 집중 복구 단계로 전환한다. 미완료 할 일 앞에서 최종 답변만 반복하거나 `task_plan`이 `applied=false`를 되풀이하는 경우, 이전 내용으로 돌아가는 파일 수정과 함께 결과 없는 회차로 센다. 서로 다른 파일 수정도 할 일 진행·조사 섹션 작성·검증 없이 계속되면 집중 복구한다. 문서 작업은 아래 [마감 단계](#마감-단계)의 진척 사다리로 반복을 제한한다. 거절된 최종 답변(인용 오류 포함) 다음에는 도구 동작을 요구한다. 사용자 취소, 전체 시간·토큰 예산, 복구할 수 없는 실제 오류의 제한도 적용한다.

### 마감 단계

문서 작업의 반복은 하나의 진척 점수로 판단한다. 점수는 작성(1)·검증 또는 미확인 처리(3)된 조사 항목, 문서 섹션 수(2)와 비어 있지 않은 줄 수의 최고치, 줄어든 문서 검토 지적, 충족된 완료 조건(2), 조사 단계에서 새로 전달된 근거 수를 더한 값이다. 모두 최고치 기준이라 이전 상태로 되돌리거나 할 일을 완료·재개해도 오르지 않는다. 검토 요청의 정상 페이지는 세지 않고, 재시도한 검토 응답만 센다.

| 점수가 오르지 않은 요청 | 동작 |
|---|---|
| 감지 횟수 × 1 (기본 8) | 집중 안내 |
| 감지 횟수 × 2 (기본 16) | `file_list`·`source_search`·`symbol_search`·`code_outline` 숨김. `file_read`·`symbol_read`는 유지 |
| 감지 횟수 × 3 (기본 24) 또는 남은 예산 ≤ 마감 예산 비율(기본 10%) | 마감 단계 |

마감 단계에서는 탐색·기억 도구를 막고, 모델에 수집한 근거로 문서를 마무리하라고 지시한다. 최대 12회 요청이 허용된다.

- 근거를 확보하지 못한 조사 항목은 `investigation` `mark_gap`(`id`, 10~400자의 구체적 `reason`)으로 미확인 처리한다. 마감 단계에서만 제공·허용되며, 이미 검증된 항목에는 쓸 수 없다. 미확인 항목은 `final_check`·완료 판정에서 처리된 것으로 보지만 검증된 것으로 보고하지 않는다. 섹션이 있으면 이후 `verify`로 실제 검증해 대체할 수 있다.
- 문서 검토와 완료 조건 검증은 마감 단계에서 각각 한 번만 실행한다. 첫 최종 답변의 거절은 한 번의 보완 기회로 쓰고, 두 번째 최종 답변은 남은 문제를 보고하며 수락한다.
- 12회 요청을 모두 쓰거나 실행 예산이 소진되면 모델 호출 없이 런타임이 마감 보고를 작성한다.
- 마감 결과는 `complete_with_gaps`(화면: 완료 · 미확인 있음)다. 미확인 조사 항목, 미완료 할 일, 남은 문서 검토 지적, 미충족·확인 불가 완료 조건, 구조 점검 문제, 미확인 사항을 최종 답변 끝과 진행 패널에 모두 표시한다(최대 30건).
- 이 작업에서 저장했고 제목 외 본문이 있으며 마지막 저장 이후 바뀌지 않은 문서만 마감할 수 있다. 문서가 없거나 외부에서 바뀌면 `closing_round_limit`으로 중단한다.
- 이어서 실행하면 새 예산으로 사다리가 다시 시작되고, 미확인 항목을 실제로 검증하면 완료로 바뀐다.

검토 응답이 3회 연속(마감 단계에서는 1회) 형식에 맞지 않으면 해당 결과에 대한 검토를 생략하고 미검토로 보고한다. 문서가 바뀌면 다시 검토할 수 있다. 문서 검토·완료 조건 검증 요청은 엄격한 JSON Schema 출력을 요청하고, 서버가 거부하면 JSON 모드, 그다음 형식 지정 없음으로 전환한다. 거부한 서버·모델 조합은 프로세스 동안 기억해 다음 요청부터 바로 JSON 모드를 쓴다. 재검토 요청은 이전 지적(`F1`…)과 마지막 검토 이후 바뀐 섹션 목록을 함께 전달하며, 바뀌지 않은 섹션에 새로운 사소한 지적을 내지 않도록 지시한다.

## 할 일 완료 후 결과 검증

할 일 완료 표시와 사용자 요청의 충족 여부는 별개다. 계획을 사용한 작업, 문서/파일/DB 변경, 명시적 결과물·완료 조건을 선언한 작업은 기본적으로 최종 답변을 보류한 뒤 별도의 읽기 전용 `completion_review`를 거친다. `completion_review_enabled=false`로 모델 검토를 끌 수 있으며, 이 경우 이 승인 게이트는 실행되지 않는다. 단순 대화에는 기본 검증을 강제하지 않는다. 문서별 쓰기·출처·인용 검사와 정적 문서 감사는 별도로 동작한다.

- 원래 사용자 요청은 `R0`, 작업 완료 조건은 `C1`부터 각각 검사한다. 원래 요청은 목록이나 작업 조건의 수정으로 덮어쓰지 않으며 재개·체크포인트 이후에도 유지한다.
- 각 조건의 판정은 `met`(충족), `unmet`(미충족), `unverified`(확인 불가)다. 모든 조건이 충족되고 `task.unresolved`도 비어야 완료할 수 있다. 존재하는 근거 ID와 구체적인 판정 이유를 요구하며, 파일/외부 작업을 최종 답변의 주장만으로 승인하는 응답은 거부한다.
- 현재 파일 내용·전체 줄 수·해시와 최근 전달된 도구 결과를 대조한다. 해시가 바뀐 과거 읽기 기록은 제외한다. 최대 100개 파일과 최근 16개 도구 관측을 유지하고, 입력은 최대 16,000토큰(설정된 입력 한도가 더 작으면 그 한도), 조건은 요청당 8개씩 검증한다. 도구 관측은 `result_tokens` 안에서 보존하며, 정상적으로 전달한 범위를 다시 3,000자로 자르지 않는다. 본문 없는 반복 읽기 안내는 근거 관측을 대체하지 않는다. 미리보기·관측 내용이 잘리거나 입력에서 빠지면 명시한다. 부족한 근거는 필요한 범위를 읽는 보완 작업으로 돌아간다.
- 미충족·확인 불가 조건의 구체적인 `next_action`을 같은 할 일 목록에 등록한다. 검토 기준 ID와 할 일 ID를 연결해 같은 조건의 조치 문구가 바뀌어도 기존 항목을 갱신하거나 재개한다. 여러 조건에 같은 조치가 필요하면 하나의 항목을 공유한다. 100개 한도와 상태 예산을 지키며, 등록이 어려워도 조건별 지적 사항과 복구 안내를 남긴다.
- 길이 제한으로 나뉜 답변은 앞부분을 포함한 전체 내용으로 검증하고, 최종 조각의 이어붙이기 표시를 보존한다. 검증 중 재개에도 보류한 답변을 유지한다.
- 동일 결과·근거·조건·답변의 재검증은 이전 판정을 재사용한다. 같은 파일 근거의 읽기 순서와 프로그램이 붙인 참조 번호만 바뀌어도 같은 검토로 취급한다. 실제 근거 내용·포함 범위·파일 해시·조건·답변 변경은 새 검토를 요구하며, 쓰기와 DB 관측의 순서는 계속 구분한다. 할 일 완료/삭제만으로 검증을 통과하거나 검증 호출을 반복하지 않는다. 검증 응답 누락·잘못된 ID·허위 근거 ID·잘린 응답은 승인이 아니다.
- 보완 가능한 누락은 즉시 작업을 이어간다. 충족 조건 수가 늘지 않은 검토 3회, 또는 미충족 판정 후 보완 도구 호출 16라운드에서는 첫 미충족 조건의 `next_action`에 집중한다. 문서 작업은 그 이후에도 원인을 명시해 보완을 계속하되, 진척 점수가 계속 오르지 않으면 마감 단계에서 미충족 조건을 보고하며 마감한다. 문서 외 작업은 기존의 6회·32라운드 미완료 보존 기준을 유지한다. 파일 해시가 매번 바뀌더라도 이 보완 횟수는 초기화되지 않는다. 문서의 잘못된 검증 응답은 오류를 전달해 교정하고, 3회 연속 실패하면 해당 결과의 검증을 생략해 미검증으로 보고한다. 문서 외 작업의 형식 복구는 기존 연속 8회 기준을 유지한다. 조건·보완 목록·반복 횟수는 재개 후에도 남으며, 결과가 실제로 개선되면 이어서 완료 검토를 진행한다. 이 상태를 `complete`로 표시하지 않는다.

동일 모델을 이용한 별도 대조이므로 의미적 정확성을 수학적으로 보장하지는 않는다. 추가 모델 호출은 전체 실행 예산에 포함되며, 유료 공급자에서는 비용이 발생한다. 진행 패널의 완료 조건 검증에는 최근 판정·이유·보완 작업을 표시한다.

## 실행 제어와 UI 설정

`모든 설정 → 실행과 예산`에서 다음 값을 편집할 수 있다. 기본 설정·저장 설정·세션 설정에 동일하게 적용된다.

- 작성·검증 예산 비율: 기본 50%. 실행 토큰 또는 시간 예산이 이 비율 이하로 남으면 조사 결과를 문서로 작성하는 단계로 전환한다.
- 검증 예산 비율: 기본 25%. 기존 미검증 항목을 우선하며 전체 파일 목록·빈 쿼리 심볼 탐색을 제한한다. 원래 요구에서 누락된 조사 항목 추가, 특정 경로 검색·소스 읽기·문서 수정은 허용한다.
- 동일 범위 반복 조회 제한: 기본 2회. 활성 대화에 동일 파일 해시·줄 범위·문자 오프셋의 결과가 이미 이 횟수 이상 있으면 본문을 재전송하지 않는다. `force_read=true`로 의도적인 재검증을 할 수 있다. 파일 변경이나 컨텍스트 제외 후에는 다시 읽을 수 있다.
- 진행 정체 감지 횟수: 기본 8회. 결과물 변경이나 검증 없이 호출이 누적되면 작성·검증 중심의 복구로 전환한다. 초기 작성 복구에서는 광범위한 재탐색을 줄이고, 검증 중에는 특정 경로·심볼 검색을 다시 제공해 필요한 근거를 찾을 수 있게 한다. 미완료 할 일 앞의 최종 답변, 미적용 계획, 이전 파일 버전으로 되돌리는 수정, 내용 없는 줄 추가는 진전으로 보지 않는다. 탐색만 누적되면 `max(24, 감지 횟수 × 8)`, 검증 없는 수정이 누적되면 `max(32, 감지 횟수 × 8)`에서 원인을 명시해 접근을 바꾼다. 문서 작업에서는 이 기준으로 중단하지 않고, 감지 횟수의 3배 동안 진척 점수가 오르지 않으면 마감 단계로 전환한다. 문서 외 작업은 기존 미완료 보존 기준을 유지한다. 진행 상태는 이어 실행에서도 유지하며, 마감 사다리는 실행마다 새 예산으로 다시 시작한다.
- 마감 예산 비율: 기본 10%. 남은 실행 예산이 이 비율 이하가 되면 문서 작업을 마감 단계로 전환한다. 검증 예산 비율보다 작아야 한다.

작성 비율은 검증 비율보다 커야 하며 두 비율은 0과 1 사이여야 한다. UI에서는 퍼센트로 입력한다. 남은 예산과 단계·미검증 항목 수는 진행 패널 및 매 LLM 요청의 현재 상태에 포함된다. 비율은 단계 전환 기준이며 토큰을 별도 계정에 적립하는 방식은 아니다. 모델이 모든 검증을 예산 안에 끝낸다고 보장하지 않는다.

미완료 항목이 있을 때 `final_check`는 우선 처리할 항목을 반환한다. 읽기 전용 구조 사전 검사는 누적 호출 수로 차단하지 않는다. 항목이 모두 검증됐더라도 구조적 출처 검사가 실패하면 완료로 처리하지 않는다. 모델이 도구 없이 종료하려 해도 실행부에서 같은 검사를 수행하며, 문서 작업은 실패 원인을 도구로 보완한 뒤 다시 검증한다. 별도 내용 검토와 완료 조건 검증까지 통과해야 최종 답변을 공개한다.

## 권장 작업 순서

1. 심볼·경로 검색으로 범위를 좁히고 필요한 소스 줄만 읽는다.
2. 조사 항목을 만들고 확인한 내용부터 섹션으로 작성한다.
3. 출력 파일 해시나 줄 수는 `document_inspect`로 얻는다. 전체 파일을 다시 읽지 않는다.
4. 오류는 해당 섹션 원문을 수정한다. 문서 끝에 정정 설명을 덧붙이지 않는다.
5. `document_audit`의 미검증 항목과 오류를 처리하고 `verify_batch`로 비교 결과를 기록한다.
6. `final_check` 결과에 따라 완료 또는 미확인 사항을 명시한다.

## 확인한 범위와 한계

모의 LLM과 작은 로컬 fixture로 단계 전환, 반복 회복, 출처 검사, 부분 실패, 한글 문서 이어 읽기, 충돌·범위 제한을 회귀 검증한다. 브라우저 테스트는 외부 API 대신 로컬 SSE 서버를 사용한다. 실제 사용자 서버와 RAM 세션은 재시작하지 않는다.

심볼 검색은 정규식 기반 선언 탐색이며 LSP·AST·호출 그래프가 아니다. 메서드나 여러 줄 선언을 놓칠 수 있고 상수 선언도 포함한다. 문서 제목은 ATX 형식(`# 제목`)을 지원한다. 출처 검사는 지원 표기법의 경로·줄 범위·최신성을 확인할 뿐 모든 설명과 API 예제의 의미를 증명하지 않는다. 이번 변경은 이전 실제 모델 테스트의 실패를 회귀 검증한 것이며, 동일 실제 모델을 통한 500줄 요약 품질·비용 개선 측정은 별도 평가가 필요하다.

## 입력 문서 조회와 읽기 범위

`document_inspect`는 선택 인자 `path`로 입력 문서를 지정한다. 상대 경로는 프로젝트 루트 기준이며, 생략하면 기존처럼 `project.output`을 조회한다. `file_read`와 같은 프로젝트 경계·포함/제외·심볼릭 링크 규칙을 적용한다. 프로젝트 밖에서는 설정된 결과 파일만 허용한다.

```json
{"path":"docs/design.md"}
{"path":"docs/design.md","section":"실행 흐름"}
```

섹션 결과가 잘리면 `next_cursor`의 `tool`을 호출할 도구 이름으로 사용하고 나머지 인자를 그대로 전달한다. 이어 읽기 정보에는 입력 문서의 절대 경로, 섹션, 문자 오프셋, 파일 해시가 포함된다. 파일이 바뀌면 이어 읽기를 거부한다.

섹션을 지정하지 않은 조회는 `coverage`와 목차 항목별 `fully_read`를 반환한다.

- `fully_read_lines`: 해당 파일 버전에서 본문 전체가 전달된 줄 수. 부분적으로 전달된 줄은 제외한다.
- `missing_ranges`: 아직 완전히 전달되지 않은 줄 범위(`start_line`, `end_line`, 양 끝 포함).
- `complete`: 모든 줄의 본문이 전달되었는지 여부. 빈 파일은 참이다.
- `previous_revision_ignored`: 이전 해시의 읽기 기록이 있어 현재 계산에서 제외했는지 여부.
- `missing_range_count`, `next_offset`: 누락 범위 목록의 개수와 다음 페이지 위치. `coverage_offset`과 `limit`으로 페이지를 조회한다. 목차의 `offset`과는 별개다.

읽기 기록은 에이전트가 개별·묶음 토큰 제한을 모두 적용한 **최종 본문**을 전달할 때 저장한다. `file_read`와 섹션 조회의 겹치는 범위를 합치며 한글·부분 줄·CRLF를 처리한다. 목차, 검색 발췌, 원문 보관소에만 남긴 결과, 반복 조회로 생략한 본문은 새 읽기로 계산하지 않는다. 원문 보관소를 통해 텍스트를 회수한 경우도 이 집계에는 포함하지 않으므로 필요하면 해당 파일/섹션 도구로 읽는다.

`file_read`·`symbol_read`는 범위 내부의 LF·CRLF를 원문 그대로 보존하며, 범위 마지막 줄의 종결 개행만 생략한다. 커서와 `line_offsets`는 이 원문 기준 Unicode 문자 위치다. 읽은 본문을 `document_edit`의 `old_text`로 복사할 때는 줄 번호 접두사를 제거하고 공백과 줄바꿈을 유지한다. 단일·배치 patch 모두 공백·개행만 있는 비어 있지 않은 대상을 허용하되, 겹치는 출현까지 포함해 문서 전체에서 정확히 한 번 일치해야 한다.

이는 세션 내 전달 이력이며 이해·의미 검증 또는 현재 활성 컨텍스트 보존을 증명하지 않는다. 체크포인트 이후에도 유지되고 세션 종료 시 사라진다. 파일이 바뀌면 이전 해시 기록을 적용하지 않으며 새 본문 전달 시 해당 파일의 기록을 교체한다. 기록은 세션 메타데이터 용량 제한에 포함한다. 전체 읽기를 강제하는 완료 조건은 추가하지 않는다.

`document_edit`와 `document_edit_batch`는 저장 결과가 이후에도 읽히도록 16MiB 초과 본문과 NUL 문자를 거부한다. 배치 결과가 이 제한을 넘으면 기존 파일은 변경하지 않는다.


## 코드 탐색 옵션

파일명만 필요한 경우 `file_list`의 `mode=paths`를 사용한다. 파일 본문을 열지 않고 일반 파일의 경로를 반환하므로 바이너리·비 UTF-8·대용량 파일도 목록에 포함될 수 있다. 기본 `mode=text`는 기존처럼 읽을 수 있는 UTF-8 텍스트 파일만 반환한다. 두 모드 모두 프로젝트의 포함/제외 규칙과 심볼릭 링크 제외 규칙을 유지하며 `total_files`를 제공한다.

```json
{"mode":"paths","path_glob":"src/**/*.rs","limit":100}
```

`source_search`는 다음 옵션을 지원한다.

| 옵션 | 동작 |
|---|---|
| `path` | 단일 파일의 정확한 경로. glob 문자를 해석하지 않으며 `path_glob`·`pattern`과 함께 사용할 수 없다. 프로젝트 경계와 제외 규칙을 유지한다. |
| `path_glob` | 여러 파일을 좁히는 glob. `pattern`은 기존 별칭이다. |
| `case_sensitive` | 기본 `true`. `false`이면 대소문자를 구분하지 않는다. |
| `whole_word` | 기본 `false`. `true`이면 정규식의 Unicode 단어 경계로 감싼다. 밑줄은 단어 문자이므로 `load`는 `load_all`에 일치하지 않는다. 구두점으로 시작하거나 끝나는 검색에는 적합하지 않을 수 있다. |
| `mode=matches` | 기본값. 일치한 줄과 출처 ID를 반환한다. |
| `mode=files` | 일치하는 파일 경로만 `files` 배열로 반환한다. 출처 ID는 만들지 않는다. |
| `mode=count` | 파일별 `matching_lines`를 `counts` 배열로 반환한다. 한 줄에 여러 번 일치해도 1줄로 센다. 출처 ID는 만들지 않는다. |
| `before`, `after` | `matches` 모드에서 앞뒤 문맥을 각각 0~20줄 제공한다. 기본 0. |

```json
{"query":"handle_request","mode":"files","path_glob":"src/**"}
{"query":"session","case_sensitive":false,"whole_word":true,"before":2,"after":2}
{"query":"TODO|FIXME","regex":true,"mode":"count"}
{"query":"agent|run|db","regex":true,"mode":"files","path_glob":"backend/**/*.js"}
```

`regex`를 생략하면 `|`, `.*` 같은 기호도 문자 그대로 검색한다. 여러 단어 중 하나를 찾으려면 위 예시처럼 `regex=true`를 명시한다.

결과가 없으면 `empty_reason`과 재탐색 안내 `guidance`를 반환한다. `no_searchable_files`는 경로 조건에 맞는 검색 가능한 텍스트 파일이 없는 경우이며, 제외·바이너리·크기 제한도 원인일 수 있다. `no_matching_lines`는 파일을 검색했지만 검색어가 일치하지 않은 경우다. 파일명만 알면 `file_list`의 `mode=paths`, `path_glob=**/파일명`으로 찾고, 검색어는 알려진 식별자나 경로부터 사용한다. 호출 객체·따옴표 형태를 추측한 검색이 비었으면 파일 범위를 유지하면서 검색어를 줄인다.

모든 검색 모드에서 `matched_files`는 검색한 텍스트 파일 수, `matching_files`는 실제 일치가 있는 파일 수, `total_matching_lines`는 일치한 전체 줄 수다. `limit`은 `matches`에서 줄 수, `files`와 `count`에서 파일 수이며 최대 100이다. 다음 페이지는 기존 검색 인자에 `cursor`를 추가한다. `limit`은 바꿀 수 있지만 검색·문맥·모드·경로 필터가 바뀌면 커서가 만료된다.

일치 줄과 문맥 줄은 각각 최대 500 Unicode 문자로 표시하고 생략이 있으면 `truncated=true`를 붙인다. 잘린 일치 줄의 출처 ID는 탐색용이며 인용 검증을 충족하지 않으므로 `file_read`로 전체 줄을 읽어야 한다. `context`에는 일치 줄을 제외한 앞뒤 줄과 줄 번호가 들어간다. 출처 ID는 일치 줄만 가리킨다. 문맥을 검증 근거로 사용할 때에도 `file_read`로 해당 범위를 읽는다.

내용 검색과 심볼 검색은 파일 후보 목록을 만든 뒤 각 파일을 한 번 읽어 텍스트 검사와 탐색을 수행한다. 내용 검색은 반환할 페이지의 결과만 보관하므로 100,000줄이 넘는 일치도 전체 결과를 메모리에 쌓지 않고 페이지 조회할 수 있다. 파일 내용과 검색 조건의 해시를 재검사하므로 다음 페이지에서도 전체 대상 파일을 다시 읽는다. 지속 캐시나 의미 기반 심볼 인덱스는 사용하지 않는다.


## 구조 탐색

구현과 테스트는 Rust이며 JS/Python 보조 구현은 추가하지 않는다. 탐색 대상 언어용 소스 fixture는 Rust 테스트 문자열로 생성한다. 구조 탐색은 [Tree-sitter Rust 바인딩](https://docs.rs/tree-sitter/latest/tree_sitter/)과 언어별 네이티브 문법을 사용한다.

두 도구는 `source-docs` 그룹 또는 개별 이름으로 선택할 수 있다.

| 도구 | 인자와 결과 |
|---|---|
| `code_outline` | `path` 필수. 선택 `query`, `match`, `case_sensitive`, `kind`, `container`, `max_depth`, `view`, `cursor`, `limit`(기본 50, 최대 100). 선언의 종류·소속·위치·`symbol_id`를 반환한다. |
| `symbol_read` | `path`, `symbol_id` 필수. 선택 `start_line`(파일의 절대 줄 번호), `max_lines`(1~2,000), `force_read`. 심볼 범위 안에서 본문과 출처를 반환한다. 범위를 생략하면 기존처럼 전체 심볼 읽기를 요청한다. |

```json
{"path":"backend/src/agent.js","view":"compact","max_depth":0}
{"path":"backend/src/agent.js","query":"handleQuestion","match":"exact","kind":"function"}
{"path":"Store.java","container":"Store","kind":"method","max_depth":1,"view":"compact"}
```

위 인자를 `code_outline`에 전달한 후, 반환된 `symbol_id`를 그대로 `symbol_read`에 전달한다. `name_line`, `name_column`은 이름의 위치이며 줄·열 모두 1부터 시작하고 열은 Unicode 문자 수다.

처음에는 `view=compact`, `max_depth=0`으로 파일의 최상위 구조를 확인한다. 함수 목록에는 `kind=function`, 클래스 메서드 목록에는 `kind=method`를 추가한다. 인자·기본값·선언된 반환 타입은 정확한 이름으로 상세 조회한 시그니처부터 확인한다. 잘리지 않은 시그니처로 답할 수 있으면 본문을 읽을 필요가 없다. 실행 동작을 확인할 때는 `symbol_read`에 `max_lines=30`처럼 필요한 양을 지정하고, 필요하면 심볼 안의 절대 `start_line`으로 이동한다.

- `query`: 이름 검색. 기본 `match=contains`는 부분 일치, `match=exact`는 전체 이름 일치다. `case_sensitive` 기본값은 false다.
- `kind`: 언어 간 공통 분류인 `symbol_kind`로 필터링한다. `function`, `method`, `constructor`, `class`, `struct`, `interface`, `trait`, `impl`, `enum`, `enum_member`, `record`, `annotation`, `field`, `variable`, `constant`, `type`, `module`, `macro`, `property`, `accessor`, `event`, `delegate`, `operator`, `destructor`를 지원한다. 기본값은 모든 종류다.
- `container`: 출력에서 복사한 정확한 소속 경로로 필터링한다. `Store`, `Outer::Inner`처럼 쓰며 대소문자를 구분한다. 빈 문자열은 최상위만 선택한다.
- `max_depth`: 심볼 중첩 깊이의 상한이다. 최상위는 0, 클래스의 직접 멤버는 1이다. AST 노드 깊이가 아니며 기본값은 제한 없음이다. 필터에서 부모가 제외돼도 자식의 소속·깊이는 유지된다.
- `view=compact`: 이름·공통 종류·소속·깊이·위치·심볼 ID만 반환한다. 선언 발췌와 출처 ID를 발급하지 않으므로 본문 근거가 필요하면 `symbol_read`를 사용한다.
- 기본 `view=detailed`: 기존 상세 필드를 유지하며 `symbol_kind`, `depth`를 추가한다. `kind`는 기존 Tree-sitter 노드 이름이고, 필터 인자 `kind`는 공통 분류를 사용한다.

각 심볼의 `location`은 `프로젝트상대경로:시작줄-끝줄` 형식이다. 위치 목록에서는 이 값을 그대로 사용하며, 다른 심볼의 끝 줄과 섞어 범위를 만들지 않는다. 메서드는 클래스 내부에 있으므로 `kind=method`, 정확한 `container`를 사용하고 `max_depth=0`은 지정하지 않는다.

자식 멤버 조회에는 부모의 `qualified_name`을 `container`에 그대로 복사한다. Java 중첩 클래스도 `Service::Inner` 형식을 사용하며 `Service.Inner`로 바꾸지 않는다. 오버로드는 같은 `qualified_name`을 가질 수 있으므로 본문 읽기에는 각각의 `symbol_id`를 사용한다. 빈 구조 조회에는 `empty_reason`, 필터 수정 안내, 최대 12개의 `available_containers`를 반환하며 후보가 더 있으면 `container_suggestions_truncated=true`로 알린다.

JS/TS의 변수에 직접 할당한 화살표 함수·함수 표현식은 `function`으로 분류한다. Java 필드 시그니처에는 타입과 접근 제한자를 포함한다. 여러 변수가 같은 선언문에 있으면 심볼 ID는 각각 구분되지만 시그니처와 본문 읽기에는 공유 선언문이 포함될 수 있다. 분류는 구문 기반이며 모든 언어의 모든 선언 형식을 인식하는 것은 아니다.

### 구조 탐색 범위

Rust(`rs`), JavaScript(`js`, `jsx`, `mjs`, `cjs`), TypeScript(`ts`, `tsx`, `mts`, `cts`), Python(`py`, `pyi`), Java(`java`), C#(`cs`)을 지원한다. 함수·클래스·메서드·인터페이스·Rust impl/trait·Java 생성자/record/enum/annotation 등의 이름 있는 선언을 탐색한다. 모든 언어의 모든 구문이나 타입 관계를 모델링하는 기능은 아니다. `container`는 구문상 소속이며 실제 호출 관계가 아니다. 지원하지 않는 확장자는 `source_search`와 `file_read`로 안내한다.

C#은 블록·파일 범위 namespace(`module`), class/struct/interface/record/enum, 생성자·메서드·지역 함수, 필드·상수, 프로퍼티·인덱서(`property`), get/set/init/add/remove(`accessor`), 이벤트·delegate·연산자·소멸자를 탐색한다. namespace도 심볼 깊이에 포함된다. `namespace Demo.Core;` 아래 `Store` 클래스의 멤버 조회에는 `container:"Demo.Core::Store"`를 사용하며, 반환된 `qualified_name`을 그대로 복사한다. 파일 범위 namespace 심볼 자체의 읽기는 namespace 선언만 포함한다. partial 타입 병합, record의 컴파일러 생성 멤버, 활성 전처리 분기 선택, 의미 기반 참조 해석은 하지 않는다. `.csproj`, `.razor`, `.cshtml`은 구조 탐색 대상이 아니다.

구문 오류가 있으면 `has_parse_errors=true`로 표시하며 부분 구조를 반환할 수 있다. 상세 조회의 `source`는 이름 선언 줄을, `signature_source`는 표시된 시그니처의 줄 범위를 가리킨다. 구조 목록과 시그니처 발췌는 탐색용 출처이므로 인용 검증에는 사용할 수 없다. 시그니처와 선언 발췌는 최대 500문자다. `signature_truncated=true`이면 시그니처가 불완전하므로 필요한 원문을 읽는다. 시그니처는 실행 동작의 근거를 대신하지 않는다. 본문은 `symbol_read`로 확인하며, 한 줄에 여러 선언이 있으면 같은 줄의 주변 코드도 포함된다.

`symbol_read`의 시작 줄은 심볼 범위 밖이면 거부하고, 요청한 줄 수는 심볼 끝에서 제한한다. 일부 줄만 읽은 결과를 전체 구현을 확인한 것으로 취급하지 않는다. 출력 예산 때문에 잘린 경우 먼저 `file_read` 커서로 요청 범위를 마저 읽는다.

LLM 요청에서는 `file_read`·`symbol_read`의 본문을 `content.numbered_text`의 `절대줄번호|원문`으로 전달한다. 원문을 중복 전송하지 않으며 `line_offsets`는 모델용 표현에서 제외한다. 원시 도구 결과·저장 이력·출처·읽기 기록은 기존 `content.text`와 Unicode 오프셋을 유지한다. 토큰 예산은 원시 표현과 모델용 표현 중 큰 값을 기준으로 제한한다. 줄 중간부터 이어 읽은 경우에도 같은 절대 줄 번호와 `first_line_complete`·`last_line_complete`를 유지하며, 번호 접두사는 원문이나 커서 오프셋에 포함되지 않는다. 빈 본문에는 가상의 줄을 추가하지 않는다.

심볼 ID는 파일 해시와 구문 범위에 연결된다. 파일이 변경되면 `symbol_read`와 목차 커서는 만료된다. 본문 읽기는 기존 파일 읽기의 결과 예산·최종 전달 범위 기록을 사용하며, 잘린 결과는 반환된 **file_read 커서**로 이어 읽는다. 2,000줄을 넘는 심볼은 `next_line`에서 새 읽기를 시작하되 `symbol.end_line`까지만 읽는다. 구조 목록이 출력 예산을 넘으면 온전한 심볼 단위로 페이지를 줄이고 `code_outline`의 `next_cursor`로 이어 조회한다. 도구 응답의 `next_cursor`에는 경로와 필터를 포함한 후속 호출 인자를 제공한다. 모든 필터와 `view`를 유지해야 하며 `limit`만 변경할 수 있다. 변경된 조건이나 소스로 커서를 재사용하면 거부한다. 예산이 심볼 하나도 담을 수 없을 만큼 작은 경우에만 원문 보관소로 이어 조회한다.

### 테스트

`cargo test`는 지원 문법의 구조 추출, 오래된 심볼·커서 거부, 본문 결과 예산·이어 읽기를 검증한다. 구조 목록을 반복 축소하거나 여러 페이지로 읽어도 심볼이 누락·중복되지 않는지, 심볼 하나도 담지 못하는 예산에서는 원문을 보존하는지도 검사한다. 구조 탐색 테스트만 실행하려면 `cargo test --test structure`를 사용한다.

문서 작업 초기화와 최종 모델 검토는 [소스 문서 작업·검토 설계](source-document-review.md)를 참고하세요. `document_edit`는 쓰기 직후 제한된 인용 오류 목록도 반환합니다.
