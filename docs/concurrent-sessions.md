# 여러 세션의 동시 실행

## 사용 방식

- 서로 다른 세션은 동시에 작업한다. 각 세션은 한 번에 하나의 실행만 받는다.
- `max_concurrent_sessions`는 앱 전체 한도이며 기본 4, 허용 범위 1~32다. 기존 설정 파일에도 기본값이 적용된다. 전체 설정에서 저장하거나 `MNEMOARC_MAX_CONCURRENT_SESSIONS`로 지정한다. 저장된 TOML이 환경변수보다 우선한다.
- 한도 변경은 다음 실행 접수부터 반영한다. 한도를 줄여도 실행 중인 세션을 취소하지 않는다. 한도 초과 요청은 409로 거부하며 대기열에 넣지 않는다.
- 세션 중지와 닫기는 해당 실행만 취소한다. 앱 종료는 모든 실행을 취소하고 각 실행이 결과를 정리할 때까지 기다린다.

## 실행과 화면 상태

프로젝트 소속은 소스 폴더가 아닌 고유한 `Project.id`로 구분한다. 같은 폴더·이름·결과 경로를 사용하는 프로젝트도 별도 식별자를 가지며, 사이드바는 각 세션을 소속 프로젝트에 한 번만 표시한다. 프로젝트 이름이나 기본 경로를 수정하거나 목록을 재정렬해도 기존 세션의 소속은 유지된다. 삭제한 프로젝트의 세션과 저장하지 않은 새 프로젝트의 세션은 등록된 다른 프로젝트에 합치지 않고 목록에 별도로 표시한다.

기존 설정의 ID 없는 프로젝트는 불러올 때 각각 식별자를 받고, 설정 저장 시 TOML에 함께 저장한다. 새 프로젝트 초안도 추가 시 식별자를 받는다. 중복 식별자를 가진 설정은 저장을 거부하며, 세션 프로젝트 수정 API는 소속 식별자 변경을 거부한다. ID를 생략한 이전 세션 생성 요청은 정의가 정확히 일치하는 등록 프로젝트가 하나일 때만 그 소속을 사용한다. 여러 프로젝트가 동일하면 새 식별자를 부여한다.

`Core.running`은 세션 ID를 키로 하는 맵이다. 실행 접수는 같은 `Core` 잠금 아래에서 종료 여부, 중복 실행, 전체 한도를 확인하고 실행을 등록한다. 완료·오류·닫기 처리는 자신의 항목만 제거한다. 각 실행의 취소 토큰과 설정·도구 변경 채널도 별개다.

에이전트는 자신의 `Session`을 소유하고 화면에는 스냅샷을 보낸다. 스트림과 스냅샷은 세션 ID로 보관하며 닫히는 세션의 늦은 이벤트는 무시한다. `/api/state`의 `running` 필드는 `{id, closing}` 배열이며 실행이 없으면 `[]`다. 이전의 단일 객체 또는 `null` 응답을 사용한 API 클라이언트는 배열을 처리하도록 바꿔야 한다.

화면의 전송 대기 상태도 세션별로 관리한다. 실행 응답을 기다리거나 화면을 전환해도 같은 세션의 중복 전송을 막으면서 다른 세션의 전송은 허용한다. 서버 실행 목록과 아직 응답을 받지 못한 세션 ID를 합쳐 한도를 계산하므로 같은 실행을 두 번 세지 않는다. 서버가 최종 접수 여부를 판단한다.

## 공유 파일과 데이터베이스

파일을 변경하는 도구(`document_edit`, `document_edit_batch`, `file_edit`, `file_write`, `file_patch`)는 프로세스 내 공통 잠금 아래에서 현재 내용을 읽고 검증한 다음 저장한다. 여러 파일을 바꾸는 패치의 실패 복구도 잠금 안에서 끝낸다. 서로 다른 경로 표현이나 도구를 사용해 같은 파일에 접근해도 검증과 저장 사이에 다른 MnemoArc 쓰기가 끼어들지 않는다. 모델 요청과 읽기는 이 잠금을 사용하지 않는다.

대기 중 취소나 시간 제한이 발생하면 쓰기를 시작하지 않는다. 시간 제한에 따른 내부 취소는 `tool_timeout` 또는 `run_timeout` 원인을 유지하며 사용자 취소와 구별한다. 다른 세션이 먼저 수정한 파일은 기존 해시 검사에서 충돌로 거부한다. 잠금은 파일 변경 손실을 방지하며 서로 다른 작성 의도를 병합하지 않는다. 독립적인 문서는 세션마다 결과 경로를 다르게 지정해야 한다. 외부 편집기나 별도 MnemoArc 프로세스는 이 메모리 잠금에 참여하지 않으며 기존 파일 해시 검사만 적용된다.

`db_execute`는 별도 공통 잠금을 사용한다. DB 쓰기가 오래 걸려도 파일 저장을 막지 않는다. 쓰기 결과가 불확실하면 기존의 앱 전체 실행 차단을 유지한다. 대기하던 쓰기도 잠금을 얻은 직후 불확실 상태를 다시 확인하며, 실패 복구·커밋 오류는 잠금을 풀기 전에 이 상태를 기록한다.

## 검증

- `tests/web_concurrency.rs`: 동시 요청의 접수 한도, 스트림 분리, 개별 취소·닫기·완료, 전체 종료, 설정·도구 변경의 소유 세션, 실행 중 한도 변경.
- `tests/concurrent_writes.rs`: 같은 해시를 읽은 문서 도구와 다중 파일 패치가 경쟁할 때 한 쓰기만 성공하고 실패한 패치가 다른 파일을 남기지 않는지 확인.
- `src/tools/writes.rs`: 대기 중 취소·불확실 상태, 취소 후 늦은 쓰기 방지, 잠금 획득 후 최신 파일 상태 검사.
- `src/agent.rs`: 시간 초과·사용자 취소 구분, 취소 직후 완료된 쓰기 결과 보존, 결과가 불확실한 쓰기의 실행 차단.
- `frontend/test/browser/concurrency.spec.js`: 실제 로컬 API로 두 세션을 실행하고 새로고침·한도 안내·세션 이동·개별 중지·닫기 확인.
- `frontend/test/browser/frontend-lifecycle.spec.js`: 실행 접수 응답이 늦어져도 한도를 중복 집계하지 않고 다른 세션의 전송 대기 상태를 보존하는지 확인.
- 기존 웹·파일 편집·화면 수명 테스트도 새로운 실행 목록과 세션별 잠금에 맞춰 검증한다.
