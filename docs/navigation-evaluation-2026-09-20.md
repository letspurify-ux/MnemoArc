# 등록된 llm_agent 탐색 검증

## 조건

등록된 `llm_agent` 프로젝트와 저장된 모델 설정(`z-ai/glm-5.3-flash`)을 사용했다. 실제 Web API 세션에서 작업별 새 세션을 만들고 `code_outline`, `symbol_read`, `source_search`, `file_read`, `file_list`를 활성화했다. 도구 발견·선택 자체의 평가는 아니다. 기존 결과 문서와 대상 소스는 수정하지 않았다. 구현 및 자동 테스트는 Rust다.

두 질문을 동일하게 유지하면서 수정 전 2회, 줄 번호 개선 후 2회, 검색 복구 안내 후 2회, 조건·오류 전파 안내 보강 후 취소 흐름 1회, 총 7회 실행했다. 아래 토큰 수는 세션 API의 공급자 사용량이며 `estimated=false`, 캐시 토큰은 0이었다. 도구 예산에 쓰는 로컬 토큰 추정치는 별도다. 통계적 성능 평가가 아니므로 한 번의 감소를 일반적인 개선율로 해석하지 않는다.

## 질문과 결과

### A. 함수 목록, 인자, 첫 사용

> backend/src/agent.js의 최상위 함수 이름들을 간결하게 확인한 다음 handleQuestion 함수의 입력 인자와 기본값을 설명해줘. 구현에서 deps와 signal을 처음 어떻게 사용하는지도 확인하고 정확한 파일 경로와 줄 범위를 근거로 제시해줘. 문서는 수정하지 마.

| 실행 | 도구 호출 | 입력 토큰 | 출력 토큰 | 본문 요청 |
|---|---:|---:|---:|---|
| 수정 전 | 3 | 32,573 | 1,328 | 60줄 |
| 줄 번호 개선 후 | 3 | 33,822 | 690 | 45줄 |
| 검색 안내까지 반영 후 | 3 | 34,595 | 927 | 60줄 |

세 실행 모두 함수 필터가 적용된 간결 목록 → 정확한 이름의 상세 구조 → 부분 본문 순서로 탐색했다. 최상위 함수는 24개다. 호출 수와 입력 토큰이 일관되게 줄지는 않았다.

수정 전에는 `capRows`의 실제 범위 43–43을 43–67로, `normalizeQuestion`의 209–209를 209–215로 적는 등 서로 다른 심볼 범위를 섞었다. `deps` 첫 사용은 308행인데 309행으로, `signal` 첫 사용은 311–312행인데 312–313행으로 인용했다. 함수 이름만 보고 요청하지 않은 실행 순서도 추가했다.

마지막 A 실행에서는 24개 함수 위치가 구조 결과와 일치했다. `deps` 308행, `signal` 311–312행, `abortable` 호출 321행, 이벤트 검사 326행, 컨텍스트 신호 전달 344행이 실제 소스와 일치했다. `rawQuestion`에 기본값이 없다는 사실과 런타임 필수 여부를 구분했다. 세 번째 인자 전체의 기본값 `{}`와 개별 멤버에 기본값이 없다는 사실도 구분했다.

### B. 여러 파일의 취소 흐름

> 이 프로젝트에서 /api/chat 응답 중 클라이언트 연결이 끊어지면 취소 신호가 어디로 전달되는지 server.js → agent.js → abort.js 경로를 확인해줘. 정상 응답 종료도 취소되는지, abortable이 원래 작업 자체를 중단하는지도 구분하고 근거 파일 경로와 정확한 줄 범위를 붙여 8문장 이내로 설명해줘. 기존 문서는 수정하지 마.

| 실행 | 도구 호출 | 입력 토큰 | 출력 토큰 |
|---|---:|---:|---:|
| 수정 전 | 7 | 51,260 | 915 |
| 줄 번호 개선 후 | 8 | 50,349 | 1,334 |
| 검색 복구 안내 후 | 6 | 43,653 | 754 |
| 조건·오류 전파 안내 보강 후 | 7 | 43,623 | 794 |

수정 전에는 신호 전달을 `server.js:196-200`으로 인용했으나 실제 코드는 192–195행이다. 취소 catch를 222–225행으로 인용했으나 실제 분기는 215–218행이다. 마지막 실행은 두 범위를 올바르게 제시했고, 162–164행의 연결 종료 처리와 163행의 `writableEnded` 조건도 맞게 설명했다. 최종 실행은 도구 오류 없이 완료했으며, `abort.js` 1–38행과 `server.js` 159–237행을 읽었다.

남은 한계도 확인했다. 최종 실행에서 `close|req.on|res.on`을 `regex:true` 없이 검색해 한 번 비었다. 이후 같은 파일에서 `chat`으로 검색 범위를 복구했다. 이를 보고 문자 검색의 `|`는 OR가 아니라는 조건부 복구 안내를 추가하고 Rust 테스트로 검증했다. 이 마지막 안내 문구에 대해서는 추가 유료 모델 실행을 하지 않았다.

또한 모델은 `throwIfAborted`가 AbortError를 만든다고 단순화했다. 실제 `abort.js:6`은 `signal.reason instanceof Error`이면 기존 오류를 그대로 던지고, 7–9행은 그 외 경우의 오류 생성이다. 요청한 핵심 구분인 “호출부의 대기를 중단하는 것과 원래 작업 자체를 취소하는 것은 다르다”는 설명은 맞았지만, 오류 생성 경로의 세부 표현까지 완전히 정확하지는 않았다. 프롬프트 보강만으로 모든 의미 오류가 사라졌다고 주장하지 않는다.

## 반영한 변경

- 모델 요청의 파일 본문에 절대 줄 번호를 붙인다. 원시 결과·저장 이력·출처·Unicode 커서와 읽기 기록은 바꾸지 않는다. 번호가 붙은 본문과 원문을 중복 전송하지 않는다.
- 실제 모델 표현을 응답 예산과 체크포인트 계산에 반영한다. 기존 예산 제한과 이어 읽기를 유지한다.
- 구조 결과에 프로젝트 상대 경로를 포함한 `location`을 제공해 심볼 위치를 그대로 복사할 수 있게 한다. 이 필드는 구현을 읽었다는 근거가 아니다.
- 빈 검색은 검색할 파일이 없는 경우와 검색어가 맞지 않은 경우를 구분한다. 문자 검색의 `|`를 정규식으로 몰래 바꾸지 않고 명시적인 재호출을 안내한다.
- 알려진 경로·파일명부터 범위를 좁히고, 선언 기본값·필수 여부·조건·오류 전파를 구분하도록 안내한다. Java 메서드에 `max_depth=0`을 적용하지 않도록 안내를 명확히 했다.

자동 테스트는 줄 번호의 빈 줄·한글·부분 줄 처리, 원문 복원, 출력 예산, 커서, 전달 범위 기록, Java 오버로드·중첩 메서드 위치, 빈 검색 복구를 검증한다. 전체 125개 통과, 유료 모델 테스트 2개는 기본 설정에 따라 제외했다. 실제 모델 검증은 위 API 실행으로 별도로 수행했다. Clippy, 포맷 검사, 릴리스 빌드도 통과했다.
